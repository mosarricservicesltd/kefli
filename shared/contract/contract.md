## 1. Principles the contract enforces

Saves are private by default and readable only by the user's key. The phone is the only holder of the user's private key in v1; the browser extension holds its own device key and the user's public key, never the user's private key. The library must survive the operator: by default every save reaches at least one server the operator does not run, normally moments after it is made (the count below shows any that haven't), and so does its text blob while the library is within its storage on the operator's server (section 5, flow decision 117), so a user who restores from their recovery code on a new phone gets their library back even if every operator machine is gone. Past that storage a save's text has only the phone's copy, as it does once the library has used up a day's uploads, until a later day's uploads take it, and for good when the text is over the operator's 8 MB limit (section 5); a new phone fetches such a text again from its page, which may have changed or gone (sections 4.1 and 4.2). A save is backed up once a relay the operator doesn't run has accepted its newest event and, for a save with text, a mirror (section 4.2) that this event names in `text.servers` holds its blob, so a save whose event went out with `text` null while its text stays on the phone isn't backed up. Each client that holds the library counts the saves that aren't backed up, those whose text has only the phone's copy among them, and shows the count (on the phone, under Advanced); the claim that the library outlives the service rests on that count staying near zero while the library is within its storage, so a default relay or mirror that refuses saves is retired within a day (section 3.1, flow decision 93). What needs the operator in v1 is making new saves: registration, the browser extension's inbox and the first copy of each text blob all go through its servers. Everything already saved stays readable and listenable without it. The word "nostr" appears on screen only where the signed-off screens use it: the sign-in route that starts at "Sign in with your nostr app", switching to a nostr app, You for someone signed in with their nostr app, and Delete my data (flow decision 86); "relay" appears only in Advanced (flow decision 76); no other nostr vocabulary reaches a screen.

What the design does not hide, stated plainly so the privacy note can repeat it: relays see the user's public key, the number of saves, when each was made or changed, and a `t` tag showing the saves belong to this app. Nobody but the user can read which URLs they are, or check whether they saved a given page: a save's address is keyed by a secret of the library's own (section 4.3), so hashing a URL doesn't find it. A new save can briefly have only the operator's copy, until a backup server accepts it, and a save's text past the library's storage on the operator's server, or past its day's uploads until a later day's take it, has only the phone's (section 5). The operator's server knows how much text each library keeps there and how much it uploaded in the last 24 hours, the two figures its fair use counts. In v1 no server sees article text in readable form, because listening uses the phone's own voice. The deferred server voices (section 6.1) would let the operator see an article's plaintext while generating its audio and would serve a cached file to any registered user who saved the same text; this paragraph must say so before they ship.

## 2. Identity and keys

Key generation happens on the phone using secp256k1 (NIP-01) when the person taps New here, or when they first share to Kefli before ever opening it (flow decision 6), unless Block Store already holds a mnemonic (below). The key is derived from a BIP-39 twelve-word mnemonic by the NIP-06 path, so that the recovery code is standard and portable to other nostr apps: 128 bits of entropy, the BIP-39 English word list, the BIP-39 seed with an empty passphrase (PBKDF2-HMAC-SHA512, 2,048 rounds), and account 0, `m/44'/1237'/0'/0/0`.

Storage on iOS is the Keychain with `kSecAttrSynchronizable` set, so the key rides iCloud Keychain and returns on reinstall or on a new iPhone signed into the same Apple account. Storage on Android is a file under `noBackupFiles`, encrypted with AES-256-GCM under an Android Keystore key (StrongBox-backed where available), plus the active local identity's mnemonic in one Google Block Store entry, so it restores on a new phone signed into the same Google account. The entry is marked for cloud backup only while Block Store reports end-to-end encryption available, checked again at each launch. `EncryptedSharedPreferences` is not used; the AndroidX security-crypto library is deprecated. The Block Store entry follows four rules:

- A launch with no key on the phone and a mnemonic in Block Store, as after a reinstall or on a new phone on the same Google account, stores that key, skips Welcome and opens Saves while the library restores (section 8, flow decision 79).
- A share made before the app is first opened reads Block Store first. If the entry holds a mnemonic, the share stores that key and saves under it, and the next open goes to Saves while the library restores (flow decision 79). Only when the entry is empty does the share make a new key, and it writes that key's mnemonic there.
- Outside a move, a restore by recovery code or second-phone pairing writes the entry when it stores the identity, and signing in with a nostr app removes it, since that identity has no mnemonic.
- During a move (section 4.8), the early-saves move included, the entry keeps the source key's mnemonic until step 5, then takes the target's, or is removed when the target is a nostr app.

The recovery code is shown only on request from the You tab, labelled "Recovery code", never "seed", "nsec" or "wallet". It is the route back for people who leave Apple or Google, or who never had account sync on.

Existing nostr users sign in through one interface:

```
Signer {
  pubkey()
  capabilities() -> { nip44: bool }
  signEvent(unsigned)
  nip44Encrypt(pubkey, plaintext)
  nip44Decrypt(pubkey, ciphertext)
}
```

Providers are: the local key (generated, or restored from the recovery code, Block Store or another phone), NIP-55 Android signers (Amber and compatible), and NIP-46 remote signers reached by a pasted `bunker://` link. Pasting a private key (an nsec) is not offered in v1 (flow decision 90). A `bunker://` link must carry the remote signer's pubkey as 64 hex characters and at least one `relay` parameter with a `wss://` URL, and may carry a `secret`; any other link is refused at the field (flow decision 91 (b)). The app talks to the signer only on the link's `wss://` relays, with a client keypair it generates and keeps with the identity, and sends `connect` with the parameters `[<signer pubkey>, <secret or "">, <perms>]`. A request unanswered after two minutes fails and changes nothing (flow decision 91 (b)). `perms` asks for the standing permissions up front, so the user is asked once rather than at every action: `nip44_encrypt,nip44_decrypt,sign_event:30078,sign_event:5,sign_event:13,sign_event:10002,sign_event:10063,sign_event:22242,sign_event:27235,sign_event:24242,sign_event:39701`. A NIP-55 signer is asked for the same, as the `permissions` of its `get_public_key` request: `[{"type":"nip44_encrypt"},{"type":"nip44_decrypt"},{"type":"sign_event","kind":30078},…]`, with one `sign_event` entry for each kind in the NIP-46 list. Kind 13 is the seal around a pair-ack (section 4.4); kinds 10002 and 10063 are the relay and server lists (sections 3.1 and 4.2). Every platform runs the same capability probe at sign-in and at step 1 of a move (section 4.8): encrypt the fixed string `kefli-probe` to the signer's own pubkey, decrypt it, compare. A signer that fails is refused. At sign-in the copy is "Your nostr app can’t keep your saves private yet. Try another app, or start a new library on this phone." (flow decision 91 (d)); when switching to a nostr app, the refusal is that screen's own drawn state (flow decision 91 (c)).

Second-phone pairing moves the mnemonic by an online exchange (flow decision 85), and only for an identity that has one: Add another device is hidden for someone signed in with their nostr app, who signs in with it on the new phone instead (flow decision 90). The source phone draws 32 random bytes `s` and a six-digit code `c`, uniform over 000000–999999, fresh for each QR, and shows a QR containing `{v:1, pubkey, secret: <hex of s>, expires}` (five-minute expiry) with the six digits under it. From `s` and `c` it derives 64 bytes with HKDF-SHA256 (input key `s`; salt `kefli/phone-pair/v1` as ASCII; info the six digits as ASCII). The first 32 bytes, in hex, are the `lookup`; the last 32 are an AES-256-GCM key, under which it encrypts `{v:1, mnemonic}` as UTF-8 JSON with a random 12-byte IV and no additional data, and posts the lookup and `base64(IV ‖ ciphertext ‖ tag)` with `POST /phone-offers` (section 6), signed by the user. The target phone scans the QR, checks that `v` is 1 and `expires` hasn't passed (allowing 60 seconds of clock skew), takes the six digits, derives the same bytes and fetches `GET /phone-offers/<lookup>` signed with a throwaway key. A code that finds no offer is the wrong-code field error, and the person can type it again. The target decrypts the offer, derives the key from the mnemonic by the path above, refuses it unless that key's pubkey equals the QR's `pubkey`, stores the identity (Block Store as above) and restores the library (section 8). The QR alone and the code alone are each useless. The operator holds the lookup and ciphertext without `s`, and someone with a photo of the QR still has to guess the six digits online, at most 30 tries an hour from each address (an IPv6 address counted by its /64), within five minutes; once 100 lookups from anyone have found nothing in five minutes, every lookup is refused until those five minutes are up (section 6), so a guesser gets at most two in ten thousand codes against any one offer. That shared count is a deliberate trade of availability for that bound: someone sending wrong lookups from many places can hold up every second phone's setup while they keep going, so one block of addresses (an IPv4 /24, an IPv6 /48) may spend only 10 of the 100, and filling the count takes ten blocks in every five minutes. An offer that is deleted after a few wrong codes would remove the shared count; it needs a change to the lookup, left for a later version.

## 3. Relays

### 3.1 The relay set every user writes to

A new user's app publishes a NIP-65 kind 10002 relay list on first save containing three relays, each for reading and writing: the operator relay (`operator.relay` in `defaults.json`) and the default relays `relays[0]` and `relays[1]`. The same kind 10002 is also published to every relay in `indexer`, so that a restoring client can find it with nothing but the public key. Its kind 10063 lists the operator Blossom server and `mirrors[0]`.

Every kind 30078 and every kind 5 deletion goes to all write relays in the user's kind 10002. Users who already have a kind 10002 or 10063 keep theirs; the app adds the operator relay and `relays[0]` to the 10002, and the operator Blossom server and `mirrors[0]` to the 10063, only with the user's agreement: a "Keep backup copies" switch, on by default, on the nostr sign-in screen and on "Use my nostr app instead" (flow decision 76). With the switch on, an entry is added only when its URL isn't already listed, and every other entry keeps its place and its read or write marker. With the switch off, the app writes only to the relays already in the user's list and leaves both lists unchanged; blobs still go to the operator server and a mirror (section 4.2), and the inbox still uses the operator relay (section 4.4). A user's list counts as absent only once every indexer relay and at least two of `relays` have sent EOSE without one, and every edit starts from the newest copy seen on any relay, so a failed read never replaces the list the user's other nostr apps share. A user with no kind 10002, or no kind 10063, gets the default one either way.

`defaults.json` lists the operator's endpoints and the defaults, each list in order of preference:

```
{ "v": 1,
  "operator": { "relay": "wss://relay.<domain>", "blossom": "https://blossom.<domain>", "api": "https://api.<domain>" },
  "relays":  ["wss://…", "wss://…"],
  "indexer": ["wss://purplepag.es"],
  "mirrors": ["https://…"] }
```

`relays` holds at least two entries, `indexer` and `mirrors` at least one each. Clients fetch it with `GET /defaults.json` (section 6) at each start and at least once a day, keep the last copy that parsed, and otherwise use the copy baked into the release, so the lists can change without an app release. The defaults are chosen in week 1 by testing candidates (starting with `relay.damus.io`, `nos.lol`, `relay.primal.net`) against four checks: accepts kind 30078 from unknown authors, keeps addressable events indefinitely, accepts events of at least 16 KB, and has a published operator.

Retiring an entry (flow decision 93). The operator removes a default relay or mirror from `defaults.json` within a day of finding that it refuses saves or fails one of the four checks. The entries after it move up, and nothing else reorders the lists, so `relays[0]` changes only when its entry is retired. A retired entry no longer counts towards a save being backed up (section 1). Where a user's 10002 or 10063 holds a retired entry that Kefli added (every default entry of a generated identity; for a nostr user, one that this phone recorded adding), the app replaces it with the first entry of the same list that the user's list lacks, republishes the list, and copies the library to the replacement: every item is published to a new relay, and for a new mirror every blob is mirrored to it and its item republished naming it.

A relay of the person's own (flow decision 113). In Advanced, the person can add a relay by its `wss://` address. Before adding it, the app connects to it and publishes the newest kind 10002 it holds, already signed, so that nothing asks a signer; a relay that doesn't connect, or answers OK false, isn't added (an identity with no list yet is checked for a connection only). An added relay joins the 10002 for reading and writing, after any entries already there; a URL already listed as a write relay isn't added again. The 10002 and 10063 are republished as above, and the library is copied to the new relay as already signed: the newest kind 30078 of each `d` and every kind 5 that the other write relays hold, read in full and published unchanged, so that no item is re-signed from one device's state, which may be behind another's. Changes still waiting to be sent include the new relay. While any relay is read from the start, clients read deletions from every relay in full, so a relay holding an item's old event can't bring back an item deleted long before. From then on it is a write relay like any other: it counts towards a save being backed up (section 1) and gets the deletions in section 4.7. The person can remove a relay they added: the 10002 is republished without it, to it as well, and nothing is deleted from it; an entry the addition replaced (an indexer, or a nostr user's read-only relay) returns as it was. Lists and kind 5s are dated after the newest copy they replace (a list after the identity's newest 10002 and 10063, a kind 5 after the newest version of each item it names), whatever the device's clock says, and a client never replaces a list it holds with an older one. Kefli's relay and the default relays can't be removed there, since the claim in section 1 rests on them, and for a nostr user only a relay added on this phone can, since the rest of their list belongs to their other nostr apps as much as to Kefli. A client that reads a newer 10002 drops any relay it holds as the person's own that the list no longer names, unless it added that relay after the list was made. From a newer list a client adds only what the list it held didn't name, so a relay this client removed, its list not yet republished, stays removed. A newer 10063 is read the same way: the servers it names that the 10063 the client held didn't name join those the client holds, so a server this client removed stays removed, a server of the person's own that it no longer names is dropped, and the operator server and the mirrors stay; a text is fetched from the servers in the newest 10063 held as well as from `text.servers` (section 8). Just before publishing either list, a client reads the newest copies and takes them in this way, so a list another app published since the last read isn't overwritten.

### 3.2 The operator relay

strfry. Writes are accepted when the event's author (`pubkey`) is on the registration allowlist; the signature proves authorship, so no NIP-42 AUTH is required to write. Two exceptions take events from authors who aren't registered. Kind 1059 gift wraps, whose author is a throwaway key, are accepted from anyone when their `p` tag names a registered pubkey or an authorised device pubkey (section 6), since pair-acks are addressed to the device. A kind 5 is accepted from any author when every event it names in an `e` tag is a kind 1059 by that author which the relay holds; this is how the extension's Undo deletes its own wrap (section 4.4). All other kinds from unregistered authors are rejected. Reads of kind 30078 and other kinds are open, because the content is encrypted and the same events already sit on public relays.

Deletion follows NIP-09 and NIP-59: a kind 5 removes the events it names whose author is the kind 5's author, and also any kind 1059 it names whose `p` tag names the kind 5's author, so the recipient can delete a wrap it has consumed. Once `DELETE /account` has run for a user, the relay drops every kind 1059 whose `p` tag names that user or one of their devices, and accepts no more, since neither key is registered or authorised any longer.

Reads of kind 1059 require NIP-42 AUTH and are served only to the pubkey in the wrap's `p` tag, as NIP-17 recommends. AUTH is per connection: the relay issues a challenge on each connection and verifies that the AUTH event carries that challenge and a `created_at` within ten minutes. Clients keep one long-lived connection per relay while foregrounded and AUTH once per connection. The phone signs AUTH only when a relay refuses a request with `auth-required:`, never on the challenge alone, so a challenge asks nothing of the user's signer, and an AUTH that fails or goes unanswered closes the connection, the next request opening a new one. Remote-signer users are not prompted each time because `sign_event:22242` is in the standing permissions in section 2. The extension, whose device key asks no one, AUTHs as that key before publishing a wrap (section 4.4).

Limits: `maxEventSize` 16,384 bytes for kinds 30078 and 1059, 64 KB otherwise; per-pubkey write rate 60 events per minute; a retention rule drops events from de-registered authors after 30 days, and the operator keeps a removed key on its list of removed keys for 60 days. Events from authors who aren't registered (gift wraps and Undo's kind 5) are limited to 240 an hour from each address, an IPv6 address counted by its /64, and a gift wrap also to 120 an hour to one recipient from one address and 1,200 an hour to one recipient from everyone together. A wrap sent on a connection AUTHed (NIP-42) as its recipient, as a device the recipient authorised, or as the user who authorised the recipient device counts only against that key's 60 a minute, so a flood from other senders can't hold up a browser's saves.

### 3.3 Event size ceiling

No client ever publishes an event larger than 16 KB. strfry's default `maxEventSize` is 65,536 bytes and many public relays use it or less, and gift-wrapping multiplies a payload's size by roughly 1.8 through two layers of NIP-44 and base64. Article text and HTML therefore never travel inside events; they go to Blossom (section 5), and events carry only a hash and a key.

## 4. Event kinds

### 4.1 Save item: kind 30078 (NIP-78 app data)

One addressable event per saved URL per user. Tags, exactly:

```
["d", "kefli/item/<HMAC-SHA256 hex, under the library key, of the save's hash>"]
["t", "kefli"]
```

The save's hash is the hex SHA-256 of its normalised URL (section 4.3). It draws the save's cover and rides inside the encrypted content as `hash`; the `d` is keyed (section 4.3), so it can't be worked out from the URL. A save published before v1.10 has the unkeyed `d` `kefli/item/<hash>` and no `hash` field, and a reader takes its hash from its `d`.

The `t` tag lets clients fetch all of a user's saves with `{"kinds":[30078], "authors":[pk], "#t":["kefli"]}` without pulling other apps' NIP-78 data. A save is an event whose `d` is `kefli/item/` followed by 64 lowercase hex characters; other `kefli/` addresses that the same filter returns, such as the connected-browsers record (section 4.9), are not saves. The `content` is NIP-44 v2 ciphertext, self-encrypted (conversation key from the user's own key pair), of:

```
{
  "v": 1,
  "url": "https://example.com/article",
  "canonical": "https://example.com/article",
  "title": "…",
  "site": "example.com",
  "byline": "…",
  "saved_at": 1757000000,
  "state": "unread" | "archived",
  "progress": 0.0,
  "words": 2450,
  "lang": "en",
  "text": { "sha256": "<hex of ciphertext blob>", "key": "<base64 32 bytes>", "nonce": "<base64 12 bytes>",
            "servers": ["https://blossom.<domain>", "https://<default mirror>"] } | null,
  "text_hash": "<sha256 hex of normalised plaintext Markdown>" | null,
  "hero": "https://example.com/img.jpg",
  "source_kind": "web" | "nostr-article" | "nostr-note",
  "source_ref": "<naddr or nevent when source_kind is nostr>",
  "audio_pref": null | { "voice": "af_heart", "model": "kokoro-82m-v1.0" },
  "hash": "<the save's hash, 64 lowercase hex; from v1.10>"
}
```

`text` and `text_hash` are null for a save whose page could not be parsed, the guard's refusals included (section 4.2), and for one whose text the operator hasn't taken, which stays on the phone that made it (section 4.2). A client that receives a save with `text` null, and doesn't hold its text, fetches and parses its page itself; when that fails too, the reader opens the original page. A client that does hold the text, on the phone or waiting to upload, keeps it when a newer copy arrives with `text` null, and publishes the save again naming it once its upload and mirror have succeeded, at once if they already have; a client that takes a newer copy naming another text cancels its own waiting upload of that save's text (v1.12). So two phones on a library that is full don't take turns publishing the save without its text, and no upload is left that no save names. `saved_at` is the save's own time in Unix seconds: the share time for a phone share, the request's `captured_at` for a browser save (or the time it is processed, if `captured_at` is later), and the import time for an imported link. `progress` is the reading position as a fraction: 0 when `words` is null or 0, otherwise min(1, w ÷ `words`), where w is the index of the word reached in the spoken projection (section 4.2); a reader takes w = round(`progress` × `words`), counting a missing or non-numeric `progress` as 0. A client that derives an article again under a later spoken projection whose count differs stores the new `words`, keeps w inside it, and publishes both with the next reading position (section 11.7). v1 clients write `source_kind` as `web` only; `nostr-article`, `nostr-note` and `source_ref` are reserved (flow decision 82). `audio_pref` is reserved for the deferred server voices and is always null in v1.

State changes republish the same `d` with a newer `created_at`. A repeat save, meaning a share or browser save whose `d` already exists, un-archives an archived save and sets its `saved_at` to the new save's time, and leaves an unread one unchanged (flow decision 89, G2). Deleting a save publishes a NIP-09 kind 5 with an `a` tag for the address and a `["k","30078"]` tag to every write relay, one kind 5 naming up to 50 addresses, and deletes the blob from every server listed in `text.servers`. Deleting a save whose text still waits to upload (section 4.2) cancels the upload, and the blob is deleted from any server that an upload already under way reached. Clients read deletions with `{"kinds":[5],"authors":[pk],"#k":["30078"]}` and drop a save whose address a kind 5 names at or after the save's `created_at`. Target size of the event: under 4 KB.

### 4.2 Article text blob

The body is Markdown produced by the canonical pipeline: `@mozilla/readability` 0.6.0 output converted by `turndown` 7.2.4 with the fixed rules in `shared/turndown-rules.json`. Both libraries are vendored under `shared/`; bumping either regenerates the fixture hashes and bumps this contract's version.

- **Readability** runs with its defaults, `new Readability(document)` with no options, on a document whose base URL is the page's address. `isProbablyReaderable(document)`, also with its defaults, is read from the same document first, and `canonical` and `hero` before that (section 4.3), since `parse()` changes the document. The extension's `charThreshold: 250` is dropped.
- **Turndown** takes its options and any added rules from `shared/turndown-rules.json`. Its first version holds the options `parser-runner.js` uses, `{"headingStyle":"atx","codeBlockStyle":"fenced","bulletListMarker":"-","emDelimiter":"_"}`, and no added rules. Its sha256 sits in `shared/vendor/VERSIONS.md` beside the libraries', and changing it, like bumping a library, regenerates the fixtures and bumps this contract.
- **The guard** (flow decisions 77 and 78). A parse whose `isProbablyReaderable` is false and whose spoken projection (below) has fewer than 120 words counts as failed, as does one where Readability returns nothing; the save then has `text` and `text_hash` null.
- **Encryption.** The plaintext is the normalised Markdown (below) as UTF-8. It is encrypted with AES-256-GCM under the item's 32-byte key and 12-byte nonce with no additional data, and the blob is the ciphertext followed by the 16-byte tag; `text.sha256` is the SHA-256 of the blob.

The blob is uploaded to the operator Blossom server with a kind 24242 Blossom auth event, then mirrored with BUD-04 to the first entry of `mirrors` in `defaults.json` that accepts it, and `text.servers` lists the operator server and that mirror. A mirror that refuses, with any HTTP 4xx answer other than 401 and 429, is passed over for the next entry, and the item is republished naming the new one, so `text.servers` never lists the operator alone; once every entry has refused, the client waits a day and starts the list again. Until a mirror holds the blob and the save's newest event names that mirror in `text.servers`, the save counts as not backed up (section 1, flow decision 93); when a mirror takes the blob after the save went out naming another (one that failed with a server error, say), the item is republished naming the mirror that holds it. The user's kind 10063 server list (BUD-03) is published as section 3.1 says. Blobs are ciphertext, so public mirrors hold nothing readable. Images are never uploaded; the Markdown keeps original image URLs and clients cache images locally.

An upload the operator refuses never holds its save back (v1.12, flow decision 117). When the text is refused for room (413 `quota` or `daily`, section 5), for good (413 `too_large`, a blob over 8 MB), with any other 4xx answer but 401 and 429, or because the operator's disk is full (507), the save is published at once with `text` and `text_hash` null, to every write relay like any other save, so its link, title, state and reading position are backed up and synced while its text stays on the phone. A text refused for good is never sent again; every other is tried again as section 5 says. The mirror copies from the operator, so it waits for the operator's copy. Once the operator and a mirror hold the text, the save is published again naming both in `text.servers`; until then it counts as not backed up (section 1). A save whose only change is its text, as when it came from another phone without one and this phone parsed its page (section 4.1), is published only then, since a refusal leaves it nothing new to send.

`text_hash` is the SHA-256 of a normalised form of the Markdown: Unicode NFC, CRLF to LF, trailing spaces and tabs removed from every line (lines split at LF only), runs of three or more newlines collapsed to two, and exactly one trailing newline. It is reserved as the key of the deferred audio cache (section 6.1); v1 computes it and the fixtures check it, so the hashes are already stable when server voices arrive.

Where the Readability runs: the extension on the live DOM; Android in a hidden WebView; iOS in Safari via the share extension's preprocessing script for Safari shares, and in a WKWebView on next foreground for URL-only shares (the extension's Swift port may parse first for the offline copy, and the item is re-parsed with Readability.js so its hash converges). A share-sheet save (HTML fetched by the phone) and an extension save (rendered DOM) of the same URL may legitimately produce different `text_hash` values; once the audio cache exists, the two would miss each other there, which is expected.

**PDFs** (flow decision 103). A response whose `Content-Type` is `application/pdf` (or `application/x-pdf`), or whose body starts `%PDF-`, is a PDF, with a 20 MB cap in place of a page's. pdf.js 4.10.38 (`pdfjs-dist`'s legacy build, vendored under `shared/vendor/pdfjs-4.10.38/` with its sha256s in `VERSIONS.md`) reads its text through `shared/vendor/pdf-runner.mjs`: each text item as a run of text, x, baseline y from the page's top, size, width and angle, in the page's viewport at scale 1 with its rotation applied, rounded to hundredths; a file over 400 pages, or one locked with a password, gives no runs. `pdfMarkdown` in `packages/protocol` lays the runs out as Markdown, which is then normalised as below; the page fixtures' rule that the fixtures win holds for the PDF fixtures (`shared/fixtures/pdfs`) too. The title is the file's own, unless it is an address, a file name or a placeholder, and otherwise the largest heading on the first page (a heading set larger than the text, not a numbered section); that heading is left out of the Markdown when it is the title or says what the file's title says, compared without case, spacing or punctuation, since the reader shows the title above the text; `byline` is the file's author; `site`, `lang`, `hero` and `canonical` are null. The guard does not apply: a PDF whose spoken projection has fewer than 20 words has no text (a scan), and like a locked one is saved with `text` and `text_hash` null. The extension never parses a PDF: a save from a browser's PDF viewer is URL-only (section 4.4), so the phone fetches it.

The spoken projection is what a voice reads and what `words` counts. It is computed from the normalised Markdown, parsed as CommonMark: the text of each node in document order, with Markdown syntax removed, link text kept and link targets dropped, images dropped with their alt text, code blocks read like other text, raw HTML read as written (the pipeline writes no tags, so any in the Markdown was text in the article), character escapes and entity references resolved, each run of whitespace inside a block read as one space, a full stop added to a heading, and to each paragraph directly inside a list item, whose text doesn't end in `.`, `!` or `?` (optionally followed by a closing quote or bracket), and blocks separated by a blank line. Citation and footnote markers are not spoken (flow decision 102), since the voice reading "bracket one" breaks the sentence it sits in: a link whose target's fragment starts with `cite_note-`, whatever its text; a link whose whole text is one to three digits, optionally in square brackets, and whose fragment starts with `fn`, `footnote` or `note`; a link whose text is only carets, arrows and spaces and whose fragment starts with `fnref`, `footnote-anchor` or `cite_ref`; and a link into Wikipedia's project namespace (`/wiki/Wikipedia:` or its localised name), alone or in emphasis, when the text before it ends in `[` and the text after it starts with `]`, which go with it (a maintenance tag such as "[citation needed]"). A list item whose first paragraph opens, after any `^` or `↑`, with a link whose fragment starts with `cite_ref-` is not spoken, nor anything in it (an entry in a reference list). The rule reads link targets, because text in square brackets is often content, such as IPA. The Markdown keeps every marker and the reader shows them. Each spoken character maps to its offset in the normalised Markdown, which word highlighting uses (section 7). `words` is the number of whitespace-separated tokens in the projection. The reference implementation is in `packages/protocol`; the page fixtures carry each page's projection and `words`, and where this paragraph and the fixtures disagree, the fixtures win.

### 4.3 URL normalisation and the `d` tag

`normalise(url, canonical?)`: lowercase the scheme; convert the host to ASCII by UTS-46 with the WHATWG URL Standard's settings (non-transitional processing), which also lowercases it; drop the fragment; remove `utm_*`, `fbclid`, `gclid`, `mc_cid`, `mc_eid`, `ref`, `igshid`, and on twitter.com/x.com only `s` and `t`; sort the remaining query parameters; strip every trailing slash, a bare host keeping its one. Parsing and serialisation follow the WHATWG URL Standard on every engine (the `whatwg-url` package, whose host step is `tr46`), so default ports, dot segments, IPv4 forms and percent-encoding come out as a browser's `location.href` gives them; only `http` and `https` URLs are links. The further rules (query names matched case-sensitively and sorted in their decoded form, as `URLSearchParams` reads them, with each pair kept byte for byte and repeated names in their order; empty pairs dropped; `s` and `t` stripped on the X hosts' subdomains too; user info and a trailing dot on the host kept) are listed in the fixtures' `rulings`. When the host begins `m.` or `amp.`, or the path ends in `/amp` or `/amp/`, and `canonical` is given and is an `http` or `https` URL, the result is `normalise(canonical)`; otherwise these are left as they are. Reference implementation `shared/normalise.ts`, which parses with `whatwg-url` and `tr46` on every engine rather than the platform's `URL`; every port must pass `shared/normalise.fixtures.json`, which includes IDN and mixed-script hosts.

`canonical` is the first `<link rel="canonical">` in the page, resolved against the page's address and kept only when its scheme is `http` or `https`. It is read before Readability runs, and so is `hero`, from `og:image`, else `twitter:image`. The extension reads both from the live document with the same code.

A save's hash is the hex SHA-256 of `normalise(finalUrl, canonical)`, where `finalUrl` is the address after every redirect (for an extension save, the page's address without its fragment), for shares, browser saves and imports alike. A client keys a new save by `normalise(sharedUrl)` until its fetch resolves, and publishes it only once its parse has succeeded or definitely failed. If the fetch gives another hash, the client re-keys the save, which is always before its first publish, and the cover, drawn from the new hash, crossfades once; if the new hash is already a save, the repeat-save rule applies (section 4.1) and the provisional save goes. Once published, a save's hash, and so its cover, never changes (flow decision 80).

The library key (v1.10; finding F5 of the pre-release audit). A save's `d` is `kefli/item/` followed by the hex HMAC-SHA256 of its hash (the 64 characters as ASCII) under the library key: 32 random bytes per identity, so that nobody without it can check whether a library saved a page by hashing the page's URL. The key is kept in one addressable kind 30078 with the tags `["d","kefli/library-key"]` and `["t","kefli"]`, self-encrypted like a save, whose content is `{"v":1,"key":"<64 hex>"}`, published to every write relay. A client makes the key at the first publish of an identity it created; for any other identity it takes the newest copy of the record on the write relays, and makes a key only once every write relay has answered without one. The record reaches at least one relay before any save it addresses. A client holding a key not yet published, or an older record's, takes the newest record it finds and publishes each of its saves again at the new address. Whenever a save is published at an address other than the one it was last at (an unkeyed one from before v1.10, or one under another key), the client sends a kind 5 for the old address, dated past the save's last version there. Once a client knows the key, it publishes again at its keyed address every save still at another address, so a library from before v1.10 moves whole. A kind 5 removes a save only when it names the address the save is known at or its address under the current key, never one the save has left. A client never names in a kind 5 an address a save wasn't published at: deleting a save, a whole library (section 4.7) or a moved identity's saves (section 4.8) names each save's keyed address and the address it was last published at, so the plain hash of a save that was only ever keyed is never published. A save published before v1.10 can't be hidden after the fact: its old event, and the kind 5 retiring it, name its plain hash, which was public already. The extension never publishes a save, so it needs no key.

X posts (flow decision 78). A URL on `x.com`, `twitter.com` or `mobile.twitter.com` with the path `/<user>/status/<id>` is never saved as itself. The client asks X's public embed service (`GET https://publish.x.com/oembed?url=<post>`, 5 s timeout), resolves the links in its `html` in order (`t.co` links followed without a browser user agent, five hops at most), and saves the first whose host isn't `x.com`, `twitter.com`, `pic.x.com`, `pic.twitter.com` or `t.co` as an ordinary link. No such link, or one to an X Article (`x.com/i/article/…`), saves nothing. Offline, or while the embed service fails, the post's URL is saved and checked again later: an article re-keys the save as above, and no article leaves it as a failed parse whose original page is the post. Nothing from X's response is stored.

### 4.4 Browser extension: device key, inbox blob and sealed save

The extension generates its own device keypair at install. It never holds the user's private key.

Pairing: the extension shows a QR containing `{v:1, device_pubkey, relay: "wss://relay.<domain>", nonce, expires, label, proof: {created_at, sig}}` (five-minute expiry), with the same offer as a typed code under it (below). `relay` is always the operator relay. `label` names the browser, such as "Chrome on a Windows laptop", built from the browser's brand and platform, never a hostname or user name. `proof` is the device key's consent to this pairing (v1.11): the `created_at` and `sig` of a kind 27235 event signed by the device key when the offer is made, with empty content and the tags `["u","<operator.api>/devices"]`, `["method","POST"]` and `["nonce",<nonce>]`. It has no `payload` tag, so it can't pass as a request's own NIP-98 header, and anyone who knows `device_pubkey`, the nonce and `operator.api` can rebuild the event and verify it. The phone scans the QR or takes the typed code and checks it: `v` is 1, `expires` hasn't passed (allowing 60 seconds of clock skew), `device_pubkey` is a valid x-only public key, `label` is plain text under 64 characters, `relay` equals `operator.relay` in `defaults.json`, and `proof` verifies for `device_pubkey` and this nonce against `operator.api`, with its `created_at` no later than `expires`. An offer without a proof that holds, as from an extension older than v1.11, is not taken. It then shows "Connect this browser?" with the label in a card under it ("Chrome on a Windows laptop", then "Pages you save there will come to this library."), and on confirmation calls `POST /devices` (section 6) signed by the user's key and carrying the offer's proof, which authorises the device key to upload blobs against the user's quota and daily limit (section 5). The phone then sends a NIP-59 gift wrap to the device pubkey on that relay, sealed by the user's key, whose rumor is kind 30078 with `["d","kefli/pair-ack"]` and content `{v:1, user_pubkey, write_relays, blossom_servers, token, nonce}`, `token` being 32 random bytes in hex, and adds the browser to the connected-browsers record (section 4.9). The extension checks the nonce, stores the result, and shows "Connected". The phone lists the device under You → Connected browsers with Disconnect, which marks its entry revoked, republishes the record and calls `DELETE /devices/<pubkey>`.

Typed code, for when the phone can't scan (flow decisions 11 and 29): the extension also shows an eight-character code, written XXXX-XXXX, drawn at random from Crockford's base32 alphabet (0–9 and A–Z without I, L, O and U), so 40 bits. It is made with each QR and expires with it. From the code the extension derives 64 bytes with scrypt (password: the eight characters in upper case without the hyphen, as ASCII; salt: `kefli/pair-code/v1`; N = 16384, r = 8, p = 1). The first 32 bytes, in hex, are the `lookup`; the last 32 are an AES-256-GCM key, under which the extension encrypts the QR's JSON as UTF-8 with a random 12-byte IV and no additional data. It posts the lookup and `base64(IV ‖ ciphertext ‖ tag)` with `POST /pair-offers` (section 6). On the phone the user types the code; the phone reads it leniently (upper case, hyphens and spaces dropped, O read as 0, I and L read as 1), derives the same bytes, fetches `GET /pair-offers/<lookup>`, decrypts the offer, checks it exactly as a scanned QR and carries on from the confirmation. A code that isn't eight characters after the lenient read, finds no offer, or gives an offer that fails to decrypt, or fails the checks above other than expiry (a missing proof among them), gets the field error "That code didn’t match. Check it in your browser, or show a new one there." The operator holds only the lookup and the ciphertext, for at most five minutes, and recovering the nonce from them takes a search of 2^40 scrypt evaluations inside that time. As with the QR, someone who reads the code off the screen during those five minutes could connect the browser to their own library instead; the options page would then say Connected while the user's phone doesn't list the browser.

Moving a browser to another identity (section 4.8): while paired, the extension keeps a subscription for kind 1059 with `#p` = its device pubkey on the operator relay, with NIP-42 AUTH by the device key, whenever it is connected there, and checks it on start. It accepts a pair-ack whose content carries `"moved_from"` (in place of `nonce`) equal to its current `user_pubkey`, and whose seal is signed by that same key. It then replaces its pairing record with the new `user_pubkey`, relays, servers and token, and wraps any saves still queued again for the new user before sending them. It ignores any other pair-ack once paired.

Save: the extension runs Readability on the page with the options and guard of section 4.2, reading `canonical` and `hero` first (section 4.3). Unless the guard trips or the content HTML is over 2 MB (2,097,152 bytes as UTF-8), it encrypts that HTML as UTF-8 with a fresh AES-256-GCM key and nonce in the blob format of section 4.2 and uploads the blob to the operator Blossom server authenticated by the device key (an inbox blob, counted against the library's day of uploads, and against its storage until the phone deletes it or it expires after 14 days; section 5). It then sends a gift wrap to the user's pubkey whose rumor and seal are signed by the device key and whose wrap is signed by a fresh random key. The rumor is kind 30078 with `["d","kefli/save-request/<uuid>"]` and content:

```
{ "v": 1, "url", "canonical", "title", "site", "byline", "lang", "hero", "captured_at", "token",
  "html": { "sha256", "key", "nonce", "server" } | null }
```

`url` is the page's address without its fragment, `lang` is Readability's, and `captured_at` is in Unix seconds. `html` is null when capture failed, the guard tripped, the HTML was over 2 MB, or the operator refused its upload with any 4xx answer but 401 and 429, `quota` and `daily` included, since the extension doesn't wait for room (v1.12, section 5); the phone then fetches and parses the URL itself, as it also does when the operator answers 404 for the inbox blob (below). The wrap is published to the operator relay only, on a connection the extension has AUTHed (NIP-42) as its device key when the relay asks, so it counts against that key's own allowance (section 3.2); a refused or missing AUTH stops nothing. The wrap is under 8 KB: a request that would make it larger is sent with `hero`, then `byline`, `site`, `lang`, `title`, `canonical` and last `html` set to null, one at a time, until it fits, and one that doesn't fit even then, its address too long, isn't sent, and the extension says so.

The phone subscribes to kind 1059 with `#p` = own pubkey on the operator relay (AUTH required), with `since` at least 172,800 + 300 seconds before its last drain, because NIP-59 lets a wrap's `created_at` lie up to two days in the past, and skips wraps it has already seen. It unwraps each, requires the rumor's pubkey to equal the seal's, and leaves alone anything that isn't a kind 30078 rumor with `d` = `kefli/save-request/…`, since other apps' messages share the `p` tag. It ignores a request whose `v` it doesn't understand (section 10), whose `token` isn't a connected entry of the connected-browsers record (section 4.9), or whose seal isn't signed by that entry's `device_pubkey`. For an accepted request whose URL is an X post, the phone discards the HTML and follows the X rule (section 4.3). Otherwise it downloads the HTML from `html.server`, which must be the operator Blossom server, checks its sha256, decrypts it, runs the canonical Markdown conversion, and creates the kind 30078 item exactly as if the share sheet had been used, with its own text key and blob, and `saved_at` = `captured_at`, or the current time if `captured_at` is later. When the operator answers 404 for the HTML, the inbox blob has expired or been deleted, and the phone fetches and parses the page at once, as for `html` null. If the save's `d` already exists, the repeat-save rule applies (section 4.1), with the new save's time worked out the same way. Only for a wrap that created, un-archived or matched a save does the phone then publish a kind 5 for the wrap (`["e", <wrap id>]`, `["k","1059"]`) to the operator relay, and delete the request's inbox blob, if it has one, from the operator Blossom server, which the server allows the library the blob counts against (section 5). The save no longer needs it by then, so an inbox blob takes room in the library's storage only until the phone has taken it. Every other wrap is left as it is, so a phone that hasn't yet received the connected-browsers record can't remove a save another phone still needs.

Undo in the extension publishes a kind 5 for the wrap signed by the wrap key, valid because that key is the wrap's author, and accepted by the operator relay (section 3.2). If the phone has already consumed the wrap, undo shows "Remove it from your phone's Saves" instead.

The phone acts on wraps within seconds while open, and the ten-second target for a browser save is measured with the app open. Closed or suspended, Android drains the subscription on foreground and on its periodic background task, which runs no more often than every 15 minutes, and later under Doze; iOS drains on launch and on background refresh when granted. A browser save made while the phone is closed therefore arrives at the next of these (flow decision 84).

Existing nostr users with a NIP-07 browser extension still pair this way in v1. Signing saves directly from the browser would duplicate the hash-critical Markdown step outside the phone.

### 4.5 Public recommendation (v2, reserved now): kind 39701

A NIP-B0 web bookmark with `d` = URL without scheme, `title`, `published_at` and `t` tags, emitted only on an explicit "Recommend" gesture and never automatically. Public recommendations are the only events any other nostr client will display.

### 4.6 Existing bookmarks import

Web links only in v1 (flow decision 82). On the first sign-in of an existing nostr user, the phone reads their kind 39701 web bookmarks (NIP-B0; each `d` is the URL without its scheme, imported as `https://<d>`) and the `r` tags of their kind 10003 list and of every kind 30003 set. Entries kept privately in a list's encrypted `content`, `e` tags and `a` tags are not imported. When at least one link is not already a save (by `d`, section 4.3), a sheet asks once, in the prototype's words (`nostr-import`): "Bring in your bookmarks?" and "We found N bookmarks in your nostr account. In your library they’ll be private, like everything else.", with Not now and Bring them in. N is the number of links not already saved, worded for one or several (flow decision 91 (f)). Either answer starts the restore. Bring them in imports every such link, with no cap, as a web save with `saved_at` set to the import time, fetched and parsed on the phone two at a time. Imported saves are private like any other, and nothing is published as a bookmark. Their texts count against the library's limits on the operator's server like any other save's (v1.12, section 5), so a large import's texts are taken over several days, and past the library's storage they stay on the phone.

### 4.7 Delete my data

"Delete my data" under You first shows the explain screen (prototype `del`), which says what goes and what can only be asked for. It keeps the line "This removes your library from all your devices and from Kefli’s server." and counts the backup servers from the user's real lists: every write relay in their kind 10002 other than the operator's, a nostr user's own included, and every server other than the operator's named in any item's `text.servers`, each counted once (flow decision 89, G8; flow decision 91 (e)). Its other words are the prototype's. A nostr user then approves the signing in their nostr app; declining deletes nothing.

The deletion runs in three steps, in this order, because the operator relay rejects kind 5s from a deleted account (section 3.2). Each step's results are kept, so a deletion interrupted part way resumes. Before anything is signed, the phone reads the operator relay and every relay in the user's kind 10002 for `{"kinds":[30078],"authors":[pk],"#t":["kefli"]}`, so that a save it doesn't hold is named too; a save found only there is decrypted for its `text.sha256`, and its blob is deleted with the rest. Deletions the phone still owes, queued or given up on, join them, and each kind 5 is dated after the newest event it names. A relay that doesn't answer the read stops nothing.

1. **The operator.** Publish to the operator relay NIP-09 deletions for every wrap addressed to the user that the phone knows of, consumed or pending, and, when the operator relay is in the user's kind 10002, for everything step 2 deletes on relays; delete every blob on the operator Blossom server; then call `DELETE /account`. These run in every case, with at most a minute of retries. If the operator is still unreachable after that minute, or `DELETE /account` fails, nothing else runs and the key stays on the phone, so the person can try again.
2. **Every other server.** Publish deletions to every other write relay in the user's kind 10002 (Kefli's backup relays and, for a nostr user, their own) for every kind 30078 with `#t` = `kefli`, whatever its `v`, the connected-browsers record included; delete every blob from every other server named in any item's `text.servers`. A relay counts as confirmed once it has answered OK true to every kind 5 sent to it, and a Blossom server once it has answered 2xx or 404 to every delete; each server gets at most a minute of retries and is otherwise reported as not confirmed. A generated identity's kind 10002 and 10063 are deleted too, by a kind 5 with the `a` tags `10002:<pubkey>:` and `10063:<pubkey>:` and the `k` tags 10002 and 10063, sent to the same relays. Then an empty kind 10002 and an empty kind 10063 (no tags, empty content), dated one second after that kind 5, go to the same relays and to the indexer relays, and take the old lists' place on any relay that refuses or ignores the kind 5. The indexer relays get only the empty lists, since they refuse kind 5. Only answers to the kind 5s count towards a relay's confirmation, and the indexer relays aren't reported. A nostr user's lists are never deleted, since their other nostr apps share them; they are republished without the operator's relay and Blossom server and without any default entry this phone recorded adding.
3. **The phone.** Wipe the key from local storage and from iCloud Keychain or Block Store, then the local library. For a nostr user, wiping the key means forgetting the link to their nostr app (the NIP-46 client key or the NIP-55 signer's package).

The deleting screen shows a step for each server and names each one that didn't confirm (flow decision 91 (e)). Public relays may not honour kind 5; the ciphertext they keep is unreadable without the user's key, which for a generated identity the app has just destroyed.

### 4.8 Moving saves to another identity

Two flows move a library from one key to another. "Use my nostr app instead" under You → Advanced moves it from the key the phone generated to the user's nostr app (flow decision 13). Saves shared before the app was first opened were made under a fresh key, unless Block Store held a mnemonic (section 2), and move into the library the user then brings back (flow decision 6); that move runs alongside the restore and shows on its progress card. In both, the source S is a local key the phone holds and the target T is any `Signer` (section 2). Text blobs need no re-encryption, since each has its own key; what changes is who signs each event and who owns each blob.

The phone stays online throughout and Android Back is disabled while it runs:

1. **Prepare T.** Run the capability probe (section 2), call `POST /register` as T, and set up T's relay and server lists: an existing kind 10002 or 10063 is handled as at any nostr sign-in, under the Keep backup copies switch (section 3.1), and a T without one gets the default set.
2. **Collect both libraries**: for S and for T, the newest event per `d` from all their read relays, with their deletions applied (section 8), merged with the phone's local copies. If either library holds an item whose `v` this client doesn't understand (section 10), the move stops here and asks for an app update; S and every save stay as they were, and T's registration and lists stay (flow decision 91 (i)).
3. **Copy each item to T.** Decrypt it with S. If T already has an item with the same hash (section 4.1), keep T's item and only un-archive it when S's copy is unread, changing its `state` alone (its `saved_at` stays). Otherwise encrypt the same JSON to T (NIP-44 v2, self-encrypted, with `v` and every field unchanged except `text.servers`, which lists T's servers) and publish it, signed by T at its address under T's library key (section 4.3) with the same `t` tag, to T's write relays. An item S never published, which exists only on this phone, is published under T alone. For an item with text, T takes ownership of the blob: it uploads the same ciphertext (fetched from `text.servers`, or the phone's own for a text that stays on the phone, section 4.2) to the operator server with a kind 24242 auth signed by T, then mirrors it as in section 4.2. The blob's `sha256`, key and nonce don't change. A blob the operator already stores costs T nothing against its day of uploads, though it counts against T's storage (section 5). An upload the operator refuses, for any reason section 4.2 lists, counts as settled for the move, which carries on. T's copy then names in `text.servers` only the mirror that holds the blob under S, if one does, so a text backed up under S stays backed up under T, and goes out with `text` null when none does. The phone keeps the text, which waits under T as any refused text does (section 4.2), and once the operator and a mirror hold it under T the item is published again naming both.
4. **Move connected browsers.** For each connected entry in S's connected-browsers record (section 4.9) that this move hasn't already paired, call `POST /devices` signed by T with the same device pubkey and a release signed at that moment by S (section 6), then send the device a pair-ack as in section 4.4, on the operator relay, sealed by S, carrying T as `user_pubkey`, T's relays and servers, a new token, and `"moved_from": "<S pubkey>"`. T's record then lists each device with its new token and is published to T's write relays. A move can't use the device's original proof, which anyone who saw its QR holds; S's release is the consent of the library that holds the browser, and S is always a key on the phone. A device the operator refuses to move gets no pair-ack, stays with S and goes when S's account is deleted, and the move carries on.
5. **Confirm, then retire S.** Read T's items back from min(2, n) of T's write relays, n being how many T has, and check that every moved save is present and decrypts. Only then: carry to T's copy any change made under S after the item was copied (its state, `saved_at`, reading position and `words`), republishing it under T, and delete under T any item S no longer holds. This carry runs once, recorded with the move's progress before any of S's deletions goes out: after that, S's own deletions read back by a sync, or S's rows wiped before the move recorded its end, remove items from S without anyone deleting them, so a resumed step 5 deletes under T only an item S holds for a delete's Undo or still owes a deletion for; drain S's inbox one last time and move anything found there; publish NIP-09 deletions for S's items (at every address each was at, together with every deletion S still owed, each kind 5 dated after the newest event it names), S's connected-browsers record and S's library key record to S's write relays, call `DELETE /account` signed by S (which leaves the blobs T now owns, section 5), and wipe S from the phone and from iCloud Keychain or Block Store; the Block Store entry takes T's mnemonic, or is removed when T is a nostr app (section 2). S's recovery code stops working from this point, as the switch screen says.

The phone records its progress locally. If it stops part way, it resumes at the next start and skips items already under T, and S stays intact until step 5, so a save is never deleted before its copy exists under T. Collecting a library, in steps 1 and 2, waits while any event it found waits for a signer that hasn't answered, so the move never goes on without them.

### 4.9 Connected browsers record: kind 30078, `d` = `kefli/devices`

The phone keeps the user's connected browsers in one addressable kind 30078 with the tags `["d","kefli/devices"]` and `["t","kefli"]`, self-encrypted like a save (section 4.1) and published to every write relay, so that a reinstall, a restore, a second phone and a move (section 4.8) all know them. Its content:

```
{ "v": 1,
  "devices": [ { "device_pubkey", "label", "token", "connected_at", "revoked_at": <unix seconds> | null } ] }
```

`connected_at` and `revoked_at` are Unix seconds. The phone republishes the record after every Connect and every Disconnect, starting from the newest copy seen on any relay. Entries are keyed by `token`, which is new for every connection. On receiving a copy, and before publishing, a phone merges the two by `token`: an entry in either copy is kept, and a `revoked_at` set in either copy stays set, taking the earlier value. A revoked entry stays in the record, so a phone that was offline can't bring its token back; only when the event would pass the 16 KB ceiling (section 3.3) are revoked entries removed, the earliest `revoked_at` first. A browser counts as connected while it has an entry whose `revoked_at` is null. The record is deleted with the saves (section 4.7) and moved with them (section 4.8).

## 5. Blossom servers

The operator Blossom server accepts uploads authenticated by a registered user pubkey or an authorised device pubkey (section 6), counts both against the user's limits (below), lists nothing publicly, and supports BUD-04 mirroring out. A blob uploaded by more than one pubkey, as after a move (section 4.8), is kept until its last owner deletes it or is deleted. A delete signed by a user removes the blob from their library, every upload of it counted against them included, so the phone can delete an inbox blob its browser uploaded (section 4.4); a device key's delete removes only its own upload. Inbox blobs uploaded by device keys expire after 14 days, unless the phone deletes them first.

Fair use (v1.12, flow decision 117) holds each library, a user's uploads and their browsers' together, to two limits. Its quota, by default 50 MB (52,428,800 bytes), about 2,000 saves of typical size, caps the total size of the blobs it holds, each counted once whichever of its keys uploaded it, so a repeat upload of a blob the library holds costs nothing. Its uploads may add at most 20 MB (20,971,520 bytes) to the server's disk in any 24 hours; an upload of a blob the server already stores, for this library or any other, adds nothing, so a move's re-uploads (section 4.8) cost nothing against the day. The day is counted from a log of the last 24 hours' uploads, so deleting a blob gives none of the day back. A library's quota is its own: libraries made at the old default of 200 MB are lowered to the new one once, a library whose quota was set to another figure keeps it, and a paid tier may later raise it. A library above its quota, as one lowered from 200 MB may be, keeps every blob it holds, and its uploads are refused until deleting brings it back within its quota.

Every refusal carries its reason in `X-Reason` (BUD-01) and in the body `{"v":1,"error":<reason>}`. An upload that would take a library past its quota gets 413 `quota`, and one past its day's uploads 413 `daily` (`quota` when it would pass both); their bodies add the library's figures in bytes, `{"v":1,"error","quota","used","daily","today"}`, as `GET /account` gives them (section 6). A phone tries both again a day later. When the operator confirms one of its blob deletions, which makes room, it also tries at once the texts waiting on `quota` that fit in the room it reckons is left, from those figures and what it has uploaded and deleted since, oldest first, stopping at the first refusal. The extension sends its request without the HTML instead (section 4.4). A blob over 8 MB (8,388,608 bytes) gets 413 `too_large`, which clients never try again; any other 4xx answer to a phone's upload but 401 and 429 is tried again a day later, so a fault on the operator's side can't leave a text unsent for good. None of these refusals holds a save back (sections 4.2 and 4.4). An upload that would leave the operator's disk below its free-space floor is refused with 507; the phone sends the save without its text, as for a refusal for room (section 4.2), and retries the upload as it does any 5xx, and the extension retries its upload as any 5xx.

The default public mirrors (`mirrors` in `defaults.json`, section 3.1) are chosen in week 1 against the same four checks as the default relays plus an upload-size limit of at least 5 MB, and are retired as section 3.1 says. If no free public mirror proves reliable, the fallback is a second small Blossom instance on a different provider and domain, run by the operator; that is weaker than an independent mirror and the privacy note must say so.

## 6. Operator HTTP API

Base `operator.api` in `defaults.json` (`https://api.<domain>`). Every request except `GET /defaults.json` and `GET /.well-known/nostr.json` carries NIP-98 HTTP auth: a kind 27235 event in `Authorization: Nostr <base64>`, with a `u` tag equal to the exact request URL, a `method` tag, a `created_at` within 60 seconds of the server's clock, and, on every POST, PUT and DELETE, a `payload` tag holding the hex SHA-256 of the body, or of the empty string when there is no body. Every request body is a JSON object with `v`. Rate limits are per pubkey unless stated; where a limit is per address, an IPv6 address counts by its /64, and for `/register` by its /56. A limited request gets 429 with `Retry-After`.

`POST /register` — body `{ "v": 1 }`. Adds the pubkey to the relay allowlist and creates its library's Blossom quota (section 5), and answers `{ "v": 1, "quota", "used" }` in bytes, `quota` being the library's own. Idempotent. New accounts are limited to 5 a day from each address (an IPv6 address counted by its /56), 20 a day from each IPv6 /48, and 200 an hour from everyone together. The hourly limit trades availability for a bound on what accounts cost: past it, every first launch waits, its saves kept on the phone and sent once a place frees.

`GET /account` — signed by a registered user (v1.12). Returns `{ "v": 1, "quota", "used", "daily", "today" }` in bytes: the library's quota and what its blobs take of it, the most its uploads may add in any 24 hours, and what they added to the server's disk in the last 24 hours (section 5). Any other key gets 403 `not_registered`, as on every route for registered users. The phone asks when Advanced opens, takes the same figures from any 413 `quota` or `daily` it gets, and keeps the last it has.

`POST /devices` — body `{ "v": 1, "device_pubkey", "proof": { "nonce", "created_at", "sig" } }`, or, in a move (section 4.8), `{ "v": 1, "device_pubkey", "release": { "pubkey", "created_at", "sig" } }`, signed by the user. Authorises a device key to upload blobs against the user's quota and daily limit (section 5), and only with the device's consent (v1.11). `proof` is the offer's (section 4.4), with its nonce. It is accepted once, made no more than 360 seconds before the request (the offer's five minutes and a minute of skew) and no more than 60 seconds after it, and it authorises the device for the caller even when another user holds it, since a fresh proof means the browser showed a new code. `release` is the `created_at` and `sig` of a kind 27235 event signed by `pubkey`, with empty content and the tags `["u","<operator.api>/devices"]`, `["method","POST"]`, `["device",<device_pubkey>]` and `["to",<caller>]`. It is accepted once, within 60 seconds of the server's clock, and only when `pubkey` is the user the device is authorised for. A caller already holding the device gets 200 and nothing changes, for any proof or release whose signature holds, however old, so a retry after a lost answer works; a proof or release still within its time is used up all the same, so someone else who saw the code can't take the device with it. Errors: 400 `proof: missing`, which a client older than v1.11 gets; 403 `proof: signature`, `proof: stale`, `proof: replayed`, `release: signature`, `release: stale`, `release: replayed` or `release: holder`. A `label` sent by a client before v1.10 is accepted and never stored: the browser's name lives only in the self-encrypted connected-browsers record (section 4.9). `DELETE /devices/<device_pubkey>` revokes it and deletes its unexpired inbox blobs that count against the caller.

`POST /pair-offers` — body `{ "v": 1, "lookup", "offer" }` (section 4.4), signed with NIP-98 by the extension's device key, which needn't be authorised yet. Holds the offer for five minutes. 409 when an unexpired offer already has that lookup; rate-limited per device key and per address to 30 an hour.

`GET /pair-offers/<lookup>` — signed by a registered user. Returns `{ "v": 1, "offer" }`, or 404 when no unexpired offer has that lookup.

`POST /phone-offers` — body `{ "v": 1, "lookup", "offer" }` (section 2), signed by a registered user. Holds the offer for five minutes. 409 when an unexpired offer already has that lookup; rate-limited per pubkey and per address to 30 an hour.

`GET /phone-offers/<lookup>` — signed with NIP-98 by any key, since the phone fetching it has no identity yet and signs with a throwaway one. Returns `{ "v": 1, "offer" }` and deletes the offer, or 404 when no unexpired offer has that lookup. Rate-limited per address to 30 an hour, 404s included. Once 10 lookups from one block of addresses (an IPv4 /24, an IPv6 /48), or 100 from anyone, have found nothing within five minutes, every lookup from that block, or from anyone, gets 429 until those five minutes are up, a right code included, since nothing tells a right guess from a wrong one before the lookup (section 2 says why the shared count stays).

`DELETE /account` — removes the user's and their devices' ownership of blobs on the operator server, deleting each blob that no other pubkey owns (section 5), and deletes their device authorisations and their allowlist entry; the operator relay then drops every kind 1059 addressed to the user or one of their devices (section 3.2). Once server audio exists (section 6.1) it also deletes their audio requests and any cached audio requested only by them. It cannot delete relay events; section 4.7 covers those. A key with no account gets 200 and nothing is recorded; a removed key stays on the operator's list of removed keys for 60 days (section 3.2).

`GET /.well-known/nostr.json?name=` — unauthenticated. NIP-05 for the operator's own identity in v1; user names are v2.

`GET /defaults.json` — unauthenticated. The operator's endpoints, the default relays, the indexer relays and the Blossom mirrors, in the schema of section 3.1.

### 6.1 Deferred: server audio (not in v1)

Listening is on-device only in v1 (flow decision 22). The endpoints below are kept as the design for the later server voices; v1 servers don't implement them and v1 clients never call them.

`POST /audio` — body `{ "v": 1, "text_hash", "voice", "model", "text"? }`. The first call omits `text`. Responses: `{"status":"ready","url","duration","timestamps"}` when cached; `{"status":"miss"}`; after a second call including `text` (the server verifies `sha256(normalise(text)) == text_hash`), `{"status":"queued","eta_seconds":<measured estimate>}`. Errors: 400 for an unknown voice or model, 413 `too_long` above 60,000 words, and a `{"status":"failed","reason"}` state when polling. Clients poll `GET /audio/status/<text_hash>/<voice>/<model>` no more than every five seconds. Plaintext sent for generation is held only on tmpfs and deleted within one hour of the job finishing or failing; it is never written to persistent storage.

`GET /audio/<id>` — readable by any registered pubkey with NIP-98 auth; byte-range capable. Cache entries expire after 90 days without access and are also evicted least-recently-used above a per-tier size ceiling.

`GET /audio/<id>/words.json` — `[{ "w": "word", "s": 0.00, "e": 0.32, "o": <character offset in the normalised Markdown> }, …]`.

## 7. Listening contract

In v1 clients implement `Voice` with one provider, `SystemVoice` (AVSpeechSynthesizer / `android.speech.tts`). `CachedVoice`, which plays server audio (section 6.1), is deferred; when it arrives, an article's playback keeps whichever provider started it until the article ends. Word highlighting maps to character offsets in the normalised Markdown through the spoken projection (section 4.2), re-anchored at paragraph boundaries to limit drift; on an engine that reports no word positions, the sentence being spoken is highlighted instead (flow decision 91 (h)).

The Listen tab holds only articles the user has played, the most recently played first (flow decision 3). "Play all" plays a snapshot of that list from the top to the end, then stops; a finished article rewinds to its start, paused; reading another article doesn't change what plays, and only starting a different article ends Play all (flow decision 35). The in-article player stops at the article's end, whose card offers "Archive and next" when another unread article has its text on the phone (the first in Unread order), beside "Archive" (flow decision 54). Listen history and the "N listened" count stay on the phone: no event carries them, so a restored or second phone starts with an empty Listen tab (flow decision 83).

## 8. Restore without the operator

A restoring client with only the recovery code and the copy of `defaults.json` baked into its release must: derive the key (section 2); fetch kind 10002 from the indexer relays and the default relays; fetch kind 10063; request `{"kinds":[30078],"authors":[pk],"#t":["kefli"]}` and `{"kinds":[5],"authors":[pk],"#k":["30078"]}` from all read relays; take the newest event per `d`, dropping any whose address an `a` tag names in a kind 5 at or after its `created_at`, and each save's hash from its content (section 4.1); take the library key from the newest `kefli/library-key` record, which it needs only to publish (section 4.3); and fetch text blobs from any server in each item's `text.servers` or the user's 10063 list. A save whose `text` is null has its page fetched and parsed again (section 4.1). This path is a contract test run with the operator relay and Blossom server switched off.

Signatures and NIP-44 ciphertext aren't deterministic in general, so the fixtures that hold them (the items and the library key record, the connected-browsers record, the save request, the pair-acks, the pair offer's proof and release, and the NIP-98 request) are checked by verifying and decrypting them and by round trips, in which a platform's own output must verify and decrypt with the fixture's keys; every other fixture must match exactly. A platform is not integrated until its CI passes all of them.

## 10. Versioning

`v` in every JSON body. Clients ignore unknown fields and refuse to write a version they do not understand. Kind numbers and `d` namespaces never change after launch; a breaking change to a JSON body increments `v` and clients migrate on read.

### 11.1 v1.11 → v1.12 (October 2026)

Made on 14 October 2026, when Richard set the fair use of the operator's server to keep its costs down (flow decision 117): each library keeps up to 50 MB of text there and uploads at most 20 MB a day, and past either the text stays on the phone and counts as not backed up. Those choices are his; the protocol details are the engineer's, under Richard's standing rule on low-level calls. No kind or event shape changes, and no client stops working with another: a phone from before v1.12 holds a save back on a 413, as it did, so in a library already past the new 50 MB it holds back every new save, link and title included, until it is updated; and an extension from before it names an inbox blob the operator refused, which a v1.12 phone meets as a 404.

1. **Fair use on the operator's server** (section 5). A library's quota falls from 200 MB to 50 MB, about 2,000 saves at the planning figure of 25 KB of text a save, still counting each blob once whether the user or one of their browsers uploaded it. A library may also add at most 20 MB to the server's disk in any 24 hours: a blob the server already stores costs nothing, and the day is counted from a log of uploads, so deleting gives none of the day back. Past either, an upload gets 413 `quota` or `daily` with the library's figures, tried again a day later, and after a confirmed deletion at once for the texts that fit the room left; a blob over 8 MB gets 413 `too_large`, never tried again, and any other 4xx answer to a phone's upload is tried again a day later. A user's delete now removes their browsers' uploads of the blob as well. Libraries made at the old default are lowered to the new one, keeping any blobs past it, and one set to another figure keeps it. Imported saves count like any other (section 4.6). *Backend; mobile, iOS and the extension read the reasons.*
2. **A refused text holds back only itself** (sections 4.1, 4.2 and 8). A save's publish waited for its text's upload, so a refusal held back the whole save, link and title included, and a refusal for good kept it off the relays for ever. A save whose text the operator refuses, a 507 for a full disk included, now goes out at once with `text` null, to every write relay, and goes out again naming the operator and a mirror once both hold the text; until then it counts as not backed up. `text` null, which meant a page that couldn't be parsed, now also means a text the operator hasn't taken. A client that receives such a save without holding its text parses its page, as a restore does; one that holds the text keeps it, and a save whose only change is a text the operator refused isn't published again until the text is taken, so two phones on a full library don't take turns publishing it without text. 3. **The claim** (section 1). Every save still reaches a server the operator doesn't run, and so does its text while the library is within its storage on the operator's server; past it, a save's text has only the phone's copy, as it does past the day's uploads until a later day's take it and, for good, over 8 MB, and a new phone fetches it again from its page. 4. **Browser captures** (sections 4.4 and 5). The extension sent a request naming its inbox blob even when the operator had refused the upload, and the phone then waited up to 14 days before fetching the page. The extension now sends the request with `html` null when the operator refuses its upload with any 4xx answer but 401 and 429, a 413 included; the phone fetches the page at once when the operator answers 404 for an inbox blob, and deletes the inbox blob once the request has made or matched a save, so a capture takes room only until the phone has taken it. *Extension, mobile, iOS, backend.*
5. **A move within the limits** (section 4.8). An upload refused under T counts as settled, so a full library doesn't hold the move for a day, and T's copy keeps naming the mirror that holds S's blob, so a text backed up under S stays backed up; T's re-uploads of blobs the server already stores cost nothing against its day. *Mobile, iOS.*
6. **`GET /account`** (section 6). It answers a registered user's quota, use, daily limit and last 24 hours' uploads, which Advanced shows with the figures a 413 carries, and `POST /register` answers with the library's own quota, where the server gave the default. *Backend, mobile, iOS.*
7. **A correction** (section 4.8, step 3). A move published T's copy "with the same `d`", which has been wrong since v1.10: T's copy is at its address under T's library key. *None; the code already did so.*

### 11.3 v1.9 → v1.10 (October 2026)

Made on 13 October 2026 from the pre-release audit's privacy findings, after Richard chose to change the code so the privacy statements hold rather than reword them.

1. **Keyed save addresses** (sections 1, 4.1, 4.3, 4.8 and 8; finding F5). A save's `d` was the plain SHA-256 of its normalised URL, so anyone holding a page's address could check whether a library had saved it, against section 1's "Nobody but the user can read which URLs they are". The `d` is now the HMAC-SHA256 of the save's hash under a per-identity library key, kept in a self-encrypted `kefli/library-key` record on the write relays. The hash itself, which still draws the cover (cover v1 is unchanged), rides inside the encrypted item as `hash`. Saves from before v1.10 are read by their unkeyed `d`, and move to their keyed addresses at the first sync that knows the key, each old address retired with a kind 5; their plain hashes, public already, stay visible in those.
