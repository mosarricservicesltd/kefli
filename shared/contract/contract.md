## 1. Principles the contract enforces

Saves are private by default and readable only by the user's key. The phone is the only holder of the user's private key in v1; the browser extension holds its own device key and the user's public key, never the user's private key. The library must survive the operator: by default every save and every text blob reaches at least one server the operator does not run, normally moments after it is made (the count below shows any that haven't), so a user who restores from their recovery code on a new phone gets their library back even if every operator machine is gone. A save is backed up once a relay the operator doesn't run has accepted its newest event and, for a save with text, a mirror (section 4.2) holds its blob. Each client that holds the library counts the saves that aren't backed up and shows the count (on the phone, under Advanced); the claim that the library outlives the service rests on that count staying near zero, so a default relay or mirror that refuses saves is retired within a day (section 3.1, flow decision 93). What needs the operator in v1 is making new saves: registration, the browser extension's inbox and the first copy of each text blob all go through its servers. Everything already saved stays readable and listenable without it. The word "nostr" appears on screen only where the signed-off screens use it: the sign-in route that starts at "Sign in with your nostr app", switching to a nostr app, You for someone signed in with their nostr app, and Delete my data (flow decision 86); "relay" appears only in Advanced (flow decision 76); no other nostr vocabulary reaches a screen.

What the design does not hide, stated plainly so the privacy note can repeat it: relays see the user's public key, the number of saves, when each was made or changed, and a `t` tag showing the saves belong to this app. Nobody but the user can read which URLs they are. A new save can briefly have only the operator's copy, until a backup server accepts it. In v1 no server sees article text in readable form, because listening uses the phone's own voice. The deferred server voices (section 6.1) would let the operator see an article's plaintext while generating its audio and would serve a cached file to any registered user who saved the same text; this paragraph must say so before they ship.

## 2. Identity and keys

Key generation happens on the phone using secp256k1 (NIP-01) when the person taps New here, or when they first share to Kefli before ever opening it (flow decision 6), unless Block Store already holds a mnemonic (below). The key is derived from a BIP-39 twelve-word mnemonic by the NIP-06 path, so that the recovery code is standard and portable to other nostr apps: 128 bits of entropy, the BIP-39 English word list, the BIP-39 seed with an empty passphrase (PBKDF2-HMAC-SHA512, 2,048 rounds), and account 0, `m/44'/1237'/0'/0/0`.

Storage on iOS is the Keychain with `kSecAttrSynchronizable` set, so the key rides iCloud Keychain and returns on reinstall or on a new iPhone signed into the same Apple account. Storage on Android is a file under `noBackupFiles`, encrypted with AES-256-GCM under an Android Keystore key (StrongBox-backed where available), plus the active local identity's mnemonic in one Google Block Store entry, so it restores on a new phone signed into the same Google account. The entry is marked for cloud backup only while Block Store reports end-to-end encryption available, checked again at each launch. `EncryptedSharedPreferences` is not used; the AndroidX security-crypto library is deprecated. The Block Store entry follows four rules:

- A launch with no key on the phone and a mnemonic in Block Store, as after a reinstall or on a new phone on the same Google account, stores that key, skips Welcome and opens Saves while the library restores (section 8, flow decision 79).
- A share made before the app is first opened reads Block Store first. If the entry holds a mnemonic, the share stores that key and saves under it, and the next open goes to Saves while the library restores (flow decision 79). Only when the entry is empty does the share make a new key, and it writes that key's mnemonic there.
- Outside a move, a restore by recovery code or second-phone pairing writes the entry when it stores the identity, and signing in with a nostr app removes it, since that identity has no mnemonic.
- During a move (section 4.8), the early-saves move included, the entry keeps the source key's mnemonic until step 5, then takes the target's, or is removed when the target is a nostr app.

The recovery code is shown only on request from the You tab, labelled "Recovery code", never "seed", "nsec" or "wallet". It is the route back for people who leave Apple or Google, or who never had account sync on.

Existing nostr users sign in through one interface:

```
Signer {
  pubkey()
  capabilities() -> { nip44: bool }
  signEvent(unsigned)
  nip44Encrypt(pubkey, plaintext)
  nip44Decrypt(pubkey, ciphertext)
}
```

Providers are: the local key (generated, or restored from the recovery code, Block Store or another phone), NIP-55 Android signers (Amber and compatible), and NIP-46 remote signers reached by a pasted `bunker://` link. Pasting a private key (an nsec) is not offered in v1 (flow decision 90). A `bunker://` link must carry the remote signer's pubkey as 64 hex characters and at least one `relay` parameter with a `wss://` URL, and may carry a `secret`; any other link is refused at the field (flow decision 91 (b)). The app talks to the signer only on the link's `wss://` relays, with a client keypair it generates and keeps with the identity, and sends `connect` with the parameters `[<signer pubkey>, <secret or "">, <perms>]`. A request unanswered after two minutes fails and changes nothing (flow decision 91 (b)). `perms` asks for the standing permissions up front, so the user is asked once rather than at every action: `nip44_encrypt,nip44_decrypt,sign_event:30078,sign_event:5,sign_event:13,sign_event:10002,sign_event:10063,sign_event:22242,sign_event:27235,sign_event:24242,sign_event:39701`. A NIP-55 signer is asked for the same, as the `permissions` of its `get_public_key` request: `[{"type":"nip44_encrypt"},{"type":"nip44_decrypt"},{"type":"sign_event","kind":30078},…]`, with one `sign_event` entry for each kind in the NIP-46 list. Kind 13 is the seal around a pair-ack (section 4.4); kinds 10002 and 10063 are the relay and server lists (sections 3.1 and 4.2). Every platform runs the same capability probe at sign-in and at step 1 of a move (section 4.8): encrypt the fixed string `kefli-probe` to the signer's own pubkey, decrypt it, compare. A signer that fails is refused. At sign-in the copy is "Your nostr app can’t keep your saves private yet. Try another app, or start a new library on this phone." (flow decision 91 (d)); when switching to a nostr app, the refusal is that screen's own drawn state (flow decision 91 (c)).

Second-phone pairing moves the mnemonic by an online exchange (flow decision 85), and only for an identity that has one: Add another device is hidden for someone signed in with their nostr app, who signs in with it on the new phone instead (flow decision 90). The source phone draws 32 random bytes `s` and a six-digit code `c`, uniform over 000000–999999, fresh for each QR, and shows a QR containing `{v:1, pubkey, secret: <hex of s>, expires}` (five-minute expiry) with the six digits under it. From `s` and `c` it derives 64 bytes with HKDF-SHA256 (input key `s`; salt `kefli/phone-pair/v1` as ASCII; info the six digits as ASCII). The first 32 bytes, in hex, are the `lookup`; the last 32 are an AES-256-GCM key, under which it encrypts `{v:1, mnemonic}` as UTF-8 JSON with a random 12-byte IV and no additional data, and posts the lookup and `base64(IV ‖ ciphertext ‖ tag)` with `POST /phone-offers` (section 6), signed by the user. The target phone scans the QR, checks that `v` is 1 and `expires` hasn't passed (allowing 60 seconds of clock skew), takes the six digits, derives the same bytes and fetches `GET /phone-offers/<lookup>` signed with a throwaway key. A code that finds no offer is the wrong-code field error, and the person can type it again. The target decrypts the offer, derives the key from the mnemonic by the path above, refuses it unless that key's pubkey equals the QR's `pubkey`, stores the identity (Block Store as above) and restores the library (section 8). The QR alone and the code alone are each useless. The operator holds the lookup and ciphertext without `s`, and someone with a photo of the QR still has to guess the six digits online, at most 30 tries an hour from each address, within five minutes.

## 3. Relays

### 3.1 The relay set every user writes to

A new user's app publishes a NIP-65 kind 10002 relay list on first save containing three relays, each for reading and writing: the operator relay (`operator.relay` in `defaults.json`) and the default relays `relays[0]` and `relays[1]`. The same kind 10002 is also published to every relay in `indexer`, so that a restoring client can find it with nothing but the public key. Its kind 10063 lists the operator Blossom server and `mirrors[0]`.

Every kind 30078 and every kind 5 deletion goes to all write relays in the user's kind 10002. Users who already have a kind 10002 or 10063 keep theirs; the app adds the operator relay and `relays[0]` to the 10002, and the operator Blossom server and `mirrors[0]` to the 10063, only with the user's agreement: a "Keep backup copies" switch, on by default, on the nostr sign-in screen and on "Use my nostr app instead" (flow decision 76). With the switch on, an entry is added only when its URL isn't already listed, and every other entry keeps its place and its read or write marker. With the switch off, the app writes only to the relays already in the user's list and leaves both lists unchanged; blobs still go to the operator server and a mirror (section 4.2), and the inbox still uses the operator relay (section 4.4). A user's list counts as absent only once every indexer relay and at least two of `relays` have sent EOSE without one, and every edit starts from the newest copy seen on any relay, so a failed read never replaces the list the user's other nostr apps share. A user with no kind 10002, or no kind 10063, gets the default one either way.

`defaults.json` lists the operator's endpoints and the defaults, each list in order of preference:

```
{ "v": 1,
  "operator": { "relay": "wss://relay.<domain>", "blossom": "https://blossom.<domain>", "api": "https://api.<domain>" },
  "relays":  ["wss://…", "wss://…"],
  "indexer": ["wss://purplepag.es"],
  "mirrors": ["https://…"] }
```

`relays` holds at least two entries, `indexer` and `mirrors` at least one each. Clients fetch it with `GET /defaults.json` (section 6) at each start and at least once a day, keep the last copy that parsed, and otherwise use the copy baked into the release, so the lists can change without an app release. The defaults are chosen in week 1 by testing candidates (starting with `relay.damus.io`, `nos.lol`, `relay.primal.net`) against four checks: accepts kind 30078 from unknown authors, keeps addressable events indefinitely, accepts events of at least 16 KB, and has a published operator.

Retiring an entry (flow decision 93). The operator removes a default relay or mirror from `defaults.json` within a day of finding that it refuses saves or fails one of the four checks. The entries after it move up, and nothing else reorders the lists, so `relays[0]` changes only when its entry is retired. A retired entry no longer counts towards a save being backed up (section 1). Where a user's 10002 or 10063 holds a retired entry that Kefli added (every default entry of a generated identity; for a nostr user, one that this phone recorded adding), the app replaces it with the first entry of the same list that the user's list lacks, republishes the list, and copies the library to the replacement: every item is published to a new relay, and for a new mirror every blob is mirrored to it and its item republished naming it.

### 3.2 The operator relay

strfry. Writes are accepted when the event's author (`pubkey`) is on the registration allowlist; the signature proves authorship, so no NIP-42 AUTH is required to write. Two exceptions take events from authors who aren't registered. Kind 1059 gift wraps, whose author is a throwaway key, are accepted from anyone when their `p` tag names a registered pubkey or an authorised device pubkey (section 6), since pair-acks are addressed to the device. A kind 5 is accepted from any author when every event it names in an `e` tag is a kind 1059 by that author which the relay holds; this is how the extension's Undo deletes its own wrap (section 4.4). All other kinds from unregistered authors are rejected. Reads of kind 30078 and other kinds are open, because the content is encrypted and the same events already sit on public relays.

Deletion follows NIP-09 and NIP-59: a kind 5 removes the events it names whose author is the kind 5's author, and also any kind 1059 it names whose `p` tag names the kind 5's author, so the recipient can delete a wrap it has consumed. Once `DELETE /account` has run for a user, the relay drops every kind 1059 whose `p` tag names that user or one of their devices, and accepts no more, since neither key is registered or authorised any longer.

Reads of kind 1059 require NIP-42 AUTH and are served only to the pubkey in the wrap's `p` tag, as NIP-17 recommends. AUTH is per connection: the relay issues a challenge on each connection and verifies that the AUTH event carries that challenge and a `created_at` within ten minutes. Clients keep one long-lived connection per relay while foregrounded and AUTH once per connection. Remote-signer users are not prompted each time because `sign_event:22242` is in the standing permissions in section 2.

Limits: `maxEventSize` 16,384 bytes for kinds 30078 and 1059, 64 KB otherwise; per-pubkey write rate 60 events per minute; a retention rule drops events from de-registered authors after 30 days.

### 3.3 Event size ceiling

No client ever publishes an event larger than 16 KB. strfry's default `maxEventSize` is 65,536 bytes and many public relays use it or less, and gift-wrapping multiplies a payload's size by roughly 1.8 through two layers of NIP-44 and base64. Article text and HTML therefore never travel inside events; they go to Blossom (section 5), and events carry only a hash and a key.

## 4. Event kinds

### 4.1 Save item: kind 30078 (NIP-78 app data)

One addressable event per saved URL per user. Tags, exactly:

```
["d", "kefli/item/<sha256 hex of the normalised URL>"]
["t", "kefli"]
```

The `t` tag lets clients fetch all of a user's saves with `{"kinds":[30078], "authors":[pk], "#t":["kefli"]}` without pulling other apps' NIP-78 data. A save is an event whose `d` is `kefli/item/` followed by 64 lowercase hex characters; other `kefli/` addresses that the same filter returns, such as the connected-browsers record (section 4.9), are not saves. The `content` is NIP-44 v2 ciphertext, self-encrypted (conversation key from the user's own key pair), of:

```
{
  "v": 1,
  "url": "https://example.com/article",
  "canonical": "https://example.com/article",
  "title": "…",
  "site": "example.com",
  "byline": "…",
  "saved_at": 1757000000,
  "state": "unread" | "archived",
  "progress": 0.0,
  "words": 2450,
  "lang": "en",
  "text": { "sha256": "<hex of ciphertext blob>", "key": "<base64 32 bytes>", "nonce": "<base64 12 bytes>",
            "servers": ["https://blossom.<domain>", "https://<default mirror>"] } | null,
  "text_hash": "<sha256 hex of normalised plaintext Markdown>" | null,
  "hero": "https://example.com/img.jpg",
  "source_kind": "web" | "nostr-article" | "nostr-note",
  "source_ref": "<naddr or nevent when source_kind is nostr>",
  "audio_pref": null | { "voice": "af_heart", "model": "kokoro-82m-v1.0" }
}
```

`text` and `text_hash` are null for a save whose page could not be parsed, the guard's refusals included (section 4.2); the reader then opens the original page. `saved_at` is the save's own time in Unix seconds: the share time for a phone share, the request's `captured_at` for a browser save (or the time it is processed, if `captured_at` is later), and the import time for an imported link. `progress` is the reading position as a fraction: 0 when `words` is null or 0, otherwise min(1, w ÷ `words`), where w is the index of the word reached in the spoken projection (section 4.2); a reader takes w = round(`progress` × `words`), counting a missing or non-numeric `progress` as 0. A client that derives an article again under a later spoken projection whose count differs stores the new `words`, keeps w inside it, and publishes both with the next reading position (section 11.1). v1 clients write `source_kind` as `web` only; `nostr-article`, `nostr-note` and `source_ref` are reserved (flow decision 82). `audio_pref` is reserved for the deferred server voices and is always null in v1.

State changes republish the same `d` with a newer `created_at`. A repeat save, meaning a share or browser save whose `d` already exists, un-archives an archived save and sets its `saved_at` to the new save's time, and leaves an unread one unchanged (flow decision 89, G2). Deleting a save publishes a NIP-09 kind 5 with an `a` tag for the address and a `["k","30078"]` tag to every write relay, one kind 5 naming up to 50 addresses, and deletes the blob from every server listed in `text.servers`. Clients read deletions with `{"kinds":[5],"authors":[pk],"#k":["30078"]}` and drop a save whose address a kind 5 names at or after the save's `created_at`. Target size of the event: under 4 KB.

### 4.2 Article text blob

The body is Markdown produced by the canonical pipeline: `@mozilla/readability` 0.6.0 output converted by `turndown` 7.2.4 with the fixed rules in `shared/turndown-rules.json`. Both libraries are vendored under `shared/`; bumping either regenerates the fixture hashes and bumps this contract's version.

- **Readability** runs with its defaults, `new Readability(document)` with no options, on a document whose base URL is the page's address. `isProbablyReaderable(document)`, also with its defaults, is read from the same document first, and `canonical` and `hero` before that (section 4.3), since `parse()` changes the document. The extension's `charThreshold: 250` is dropped.
- **Turndown** takes its options and any added rules from `shared/turndown-rules.json`. Its first version holds the options `parser-runner.js` uses, `{"headingStyle":"atx","codeBlockStyle":"fenced","bulletListMarker":"-","emDelimiter":"_"}`, and no added rules. Its sha256 sits in `shared/vendor/VERSIONS.md` beside the libraries', and changing it, like bumping a library, regenerates the fixtures and bumps this contract.
- **The guard** (flow decisions 77 and 78). A parse whose `isProbablyReaderable` is false and whose spoken projection (below) has fewer than 120 words counts as failed, as does one where Readability returns nothing; the save then has `text` and `text_hash` null.
- **Encryption.** The plaintext is the normalised Markdown (below) as UTF-8. It is encrypted with AES-256-GCM under the item's 32-byte key and 12-byte nonce with no additional data, and the blob is the ciphertext followed by the 16-byte tag; `text.sha256` is the SHA-256 of the blob.

The blob is uploaded to the operator Blossom server with a kind 24242 Blossom auth event, then mirrored with BUD-04 to the first entry of `mirrors` in `defaults.json` that accepts it, and `text.servers` lists the operator server and that mirror. A mirror that refuses, with any HTTP 4xx answer other than 401 and 429, is passed over for the next entry, and the item is republished naming the new one, so `text.servers` never lists the operator alone; once every entry has refused, the client waits a day and starts the list again. Until a mirror holds the blob, the save counts as not backed up (section 1, flow decision 93). The user's kind 10063 server list (BUD-03) is published as section 3.1 says. Blobs are ciphertext, so public mirrors hold nothing readable. Images are never uploaded; the Markdown keeps original image URLs and clients cache images locally.

`text_hash` is the SHA-256 of a normalised form of the Markdown: Unicode NFC, CRLF to LF, trailing spaces and tabs removed from every line (lines split at LF only), runs of three or more newlines collapsed to two, and exactly one trailing newline. It is reserved as the key of the deferred audio cache (section 6.1); v1 computes it and the fixtures check it, so the hashes are already stable when server voices arrive.

Where the Readability runs: the extension on the live DOM; Android in a hidden WebView; iOS in Safari via the share extension's preprocessing script for Safari shares, and in a WKWebView on next foreground for URL-only shares (the extension's Swift port may parse first for the offline copy, and the item is re-parsed with Readability.js so its hash converges). A share-sheet save (HTML fetched by the phone) and an extension save (rendered DOM) of the same URL may legitimately produce different `text_hash` values; once the audio cache exists, the two would miss each other there, which is expected.

The spoken projection is what a voice reads and what `words` counts. It is computed from the normalised Markdown, parsed as CommonMark: the text of each node in document order, with Markdown syntax removed, link text kept and link targets dropped, images dropped with their alt text, code blocks read like other text, raw HTML read as written (the pipeline writes no tags, so any in the Markdown was text in the article), character escapes and entity references resolved, each run of whitespace inside a block read as one space, a full stop added to a heading, and to each paragraph directly inside a list item, whose text doesn't end in `.`, `!` or `?` (optionally followed by a closing quote or bracket), and blocks separated by a blank line. Citation and footnote markers are not spoken (flow decision 102), since the voice reading "bracket one" breaks the sentence it sits in: a link whose target's fragment starts with `cite_note-`, whatever its text; a link whose whole text is one to three digits, optionally in square brackets, and whose fragment starts with `fn`, `footnote` or `note`; a link whose text is only carets, arrows and spaces and whose fragment starts with `fnref`, `footnote-anchor` or `cite_ref`; and a link into Wikipedia's project namespace (`/wiki/Wikipedia:` or its localised name), alone or in emphasis, when the text before it ends in `[` and the text after it starts with `]`, which go with it (a maintenance tag such as "[citation needed]"). A list item whose first paragraph opens, after any `^` or `↑`, with a link whose fragment starts with `cite_ref-` is not spoken, nor anything in it (an entry in a reference list). The rule reads link targets, because text in square brackets is often content, such as IPA. The Markdown keeps every marker and the reader shows them. Each spoken character maps to its offset in the normalised Markdown, which word highlighting uses (section 7). `words` is the number of whitespace-separated tokens in the projection. The reference implementation is in `packages/protocol`; the page fixtures carry each page's projection and `words`, and where this paragraph and the fixtures disagree, the fixtures win.

### 4.3 URL normalisation and the `d` tag

`normalise(url, canonical?)`: lowercase the scheme; convert the host to ASCII by UTS-46 with the WHATWG URL Standard's settings (non-transitional processing), which also lowercases it; drop the fragment; remove `utm_*`, `fbclid`, `gclid`, `mc_cid`, `mc_eid`, `ref`, `igshid`, and on twitter.com/x.com only `s` and `t`; sort the remaining query parameters; strip every trailing slash, a bare host keeping its one. Parsing and serialisation follow the WHATWG URL Standard on every engine (the `whatwg-url` package, whose host step is `tr46`), so default ports, dot segments, IPv4 forms and percent-encoding come out as a browser's `location.href` gives them; only `http` and `https` URLs are links. The further rules (query names matched case-sensitively and sorted in their decoded form, as `URLSearchParams` reads them, with each pair kept byte for byte and repeated names in their order; empty pairs dropped; `s` and `t` stripped on the X hosts' subdomains too; user info and a trailing dot on the host kept) are listed in the fixtures' `rulings`. When the host begins `m.` or `amp.`, or the path ends in `/amp` or `/amp/`, and `canonical` is given and is an `http` or `https` URL, the result is `normalise(canonical)`; otherwise these are left as they are. Reference implementation `shared/normalise.ts`, which parses with `whatwg-url` and `tr46` on every engine rather than the platform's `URL`; every port must pass `shared/normalise.fixtures.json`, which includes IDN and mixed-script hosts.

`canonical` is the first `<link rel="canonical">` in the page, resolved against the page's address and kept only when its scheme is `http` or `https`. It is read before Readability runs, and so is `hero`, from `og:image`, else `twitter:image`. The extension reads both from the live document with the same code.

A save's `d` is `kefli/item/` followed by the hex SHA-256 of `normalise(finalUrl, canonical)`, where `finalUrl` is the address after every redirect (for an extension save, the page's address without its fragment), for shares, browser saves and imports alike. A client keys a new save by `normalise(sharedUrl)` until its fetch resolves, and publishes it only once its parse has succeeded or definitely failed. If the fetch gives another `d`, the client re-keys the save, which is always before its first publish, and the cover, drawn from the new hash, crossfades once; if the new `d` is already a save, the repeat-save rule applies (section 4.1) and the provisional save goes. Once published, a save's `d`, and so its cover, never changes (flow decision 80).

X posts (flow decision 78). A URL on `x.com`, `twitter.com` or `mobile.twitter.com` with the path `/<user>/status/<id>` is never saved as itself. The client asks X's public embed service (`GET https://publish.x.com/oembed?url=<post>`, 5 s timeout), resolves the links in its `html` in order (`t.co` links followed without a browser user agent, five hops at most), and saves the first whose host isn't `x.com`, `twitter.com`, `pic.x.com`, `pic.twitter.com` or `t.co` as an ordinary link. No such link, or one to an X Article (`x.com/i/article/…`), saves nothing. Offline, or while the embed service fails, the post's URL is saved and checked again later: an article re-keys the save as above, and no article leaves it as a failed parse whose original page is the post. Nothing from X's response is stored.

### 4.4 Browser extension: device key, inbox blob and sealed save

The extension generates its own device keypair at install. It never holds the user's private key.

Pairing: the extension shows a QR containing `{v:1, device_pubkey, relay: "wss://relay.<domain>", nonce, expires, label}` (five-minute expiry), with the same offer as a typed code under it (below). `relay` is always the operator relay. `label` names the browser, such as "Chrome on a Windows laptop", built from the browser's brand and platform, never a hostname or user name. The phone scans the QR or takes the typed code and checks it: `v` is 1, `expires` hasn't passed (allowing 60 seconds of clock skew), `device_pubkey` is a valid x-only public key, `label` is plain text under 64 characters, and `relay` equals `operator.relay` in `defaults.json`. It then shows "Connect this browser?" with the label in a card under it ("Chrome on a Windows laptop", then "Pages you save there will come to this library."), and on confirmation calls `POST /devices` (section 6) signed by the user's key, which authorises the device key to upload blobs against the user's quota. The phone then sends a NIP-59 gift wrap to the device pubkey on that relay, sealed by the user's key, whose rumor is kind 30078 with `["d","kefli/pair-ack"]` and content `{v:1, user_pubkey, write_relays, blossom_servers, token, nonce}`, `token` being 32 random bytes in hex, and adds the browser to the connected-browsers record (section 4.9). The extension checks the nonce, stores the result, and shows "Connected". The phone lists the device under You → Connected browsers with Disconnect, which marks its entry revoked, republishes the record and calls `DELETE /devices/<pubkey>`.

Typed code, for when the phone can't scan (flow decisions 11 and 29): the extension also shows an eight-character code, written XXXX-XXXX, drawn at random from Crockford's base32 alphabet (0–9 and A–Z without I, L, O and U), so 40 bits. It is made with each QR and expires with it. From the code the extension derives 64 bytes with scrypt (password: the eight characters in upper case without the hyphen, as ASCII; salt: `kefli/pair-code/v1`; N = 16384, r = 8, p = 1). The first 32 bytes, in hex, are the `lookup`; the last 32 are an AES-256-GCM key, under which the extension encrypts the QR's JSON as UTF-8 with a random 12-byte IV and no additional data. It posts the lookup and `base64(IV ‖ ciphertext ‖ tag)` with `POST /pair-offers` (section 6). On the phone the user types the code; the phone reads it leniently (upper case, hyphens and spaces dropped, O read as 0, I and L read as 1), derives the same bytes, fetches `GET /pair-offers/<lookup>`, decrypts the offer, checks it exactly as a scanned QR and carries on from the confirmation. A code that isn't eight characters after the lenient read, finds no offer, or gives an offer that fails to decrypt gets the field error "That code didn’t match. Check it in your browser, or show a new one there." The operator holds only the lookup and the ciphertext, for at most five minutes, and recovering the nonce from them takes a search of 2^40 scrypt evaluations inside that time. As with the QR, someone who reads the code off the screen during those five minutes could connect the browser to their own library instead; the options page would then say Connected while the user's phone doesn't list the browser.

Moving a browser to another identity (section 4.8): while paired, the extension keeps a subscription for kind 1059 with `#p` = its device pubkey on the operator relay, with NIP-42 AUTH by the device key, whenever it is connected there, and checks it on start. It accepts a pair-ack whose content carries `"moved_from"` (in place of `nonce`) equal to its current `user_pubkey`, and whose seal is signed by that same key. It then replaces its pairing record with the new `user_pubkey`, relays, servers and token, and wraps any saves still queued again for the new user before sending them. It ignores any other pair-ack once paired.

Save: the extension runs Readability on the page with the options and guard of section 4.2, reading `canonical` and `hero` first (section 4.3). Unless the guard trips or the content HTML is over 2 MB (2,097,152 bytes as UTF-8), it encrypts that HTML as UTF-8 with a fresh AES-256-GCM key and nonce in the blob format of section 4.2 and uploads the blob to the operator Blossom server authenticated by the device key (an inbox blob, auto-expiring after 14 days). It then sends a gift wrap to the user's pubkey whose rumor and seal are signed by the device key and whose wrap is signed by a fresh random key. The rumor is kind 30078 with `["d","kefli/save-request/<uuid>"]` and content:

```
{ "v": 1, "url", "canonical", "title", "site", "byline", "lang", "hero", "captured_at", "token",
  "html": { "sha256", "key", "nonce", "server" } | null }
```

`url` is the page's address without its fragment, `lang` is Readability's, and `captured_at` is in Unix seconds. `html` is null when capture failed, the guard tripped or the HTML was over 2 MB; the phone then fetches and parses the URL itself, as it also does once the inbox blob has expired. The wrap is published to the operator relay only and is under 8 KB.

The phone subscribes to kind 1059 with `#p` = own pubkey on the operator relay (AUTH required), with `since` at least 172,800 + 300 seconds before its last drain, because NIP-59 lets a wrap's `created_at` lie up to two days in the past, and skips wraps it has already seen. It unwraps each, requires the rumor's pubkey to equal the seal's, and leaves alone anything that isn't a kind 30078 rumor with `d` = `kefli/save-request/…`, since other apps' messages share the `p` tag. It ignores a request whose `v` it doesn't understand (section 10), whose `token` isn't a connected entry of the connected-browsers record (section 4.9), or whose seal isn't signed by that entry's `device_pubkey`. For an accepted request whose URL is an X post, the phone discards the HTML and follows the X rule (section 4.3). Otherwise it downloads the HTML from `html.server`, which must be the operator Blossom server, checks its sha256, decrypts it, runs the canonical Markdown conversion, and creates the kind 30078 item exactly as if the share sheet had been used, with its own text key and blob, and `saved_at` = `captured_at`, or the current time if `captured_at` is later. If the save's `d` already exists, the repeat-save rule applies (section 4.1), with the new save's time worked out the same way. Only for a wrap that created, un-archived or matched a save does the phone then publish a kind 5 for the wrap (`["e", <wrap id>]`, `["k","1059"]`) to the operator relay. Every other wrap is left as it is, so a phone that hasn't yet received the connected-browsers record can't remove a save another phone still needs.

Undo in the extension publishes a kind 5 for the wrap signed by the wrap key, valid because that key is the wrap's author, and accepted by the operator relay (section 3.2). If the phone has already consumed the wrap, undo shows "Remove it from your phone's Saves" instead.

The phone acts on wraps within seconds while open, and the ten-second target for a browser save is measured with the app open. Closed or suspended, Android drains the subscription on foreground and on its periodic background task, which runs no more often than every 15 minutes, and later under Doze; iOS drains on launch and on background refresh when granted. A browser save made while the phone is closed therefore arrives at the next of these (flow decision 84).

Existing nostr users with a NIP-07 browser extension still pair this way in v1. Signing saves directly from the browser would duplicate the hash-critical Markdown step outside the phone.

### 4.5 Public recommendation (v2, reserved now): kind 39701

A NIP-B0 web bookmark with `d` = URL without scheme, `title`, `published_at` and `t` tags, emitted only on an explicit "Recommend" gesture and never automatically. Public recommendations are the only events any other nostr client will display.

### 4.6 Existing bookmarks import

Web links only in v1 (flow decision 82). On the first sign-in of an existing nostr user, the phone reads their kind 39701 web bookmarks (NIP-B0; each `d` is the URL without its scheme, imported as `https://<d>`) and the `r` tags of their kind 10003 list and of every kind 30003 set. Entries kept privately in a list's encrypted `content`, `e` tags and `a` tags are not imported. When at least one link is not already a save (by `d`, section 4.3), a sheet asks once, in the prototype's words (`nostr-import`): "Bring in your bookmarks?" and "We found N bookmarks in your nostr account. In your library they’ll be private, like everything else.", with Not now and Bring them in. N is the number of links not already saved, worded for one or several (flow decision 91 (f)). Either answer starts the restore. Bring them in imports every such link, with no cap, as a web save with `saved_at` set to the import time, fetched and parsed on the phone two at a time. Imported saves are private like any other, and nothing is published as a bookmark.

### 4.7 Delete my data

"Delete my data" under You first shows the explain screen (prototype `del`), which says what goes and what can only be asked for. It keeps the line "This removes your library from all your devices and from Kefli’s server." and counts the backup servers from the user's real lists: every write relay in their kind 10002 other than the operator's, a nostr user's own included, and every server other than the operator's named in any item's `text.servers`, each counted once (flow decision 89, G8; flow decision 91 (e)). Its other words are the prototype's. A nostr user then approves the signing in their nostr app; declining deletes nothing.

The deletion runs in three steps, in this order, because the operator relay rejects kind 5s from a deleted account (section 3.2). Each step's results are kept, so a deletion interrupted part way resumes.

1. **The operator.** Publish to the operator relay NIP-09 deletions for every wrap addressed to the user that the phone knows of, consumed or pending, and, when the operator relay is in the user's kind 10002, for everything step 2 deletes on relays; delete every blob on the operator Blossom server; then call `DELETE /account`. These run in every case, with at most a minute of retries. If the operator is still unreachable after that minute, or `DELETE /account` fails, nothing else runs and the key stays on the phone, so the person can try again.
2. **Every other server.** Publish deletions to every other write relay in the user's kind 10002 (Kefli's backup relays and, for a nostr user, their own) for every kind 30078 with `#t` = `kefli`, whatever its `v`, the connected-browsers record included; delete every blob from every other server named in any item's `text.servers`. A relay counts as confirmed once it has answered OK true to every kind 5 sent to it, and a Blossom server once it has answered 2xx or 404 to every delete; each server gets at most a minute of retries and is otherwise reported as not confirmed. A generated identity's kind 10002 and 10063 are deleted too, by a kind 5 with the `a` tags `10002:<pubkey>:` and `10063:<pubkey>:` and the `k` tags 10002 and 10063, sent to the same relays and to the indexer relays. A nostr user's lists are never deleted, since their other nostr apps share them; they are republished without the operator's relay and Blossom server and without any default entry this phone recorded adding.
3. **The phone.** Wipe the key from local storage and from iCloud Keychain or Block Store, then the local library. For a nostr user, wiping the key means forgetting the link to their nostr app (the NIP-46 client key or the NIP-55 signer's package).

The deleting screen shows a step for each server and names each one that didn't confirm (flow decision 91 (e)). Public relays may not honour kind 5; the ciphertext they keep is unreadable without the user's key, which for a generated identity the app has just destroyed.

### 4.8 Moving saves to another identity

Two flows move a library from one key to another. "Use my nostr app instead" under You → Advanced moves it from the key the phone generated to the user's nostr app (flow decision 13). Saves shared before the app was first opened were made under a fresh key, unless Block Store held a mnemonic (section 2), and move into the library the user then brings back (flow decision 6); that move runs alongside the restore and shows on its progress card. In both, the source S is a local key the phone holds and the target T is any `Signer` (section 2). Text blobs need no re-encryption, since each has its own key; what changes is who signs each event and who owns each blob.

The phone stays online throughout and Android Back is disabled while it runs:

1. **Prepare T.** Run the capability probe (section 2), call `POST /register` as T, and set up T's relay and server lists: an existing kind 10002 or 10063 is handled as at any nostr sign-in, under the Keep backup copies switch (section 3.1), and a T without one gets the default set.
2. **Collect both libraries**: for S and for T, the newest event per `d` from all their read relays, with their deletions applied (section 8), merged with the phone's local copies. If either library holds an item whose `v` this client doesn't understand (section 10), the move stops here and asks for an app update; S and every save stay as they were, and T's registration and lists stay (flow decision 91 (i)).
3. **Copy each item to T.** Decrypt it with S. If T already has an item with the same `d`, keep T's item and only un-archive it when S's copy is unread, as for a repeated save (section 4.1). Otherwise encrypt the same JSON to T (NIP-44 v2, self-encrypted, with `v` and every field unchanged except `text.servers`, which lists T's servers) and publish it, signed by T with the same `d` and `t` tags, to T's write relays. An item S never published, which exists only on this phone, is published under T alone. For an item with text, T takes ownership of the blob: it uploads the same ciphertext (fetched from `text.servers`) to the operator server with a kind 24242 auth signed by T, then mirrors it as in section 4.2. The blob's `sha256`, key and nonce don't change.
4. **Move connected browsers.** For each connected entry in S's connected-browsers record (section 4.9), call `POST /devices` signed by T with the same device pubkey and label, then send the device a pair-ack as in section 4.4, sealed by S, carrying T as `user_pubkey`, T's relays and servers, a new token, and `"moved_from": "<S pubkey>"`. T's record then lists each device with its new token and is published to T's write relays.
5. **Confirm, then retire S.** Read T's items back from min(2, n) of T's write relays, n being how many T has, and check that every `d` is present and decrypts. Only then: drain S's inbox one last time and move anything found there, publish NIP-09 deletions for S's items and S's connected-browsers record to S's write relays, call `DELETE /account` signed by S (which leaves the blobs T now owns, section 5), and wipe S from the phone and from iCloud Keychain or Block Store; the Block Store entry takes T's mnemonic, or is removed when T is a nostr app (section 2). S's recovery code stops working from this point, as the switch screen says.

The phone records its progress locally. If it stops part way, it resumes at the next start and skips items already under T, and S stays intact until step 5, so a save is never deleted before its copy exists under T.

### 4.9 Connected browsers record: kind 30078, `d` = `kefli/devices`

The phone keeps the user's connected browsers in one addressable kind 30078 with the tags `["d","kefli/devices"]` and `["t","kefli"]`, self-encrypted like a save (section 4.1) and published to every write relay, so that a reinstall, a restore, a second phone and a move (section 4.8) all know them. Its content:

```
{ "v": 1,
  "devices": [ { "device_pubkey", "label", "token", "connected_at", "revoked_at": <unix seconds> | null } ] }
```

`connected_at` and `revoked_at` are Unix seconds. The phone republishes the record after every Connect and every Disconnect, starting from the newest copy seen on any relay. Entries are keyed by `token`, which is new for every connection. On receiving a copy, and before publishing, a phone merges the two by `token`: an entry in either copy is kept, and a `revoked_at` set in either copy stays set, taking the earlier value. A revoked entry stays in the record, so a phone that was offline can't bring its token back; only when the event would pass the 16 KB ceiling (section 3.3) are revoked entries removed, the earliest `revoked_at` first. A browser counts as connected while it has an entry whose `revoked_at` is null. The record is deleted with the saves (section 4.7) and moved with them (section 4.8).

## 5. Blossom servers

The operator Blossom server accepts uploads authenticated by a registered user pubkey or an authorised device pubkey (section 6), counts both against the user's quota (default 200 MB), lists nothing publicly, and supports BUD-04 mirroring out. A blob uploaded by more than one pubkey, as after a move (section 4.8), is kept until its last owner deletes it or is deleted. Inbox blobs uploaded by device keys expire after 14 days. The default public mirrors (`mirrors` in `defaults.json`, section 3.1) are chosen in week 1 against the same four checks as the default relays plus an upload-size limit of at least 5 MB, and are retired as section 3.1 says. If no free public mirror proves reliable, the fallback is a second small Blossom instance on a different provider and domain, run by the operator; that is weaker than an independent mirror and the privacy note must say so.

## 6. Operator HTTP API

Base `operator.api` in `defaults.json` (`https://api.<domain>`). Every request except `GET /defaults.json` and `GET /.well-known/nostr.json` carries NIP-98 HTTP auth: a kind 27235 event in `Authorization: Nostr <base64>`, with a `u` tag equal to the exact request URL, a `method` tag, a `created_at` within 60 seconds of the server's clock, and, on every POST, PUT and DELETE, a `payload` tag holding the hex SHA-256 of the body, or of the empty string when there is no body. Every request body is a JSON object with `v`. Rate limits are per pubkey unless stated.

`POST /register` — body `{ "v": 1 }`. Adds the pubkey to the relay allowlist and creates the Blossom quota. Idempotent.

`POST /devices` — body `{ "v": 1, "device_pubkey", "label" }`, signed by the user. Authorises a device key to upload blobs against the user's quota. `DELETE /devices/<device_pubkey>` revokes it and deletes its unexpired inbox blobs.

`POST /pair-offers` — body `{ "v": 1, "lookup", "offer" }` (section 4.4), signed with NIP-98 by the extension's device key, which needn't be authorised yet. Holds the offer for five minutes. 409 when an unexpired offer already has that lookup; rate-limited per device key and per IP address to 30 an hour.

`GET /pair-offers/<lookup>` — signed by a registered user. Returns `{ "v": 1, "offer" }`, or 404 when no unexpired offer has that lookup.

`POST /phone-offers` — body `{ "v": 1, "lookup", "offer" }` (section 2), signed by a registered user. Holds the offer for five minutes. 409 when an unexpired offer already has that lookup; rate-limited per pubkey and per IP address to 30 an hour.

`GET /phone-offers/<lookup>` — signed with NIP-98 by any key, since the phone fetching it has no identity yet and signs with a throwaway one. Returns `{ "v": 1, "offer" }` and deletes the offer, or 404 when no unexpired offer has that lookup. Rate-limited per IP address to 30 an hour, 404s included.

`DELETE /account` — removes the user's and their devices' ownership of blobs on the operator server, deleting each blob that no other pubkey owns (section 5), and deletes their device authorisations and their allowlist entry; the operator relay then drops every kind 1059 addressed to the user or one of their devices (section 3.2). Once server audio exists (section 6.1) it also deletes their audio requests and any cached audio requested only by them. It cannot delete relay events; section 4.7 covers those.

`GET /.well-known/nostr.json?name=` — unauthenticated. NIP-05 for the operator's own identity in v1; user names are v2.

`GET /defaults.json` — unauthenticated. The operator's endpoints, the default relays, the indexer relays and the Blossom mirrors, in the schema of section 3.1.

### 6.1 Deferred: server audio (not in v1)

Listening is on-device only in v1 (flow decision 22). The endpoints below are kept as the design for the later server voices; v1 servers don't implement them and v1 clients never call them.

`POST /audio` — body `{ "v": 1, "text_hash", "voice", "model", "text"? }`. The first call omits `text`. Responses: `{"status":"ready","url","duration","timestamps"}` when cached; `{"status":"miss"}`; after a second call including `text` (the server verifies `sha256(normalise(text)) == text_hash`), `{"status":"queued","eta_seconds":<measured estimate>}`. Errors: 400 for an unknown voice or model, 413 `too_long` above 60,000 words, and a `{"status":"failed","reason"}` state when polling. Clients poll `GET /audio/status/<text_hash>/<voice>/<model>` no more than every five seconds. Plaintext sent for generation is held only on tmpfs and deleted within one hour of the job finishing or failing; it is never written to persistent storage.

`GET /audio/<id>` — readable by any registered pubkey with NIP-98 auth; byte-range capable. Cache entries expire after 90 days without access and are also evicted least-recently-used above a per-tier size ceiling.

`GET /audio/<id>/words.json` — `[{ "w": "word", "s": 0.00, "e": 0.32, "o": <character offset in the normalised Markdown> }, …]`.

## 7. Listening contract

In v1 clients implement `Voice` with one provider, `SystemVoice` (AVSpeechSynthesizer / `android.speech.tts`). `CachedVoice`, which plays server audio (section 6.1), is deferred; when it arrives, an article's playback keeps whichever provider started it until the article ends. Word highlighting maps to character offsets in the normalised Markdown through the spoken projection (section 4.2), re-anchored at paragraph boundaries to limit drift; on an engine that reports no word positions, the sentence being spoken is highlighted instead (flow decision 91 (h)).

The Listen tab holds only articles the user has played, the most recently played first (flow decision 3). "Play all" plays a snapshot of that list from the top to the end, then stops; a finished article rewinds to its start, paused; reading another article doesn't change what plays, and only starting a different article ends Play all (flow decision 35). The in-article player stops at the article's end, whose card offers "Archive and next" when another unread article has its text on the phone (the first in Unread order), beside "Archive" (flow decision 54). Listen history and the "N listened" count stay on the phone: no event carries them, so a restored or second phone starts with an empty Listen tab (flow decision 83).

## 8. Restore without the operator

A restoring client with only the recovery code and the copy of `defaults.json` baked into its release must: derive the key (section 2); fetch kind 10002 from the indexer relays and the default relays; fetch kind 10063; request `{"kinds":[30078],"authors":[pk],"#t":["kefli"]}` and `{"kinds":[5],"authors":[pk],"#k":["30078"]}` from all read relays; take the newest event per `d`, dropping any whose address an `a` tag names in a kind 5 at or after its `created_at`; and fetch text blobs from any server in each item's `text.servers` or the user's 10063 list. This path is a contract test run with the operator relay and Blossom server switched off.

## 9. Shared test fixtures

`shared/fixtures/` contains: twenty saved HTML pages, generated outside every client's CI by a pinned headless Chromium running the vendored parser bundle (its version in `shared/vendor/VERSIONS.md`), each with its Readability output HTML, expected Markdown, expected normalised `text_hash`, spoken projection and `words`; the normalise fixtures, with IDN and mixed-script hosts and the canonical rule; a mnemonic with its NIP-06 key; one text blob with its key, nonce, plaintext and sha256; three sample kind 30078 items with known keys and their decrypted JSON, and a fourth whose `text` is null; one connected-browsers record with its decrypted JSON; one kind 1059 save request with its rumor, recipient secret and inbox blob; one pair-ack and one move pair-ack; one typed-code pair offer with its code, lookup, key and decrypted offer; one phone-pair offer with its QR, six digits, lookup, key and decrypted payload; a NIP-98 signed request; a move scenario with three items under a source key, one of whose `d` the target already holds, and the items expected under the target; a restore scenario with the operator absent and a kind 5 removing one item; and the cover v1 fixtures (`shared/cover/fixtures.json`), run on each platform's own JavaScript engine (Hermes on the phone). Signatures and NIP-44 ciphertext aren't deterministic, so the fixtures that hold them (the items, the connected-browsers record, the save request, the pair-acks and the NIP-98 request) are checked by verifying and decrypting them and by round trips, in which a platform's own output must verify and decrypt with the fixture's keys; every other fixture must match exactly. A platform is not integrated until its CI passes all of them.

## 10. Versioning

`v` in every JSON body. Clients ignore unknown fields and refuse to write a version they do not understand. Kind numbers and `d` namespaces never change after launch; a breaking change to a JSON body increments `v` and clients migrate on read.

### 11.5 v1.1 → v1.2 (October 2026)

1. **Pairing by typed code** (flow decisions 11 and 29). The extension shows an eight-character code beside the QR; the phone can type it instead of scanning. The code is stretched with scrypt into a lookup and a key, and the offer waits encrypted on the operator for five minutes (`POST /pair-offers`, `GET /pair-offers/<lookup>`). The QR payload gains `label`, the browser's name the phone shows before connecting. *Extension (spec section 3), backend, Android.*
2. **Moving saves to another identity** (flow decisions 6 and 13), new section 4.8: copy every item to the target, take ownership of its blob, move connected browsers with a `moved_from` pair-ack, confirm, and only then retire the source key. The extension keeps a device-key subscription for that ack. A blob can have several owners, and `DELETE /account` leaves blobs that another pubkey owns. *Android, extension, backend.*
3. **Server audio is out of v1** (flow decision 22). The audio endpoints move to section 6.1 as deferred design; `Voice` has only `SystemVoice`; `audio_pref` is always null; `text_hash` is still computed and checked so it is stable for later. Section 1's privacy paragraph now says no server sees article text in v1. *Backend drops the TTS worker and audio API from v1; Android, iOS.*
4. **"Open in app" and the `/open` page are out of v1** (flow decision 9). The contract never specified them; the extension spec's timeline and the repo layout drop them. *Extension, website.*
5. **Three gaps found while writing v1.2.** The NIP-46 standing permissions lacked kinds 13, 10002 and 10063, which the pair-ack seal and the relay and server lists need, so a remote-signer user would have been prompted or refused. The operator relay accepted kind 1059 only for registered pubkeys, so a pair-ack addressed to a device key would have been rejected; it now accepts authorised device pubkeys too. Section 1 said the only thing lost without the operator was server audio; making new saves needs it too, and the sentence now says so. *Backend, Android, iOS, extension.*
6. **The sign-in agreement in 3.1 is a switch** (flow decision 76): "Keep backup copies", on by default, on the nostr sign-in screen and on "Use my nostr app instead", worded without "relay". With it off the app writes only to the user's own relays. *Android, iOS.*

### 11.6 v1.0 → v1.1 (September 2026)

1. **Private saves move from app-invented kind 30979 to NIP-78 kind 30078** with `d` = `shelf/item/<hash>` and a `t` tag `shelf`. Satellite rumors (kinds 979, 978) become kind 30078 rumors under `shelf/save-request/…` and `shelf/pair-ack`. *All specs.*
2. **Default mirrors so the library survives the operator.** New users publish kind 10002 with the operator relay plus two default public relays, to an indexer too; text blobs mirror to a default public Blossom server; kind 10063 is published; a no-operator restore test is added (section 8). *All specs; backend adds `/defaults.json`.*
3. **NIP-42 corrected.** The v1.0 ruling that let a relay accept an AUTH event up to an hour old was wrong: AUTH carries the relay's per-connection challenge and cannot be reused. Writes now need no AUTH at all (signatures prove authorship); only kind 1059 reads need it; bunker users grant `sign_event:22242` once. The private-relay list (kind 10013) and read restriction on saves are dropped because saves are ciphertext on public relays anyway. *Backend, Android, iOS.*
4. **Event size ceiling of 16 KB.** Extension HTML no longer rides inside gift wraps (up to 512 KB in v1.0, which most relays would reject); it goes to Blossom as an inbox blob uploaded with an authorised device key, and the wrap carries a hash and key. *Extension, backend (new `/devices` endpoints, device uploads, inbox expiry), Android, iOS.*
5. **Extension identity.** The extension has its own device keypair, authorised by the phone through `POST /devices`, replacing the v1.0 per-browser token-only design. The token stays inside the pair-ack and save request. *Extension, backend, Android, iOS.*
6. **Rulings on v1.0 objections, folded in:** Readability.js 0.6.0 and Turndown 7.2.4 vendored and canonical; `text_hash` over normalised Markdown; Android key storage via Keystore file plus Block Store; `Signer.capabilities()` and a fixed probe; audio API `eta_seconds` measured, 413 `too_long`, `failed` status, size-capped cache, registered-reader access, one-hour plaintext bound; `words` defined; deletion copy covers iCloud/Block Store propagation; the suspended-phone behaviour for extension saves and the toast copy; the image-URL privacy line.
7. **Honest privacy statements** added to section 1: metadata visible to relays, plaintext seen by the audio service, cached audio shared among users who saved the same text.
