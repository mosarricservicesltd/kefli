## 1. Goal and scope

The backend exists so that a phone can publish encrypted saves somewhere durable, store encrypted article bodies, and ask for spoken audio of an article without the operator learning what the article is. Everything the backend holds must be either ciphertext the operator cannot read, or a cache that can be thrown away without the user losing anything except server-generated audio. The project plan's definition of done includes turning the server off for an hour with no loss of app function beyond audio generation; that sentence shapes every decision below.

In scope: one VPS running strfry with a NIP-42 policy and a write-policy plugin, a Blossom-compatible blob store with per-pubkey quotas, the HTTP API from contract section 5, the Kokoro-82M worker with its queue and audio cache, TLS and the reverse proxy, backups, monitoring, log policy, abuse controls, a relay retention script, and a staging environment for the project engineer's contract tests. Out of scope: fetching third-party URLs (the server never fetches anything, so SSRF does not arise), parsing article HTML, plaintext storage beyond the lifetime of a TTS job, and the v2 NIP-05 name registry.

## 2. Architecture

One Debian 12 host, one public IP, three hostnames terminating at one Caddy instance. Behind Caddy sit three processes: strfry, a single Go binary called `keflid` that provides the HTTP API, the Blossom endpoints, the job queue, the audio cache and NIP-05, and a Kokoro-FastAPI container reachable only on localhost. A single SQLite database owned by `keflid` holds accounts, quotas, blob ownership, audio cache metadata and the job table; the strfry write-policy plugin opens the same database read-only to consult the allowlist.

```
                     Internet
                        |
                 +------+------+   :443 TLS, HTTP/2, rate limits per IP
                 |    Caddy    |   relay.<d>  api.<d>  blossom.<d>
                 +--+---+---+--+
                    |   |   |
       ws /  ------+    |   +------ /upload, /<sha256>, /list, /.well-known
       +---------+      |                 |
       | strfry  |      |          +------+------+
       | LMDB    |      +--------> |   keflid    |  Go, one binary
       +----+----+  /register     |  API + Blossom + queue + cache + NIP-05
            |       /audio        +--+-------+---+
            | stdin/stdout          |       |   \
     +------+--------+          SQLite    blobs/   audio/  (local disk)
     | write-policy  | ro         |
     | plugin (Go)   +------------+
     +---------------+              |
                                    | HTTP localhost:8880
                             +------+--------+
                             | Kokoro-FastAPI |  Docker, CPU image
                             | kokoro-82m     |  /dev/captioned_speech
                             +----------------+
```

One binary for the API-side pieces is deliberate: quota, accounts, blob ownership and the audio cache are all touched by `DELETE /account`, and one process with one database makes that a single transaction. The relay stays separate because strfry already implements the two features the contract leans on: NIP-42 with per-kind read restriction, and an external write-policy plugin ([strfry.conf](https://raw.githubusercontent.com/hoytech/strfry/master/strfry.conf), [plugins.md](https://github.com/hoytech/strfry/blob/master/docs/plugins.md)).

## 3. Components

### 3.1 Relay: strfry

strfry is configured with `relay.auth.enabled = true`, `relay.auth.serviceUrl = "wss://relay.<domain>"`, `relay.auth.restrictedReadKinds = "30979,1059"` and `relay.auth.restrictReadToInvolvedPubkey = true`. A REQ that mentions either restricted kind is then refused with `auth-required:` until the client completes NIP-42, and once authenticated the filter must name the authed pubkey in `authors` or `#p`, which strfry enforces itself. Clients must therefore include `"authors": [<own pubkey>]` on kind 30979 subscriptions and `"#p": [<own pubkey>]` on kind 1059 subscriptions.

`relay.maxWebsocketPayloadSize` defaults to 131,072 bytes ([strfry.conf](https://raw.githubusercontent.com/hoytech/strfry/master/strfry.conf)). A kind 1059 save request carries up to 512 KB of HTML inside a base64-encoded NIP-44 payload and can approach 750 KB, so the relay sets the frame limit to 1 MiB and the plugin applies per-kind ceilings below that. Negentropy stays enabled because it makes the retention export and the staging seed cheap.

The write-policy plugin is a small Go program launched via `relay.writePolicy.plugin`. strfry feeds it one JSON line per event with `event`, `receivedAt`, `sourceType`, `sourceInfo` and, when the connection has completed NIP-42, an `authed` field carrying the authenticated pubkey; the plugin answers with `id`, `action` (`accept`, `reject` or `shadowReject`) and an optional `msg` ([plugins.md](https://github.com/hoytech/strfry/blob/master/docs/plugins.md)). The rules: kind 30979 is accepted only when `authed` equals `event.pubkey` and that pubkey is in the `accounts` table, the event is under 64 KB, and the pubkey is under 120 events per hour. Kind 1059 has a throwaway author by construction of NIP-59, so the plugin instead requires `authed` to be present with any key (which forces the extension to AUTH with its ephemeral key and gives the limiter a handle), exactly one `p` tag naming a registered pubkey, size under 1 MiB, and under 60 wraps per recipient and 120 per source IP per hour; section 9 flags this reading of the contract. Kind 5 passes through, since strfry checks authorship itself. Every other kind is accepted under 64 KB at 300 per pubkey or IP per hour, and the restricted kinds are refused when `sourceType` is anything other than IP4 or IP6, so nothing syncs them in from another relay. The plugin opens the SQLite database read-only and refreshes the allowlist every five seconds, so `/register` takes effect on the relay within that window. It logs accept and reject counters per rule and nothing else.

strfry answers each filter with at most `relay.maxFilterLimit` events, 500, its own default, which the operator's configuration sets explicitly (section 12). The phone's inbox relies on it: it reads its gift wraps 500 at a time and takes an answer the relay ended with EOSE holding fewer than 500 as the whole window, so a lower limit would pass over browser saves.

### 3.2 Blob store: Blossom endpoints inside `keflid`

The obvious candidate is hzrd149/blossom-server, MIT licensed, implementing BUD-01, 02, 04, 05, 06, 08, 09 and 11 ([README](https://github.com/hzrd149/blossom-server)). Its configuration offers `upload.maxSize`, `upload.requirePubkeyInRule`, per-pubkey retention rules and a `list.enabled` switch, but no per-pubkey storage quota ([config.example.yml](https://github.com/hzrd149/blossom-server/blob/master/config.example.yml)). The contract makes the quota a property of `/register` (50 MB per library since contract 1.12, where it was 200 MB, with a limit on a day's uploads beside it), and enforcing them from outside blossom-server would mean a preflight in the proxy on every upload and two databases to reconcile on deletion. The surface the app needs is small: `PUT /upload`, `HEAD /upload` (BUD-06 preflight), `GET` and `HEAD /<sha256>`, `DELETE /<sha256>`, and an owner-only `GET /list/<pubkey>`. That is a few hundred lines of Go over a directory of files, so `keflid` implements it directly, with blossom-server behind Caddy as the fallback if the implementation stalls in week 1.

Uploads require a kind 24242 authorisation event with `t = upload`, an `x` tag matching the body's sha256 and a future `expiration`, as BUD-02 specifies, from a registered pubkey. The server checks `bytes_used + content_length <= quota_bytes`, each blob counted once per library whether the user or one of their devices uploaded it, and, from contract 1.12, that the library's uploads add no more than 20 MB (20,971,520 bytes) to the disk in any 24 hours: an upload of a blob already stored, for any library, adds nothing, and the count comes from a log of uploads pruned past 24 hours, so a delete gives none of the day back. Each blob counts for its size, and never less than 4,096 bytes, the disk block its file takes however small it is (`store.Cost`), against both the quota and the day: a library at the default quota holds at most 12,800 blobs and adds at most 5,120 a day, and a text of 4,096 bytes or more counts exactly its size. Every refusal carries its reason in `X-Reason` and the body `{ "v": 1, "error": <reason> }`; the two limits' 413s, `quota` and `daily` (`quota` when an upload would pass both), add the library's `quota`, `used`, `daily` and `today` in bytes (contract 5). Blobs are capped at 8 MB, a larger one answered 413 `too_large`, and accepted only as `application/octet-stream`, since the body is ciphertext; the ceiling stops the store being used for anything except article text. Files live at `blobs/<first two hex>/<sha256>` with ownership rows `(sha256, pubkey, size, created_at)`, many-to-one so deletion behaves. Each upload is written to a temporary file in its blob's folder and synced to the disk, renamed into place and the folder synced, all before its ownership row is written and the upload answered, so a power cut can't leave a recorded blob short, empty or missing; a folder made for a blob is synced into the folder above it, and a copy of a blob already on the disk is checked against its hash and not written. A failed sync is answered 500 and leaves nothing behind; a filesystem that can't sync folders at all (EINVAL, ENOTSUP) takes the upload with its file synced. `GET /<sha256>` needs no authentication, matching Blossom's model: the address is 256 bits of hash and the content is AES-256-GCM ciphertext whose key lives only inside the user's kind 30979 event. There is no landing page or directory listing, `/list/<pubkey>` answers only to a `t = list` event from that pubkey, and `DELETE` with a `t = delete` event removes the caller's ownership row, or for a user every row of the blob counted against them, their devices' inbox uploads included (contract 1.12), unlinks the file when no owner remains, and decrements quota use.

### 3.3 HTTP API

`keflid` serves `api.<domain>`. Every request except NIP-05 carries NIP-98: an `Authorization: Nostr <base64 event>` header holding a kind 27235 event with `u` and `method` tags and, for bodies, a `payload` tag ([NIP-98](https://github.com/nostr-protocol/nips/blob/master/98.md)). Validation: signature verifies; kind is 27235; `created_at` within 60 seconds of server time; `u` equals the full request URL as Caddy received it, scheme and host included; `method` matches; for POST and DELETE the `payload` tag equals the sha256 of the raw body (the empty body still hashes and the tag is still required); the event id has not been seen in the last 120 seconds. Failures answer 401 `{ "error": "auth", "reason": "<one word>" }`. Per-pubkey limits are 60 requests per minute overall, 6 per minute for `POST /audio` calls carrying `text`, 12 per minute for status polls, with 429 and `Retry-After` above them.

`POST /register` inserts the pubkey into `accounts` with `quota_bytes = 52428800` (50 MB from contract 1.12; it was 209715200) and returns 200 `{ "v": 1, "quota", "used" }` with the account's own quota and use, whether or not the row existed. Nothing beyond a valid signature is asked for in v1; abuse is handled by quota, the day's limit and account disabling (section 5). `GET /account` (contract 1.12), from a registered user, returns `{ "v": 1, "quota", "used", "daily", "today" }` in bytes: the account's quota and what its blobs take of it, the most its uploads may add in any 24 hours (20,971,520 bytes), and what they added to the disk in the last 24; any other key, a disabled library's included, gets 403 `not_registered`, though `POST /register` still answers a disabled library 200 with its figures.

`POST /audio` takes `{ "v": 1, "text_hash", "voice", "model", "text"? }`. `voice` must be in the served list and `model` must equal `kokoro-82m-v1.0`, else 400. The lookup key is `(text_hash, voice, model)`. An existing `audio` row with its file present answers `ready` with URL, duration and timestamps URL and touches `last_access`. A job in `queued` or `running` answers `queued` with the current ETA whether or not `text` was sent, so a client racing itself never enqueues twice. Nothing found and no `text` answers `miss`. With `text`, the server hashes the exact bytes; mismatch is 400 `{ "error": "hash_mismatch" }`, and text over 120,000 characters (about 20,000 words, over two hours of audio) is 413 `{ "error": "too_long", "max_chars": 120000 }`, a contract addition flagged in section 9. Otherwise the plaintext goes to tmpfs at `/run/kefli/jobs/<job id>/text.md`, a job row is inserted, and the answer is `{ "status": "queued", "eta_seconds": N }` where N sums the estimated generation time of every job ahead plus this one, using the real-time factor measured over the last twenty jobs.

`GET /audio/status/<text_hash>/<voice>/<model>` answers the same three shapes plus `{ "status": "failed", "reason": "worker" | "lost" }` when generation failed twice or the plaintext was lost to a reboot; a client treats `failed` as `miss` and may resend. `GET /audio/<id>` streams `audio/ogg` with byte-range support so the phone can seek, requires NIP-98 from any registered pubkey, and refreshes `last_access`; `words.json` follows the same rules. Ids are 20 random bytes in unpadded base32, stored on the `audio` row and derivable no other way.

`DELETE /account` runs one transaction: delete every blob ownership row for the pubkey and unlink files with no remaining owner, delete the pubkey's `audio_request` rows and any audio requested only by it, drop its queued jobs and wipe their tmpfs directories, then delete the account row with its authorised devices and its uploads log, so a key registered again starts a fresh day with none of its blobs left; the relay plugin notices within five seconds. Events already on the relay are the user's own to remove with kind 5 from the phone, per contract 4.7. The answer is 200 `{ "v": 1, "deleted": { "blobs": n, "audio": m } }`, or `{ "v": 1, "deleted": { "blobs": n } }` as built without server audio (section 12), and the call is idempotent. Word timestamps are covered in 3.4 and NIP-05 in 3.7.

### 3.4 TTS worker: Kokoro-FastAPI

The worker is remsky/Kokoro-FastAPI, Apache 2.0, running the CPU Docker image with the Apache 2.0 Kokoro-82M weights; the image includes espeak-ng (GPL-3.0) as a fallback phonemiser, which is fine server-side since nothing is redistributed ([Kokoro-FastAPI README](https://github.com/remsky/Kokoro-FastAPI)). Its `/dev/captioned_speech` endpoint returns audio with word-level start and end times, and it emits Opus directly, so no separate encoder is needed. The container binds to `127.0.0.1:8880` only. `keflid` runs one worker goroutine per allocated CPU worker (section 4); each pulls the oldest `queued` job, marks it `running` with a heartbeat, and drives the container.

Before text reaches Kokoro, `keflid` converts Markdown to speakable text with a deterministic pass that records, for every emitted token, its character offset in the original Markdown: headings lose their hashes, emphasis markers go, link text stays and the URL goes, images are dropped, code blocks become the phrase "code omitted", list markers become pauses, tables are read row by row. The flattened text is sent in paragraphs of at most 2,000 characters, each response's timestamps shifted by the running duration. Kokoro's words are aligned to the token array by a forward-only matcher that normalises case and punctuation and tolerates splits or merges within a window of three; when it loses sync it skips to the next paragraph boundary, where both sides are known to coincide, which is the re-anchoring the project plan calls for. The output is `[{ "w", "s", "e", "o" }, …]` with `o` the Markdown offset; unaligned words carry the last aligned offset so highlights never jump backwards. Chunks are concatenated into one Ogg Opus file at 48 kbps mono, 24 kHz.

Kokoro-FastAPI's README reports 35x to 100x real time on an RTX 4060 Ti and about 3.5 seconds to first token on an older i7; an independent benchmark on four EPYC 7763 cores measured a mean RTF of 0.47 (PyTorch) and 0.51 (ONNX), so one wall second yields about two seconds of audio ([heyneo benchmark](https://heyneo.com/blog/kokoro-tts-vs-supertonic-3-tts), [Kokoro-FastAPI README](https://github.com/remsky/Kokoro-FastAPI)). Section 4 sizes on RTF 0.5 per four dedicated cores and treats a GPU as the scaling step.

On completion `keflid` writes audio and timestamps to `audio/<id>/`, inserts the `audio` row and an `audio_request` row `(audio id, requesting pubkey)`, deletes the job and shreds the tmpfs directory. On failure it retries once after thirty seconds; a second failure marks the job `failed`, wipes tmpfs, and the status endpoint reports it for ten minutes. After a `keflid` restart, `running` jobs with a stale heartbeat return to `queued` when their tmpfs text survives (a process restart) and become `failed: lost` when it does not (a host reboot).

### 3.5 Queue and cache

The queue is the `jobs` table in SQLite, ordered by `created_at`, one row per `(text_hash, voice, model)`. There is no external broker; the largest planned size needs a few jobs per minute, and SQLite in WAL mode with workers polling every second handles that. Order is first come first served with one exception: a pubkey that already has a running job waits behind everyone else's first job, so one user's "Play all" cannot monopolise the workers.

The cache is the `audio` table plus files. An hourly sweeper removes rows whose `last_access` is older than 90 days, the contract's expiry, and also enforces a size ceiling (per tier in section 4) by evicting least-recently-accessed entries; the ceiling is flagged in section 9 because the contract names only the age. Entries are shared across users, which is the point of the fixture-locked Markdown conversion. The privacy consequence is that any registered user who knows a `text_hash` can fetch that audio; since the hash is of the full plaintext, knowing it means already having the text, so the sharing reveals only that someone generated it before.

### 3.6 Reverse proxy and TLS

Caddy 2 (Apache 2.0) terminates TLS for the three hostnames with automatic Let's Encrypt certificates, HTTP/2, TLS 1.2 minimum and one-year HSTS. It proxies `relay.<domain>` to strfry on `127.0.0.1:7777` with websocket upgrade, and `api.<domain>` and `blossom.<domain>` to `keflid` on a Unix socket with a 9 MB body limit on the upload path and 1 MB elsewhere. Per-IP limits in Caddy are coarse (300 API requests, 60 uploads and 200 new websocket connections per minute); the per-pubkey limits in `keflid` and the plugin are the fine ones. nftables allows 22 (key only, from a known IP list), 80 and 443 inbound and nothing else, and Docker runs with `iptables: false` so it cannot punch its own holes.

### 3.7 NIP-05

`GET /.well-known/nostr.json?name=<n>` is served by `keflid` on `api.<domain>` and, through a Caddy rewrite, on the apex. In v1 the only name is `_`, resolving to the operator's pubkey with the operator relay in `relays`, plus any names in a static YAML file, with `Access-Control-Allow-Origin: *` as the NIP requires. The `accounts` table carries a nullable `nip05_name` column so the v2 registry is a migration rather than a redesign; nothing writes it in v1.

### 3.8 Backups

Three things are backed up nightly: the strfry database via `strfry export` to gzipped JSONL, the `keflid` SQLite database via the online backup API, and the blob directory. They go to a Hetzner Storage Box over SFTP using restic (BSD-2-Clause), encrypted client-side with a key held on the VPS and in the operator's password manager, retained as 14 daily and 8 weekly snapshots. The audio cache is excluded because the phones can regenerate it. Each job pings a healthchecks endpoint; a missed ping alerts. Restore is rehearsed in weeks 2 and 5 by rebuilding staging from a production snapshot with the playbook and confirming a fixture pubkey can read its events and fetch its blob. After the relay is restored from a backup onto its own box, remove `/var/lib/strfry/relay-sweep.last`, so the next sweep looks at every key on the gone list again.

### 3.9 Monitoring

Prometheus, node_exporter and Alertmanager run on the host; `keflid` exposes `/metrics` on its Unix socket and a tiny exporter reads `strfry info`. Alerts go over ntfy and email for: disk above 80 per cent, cache above ceiling for an hour, queue depth above 50 or oldest job older than 20 minutes, stale worker heartbeat, TLS certificate under 14 days, missed backup ping, 5xx above 1 per cent over five minutes, and host unreachable from an Uptime Kuma instance on a different provider that probes NIP-11, the API health path and a Blossom HEAD every minute. The dashboard is one page: requests, queue, cache size, blob store size, disk.

## 4. VPS requirements and cost

Assumptions, stated so they can be corrected once real numbers arrive: a user saves 30 articles a month and keeps them; an encrypted text blob is 30 KB; a kind 30979 event is 1.5 KB and strfry keeps one per `d`; a save request wrap averages 200 KB and lives at most 30 days; 20 per cent of users listen on a given day, two articles each; an article averages 2,450 words, 16 minutes at 150 words per minute; 48 kbps Opus is 6 KB per second, 0.36 MB per minute, 5.9 MB per article (64 kbps works out at 0.48 MB per minute, and the sizing rounds to 0.5 MB per minute to stay conservative); 15 per cent of audio requests hit the cache, because read-later libraries overlap little; Kokoro on four dedicated cores runs at RTF 0.5, so 16 minutes of audio costs 8 minutes of four-core time.

| Quantity | 100 users | 1,000 users | 10,000 users |
|---|---|---|---|
| Blob growth per month (30 saves × 30 KB) | 90 MB | 900 MB | 9 GB |
| Blob store after 12 months | 1.1 GB | 10.8 GB | 108 GB |
| Relay: 30979 events after 12 months (3,600 × 1.5 KB per user-year) | 5 MB | 54 MB | 540 MB |
| Relay: live 1059 wraps (30 saves × 200 KB, 30-day window) | 600 MB | 6 GB | 60 GB |
| Audio requests per day (20% × 2) | 40 | 400 | 4,000 |
| Audio generated per day after 15% hits | 34 articles, 9.1 h | 340 articles, 91 h | 3,400 articles, 907 h |
| Four-core CPU hours per day at RTF 0.5 | 4.5 h | 45 h | 453 h |
| Cache growth per day at 0.5 MB/min | 0.27 GB | 2.7 GB | 27 GB |
| Cache at 90 days, uncapped | 25 GB | 245 GB | 2.4 TB |
| Cache ceiling set | 30 GB | 200 GB | 1 TB |

Two conclusions fall out. Live gift wraps dominate relay storage, which is why section 6 deletes them at 30 days and why the extension should keep captured HTML small. And CPU synthesis stops fitting at around a thousand users: 45 four-core hours a day means two four-core boxes running flat out, ten thousand users would need fifty, whereas one mid-range GPU at RTF 0.02 covers 907 audio hours in about 18 GPU hours. The scaling trigger is the queue: when daily generation hours exceed 60 per cent of available four-core hours for a week, the worker moves to a GPU host.

## 5. Security and abuse

The server holds nothing that reads as an article: event content is NIP-44 ciphertext, blobs are AES-GCM ciphertext, and the only plaintext is the TTS job text, which lives on tmpfs for the duration of the job and is overwritten with zeros before unlinking. Swap is disabled on the host so tmpfs pages cannot land on disk. The Kokoro container has no network route except the loopback and no volume mounts; text goes in over HTTP and audio comes back the same way.

Authentication is NIP-98 everywhere on the API, Blossom kind 24242 auth on the blob store, and NIP-42 on the relay, each validated with a freshness window and replay cache. The three per-pubkey rate limits (relay writes, API calls, uploads) and the two per-IP limits (Caddy, plugin) bound the cost a single key or address can impose. Quota bounds storage per key to 50 MB, and the day's limit bounds how fast one key fills it to 20 MB in 24 hours (contract 1.12); the number of keys is unbounded in v1 because registration is free, so the defence against someone registering ten thousand keys to get 500 GB is a per-IP registration limit of 5 per day (an IPv6 client counted by its /56), 20 a day per IPv6 /48, a limit of 200 new accounts an hour from everyone together, logged once when it is reached in place of the alert first planned (section 12), and an operator command `keflictl disable <pubkey>` that removes a key from the allowlist and freezes its blobs without deleting them. Uploads are ciphertext only, 8 MB maximum, MIME fixed, and never served with a content type a browser would execute. Audio requests are the expensive operation, so a single pubkey may have at most three jobs queued, and text-bearing calls are capped at six per minute; a pubkey that submits text whose hash never matches three times in an hour is rate-limited for an hour.

Log policy: Caddy's access log is configured with a custom format that records timestamp, method, path with the first segment only, status, bytes and latency, and omits query strings, the `Authorization` header, request bodies and the referrer. `keflid` logs a 12-hex-character truncated hash of the pubkey rather than the pubkey, never logs `text_hash` at the level shipped in production, and never logs any request body. strfry's log is left at its default, which prints event ids and kinds and no content. Nothing in any log is a URL, a title, or a piece of text a user saved. Logs rotate at seven days. The SQLite database contains pubkeys, quotas, blob hashes, text hashes and audio ids; it never contains a URL.

Host hardening is the usual: unattended security upgrades, SSH keys only, a non-root service user per process, systemd sandboxing (`ProtectSystem=strict`, `PrivateTmp`, `NoNewPrivileges`) for `keflid` and strfry, Docker rootless for the worker, and nftables as described. The operator's key for NIP-05 and relay NIP-11 metadata is held offline; nothing on the server signs anything.

## 6. Data retention and deletion

Blobs live until their owner deletes them, through Blossom `DELETE` or `DELETE /account`. Relay events of the restricted kinds live until a kind 5 from the author or the retention script removes them. The retention script runs nightly: it deletes kind 1059 events older than 30 days (the phone deletes them within seconds of processing under normal conditions, so anything older is orphaned), deletes kind 30979 events whose author is no longer in `accounts` and has been absent for 30 days, keeps ephemeral and replaceable kinds per their NIP semantics, and trims public kinds (anything other than 30979, 1059, 5, 0, 3, 10002, 10013, 10003, 30003, 30023, 39701) to 90 days so the relay does not become a free archive for unrelated traffic. It is a `strfry delete --filter` invocation wrapped in a script that logs counts only. Audio cache entries expire at 90 days without access or earlier under the size ceiling. Job plaintext is deleted at job completion, at second failure, or by the ten-minute sweep for any tmpfs directory with no job row. Backups follow their 14-daily, 8-weekly retention, which means a deleted account's blobs can persist in encrypted backups for up to eight weeks; the app's deletion dialog already says copies may persist, and the privacy policy the project engineer writes for the stores should say so explicitly.

`DELETE /account` is described in 3.3. The one thing it cannot do is delete the user's events from the relay, because those are the user's signed data and the contract has the phone publish kind 5 for them; the retention rule for de-registered authors closes the gap after 30 days for users whose phone never got the chance.

(2) `eta_seconds: 40` in the example is unreachable on CPU for a typical article, which takes eight minutes on four cores; clients should display the real ETA and the contract example should change. (3) A 413 `too_long` error and a `failed` status are added to the audio API. (4) The cache is capped by size as well as by the 90-day age rule. ## 10. Risks

Kokoro CPU throughput is the largest. If the real RTF on Hetzner's EPYC-based dedicated vCPUs is worse than 0.5, the launch box still copes with a hundred users, but the thousand-user step moves to a GPU earlier and costs more; the mitigation is measuring RTF in week 3 and revising section 4 before beta. Timestamp alignment on articles with heavy Markdown (tables, code, nested lists) may drift; the tokeniser and matcher are unit-tested against all twenty fixtures and paragraph re-anchoring bounds the damage, and the system voice remains the reference implementation as the plan says. Implementing Blossom in-house risks a subtle BUD incompatibility with third-party clients the user may point at the server later; the tests use the reference `blossom-client-sdk` behaviour recorded as fixtures, and blossom-server stays available as a drop-in behind Caddy if a compatibility problem appears. Gift-wrap volume on the relay could surprise if the extension does not cap HTML. SQLite as the single store is a ceiling somewhere above ten thousand users; the schema is plain enough to move to Postgres, and the trigger is write contention showing up as `SQLITE_BUSY` in metrics. A provider rejecting a nostr relay on its terms is possible; the playbook targets any Debian host and the DNS TTL is kept at five minutes. Finally, an operator-side compromise exposes pubkeys, hashes and ciphertext but no readable content, which is the property the whole design is built to preserve.

## 11. Definition of done

Production and staging are built from the same playbook with no manual steps; every contract test row in section 7 passes on staging and the same suite passes on production with fixture keys; the failure drills have been run and their runbooks written; backups restore on staging to a working service; monitoring alerts have each fired at least once in a drill; no log line on the host contains a URL, a title or article text, verified by a grep audit on a week of logs; the load test passes at ten times the launch rate; `DELETE /account` leaves no file, row or allowlist entry for the pubkey; the server can be stopped for an hour during beta with Richard's phone losing nothing but audio generation; and the cost report in week 7 shows the real per-user figures next to the assumptions in section 4.

## 12. Build notes (October 2026)

The first build is in `server/api`, against contract v1.5 (sections 3.2, 5 and 6) rather than v1.0, and without server audio, which v1 doesn't have (flow decision 22): no Kokoro worker, queue or audio cache, and no `/audio` routes. It is three Go programs over one SQLite database, and a fourth that forwards mail, built and tested in Docker's `golang:1.26` image (`make -C server/api test build`), so the host needs only Docker; the binaries are static, since strfry's image is Alpine.

- **`keflid`** serves the API (contract 6: `defaults.json`, `/register`, `/devices`, both pairing offers, `DELETE /account`, NIP-05) and the Blossom store (contract 5) on two addresses, one per hostname behind Caddy. NIP-98 is checked as 3.3 says, including a replay cache of event ids. Blossom is in-house as 3.2 planned: uploads by a registered user or an authorised device key, both counted against the user's quota with each blob once (200 MB as first built; contract 1.12 makes it 50 MB with a day's limit, below), a device's uploads kept as inbox blobs for 14 days, a blob kept until its last owner deletes it, served to anyone by hash with byte ranges, and nothing listed. Every answer carries CORS (extension spec 15). Limits: 60 calls a minute per key, offers 30 an hour per key and per address, new registrations 5 a day per address; the limits on everyone together that the pre-release audit added, and those the hardening added after it, are at the end of this section.
- **`kefli-writepolicy`** is strfry's write-policy plugin, with the rules of contract 3.2: a registered author writes, 60 events a minute; a kind 1059 from any key is taken when its one `p` tag names a registered user or an authorised device; a kind 5 from an unregistered key only when every event it names is a wrap of its own that the relay holds (the extension's Undo); kinds 30078 and 1059 at most 16 KB, strfry holding the rest to 64 KB. Two things strfry doesn't do itself are the plugin's: it keeps its own record of the wraps the relay holds, for the kind 5 rule, and when a user's kind 5 names wraps addressed to that user (the phone deleting what it has collected) it removes them with `strfry delete`, since NIP-09 alone deletes only the author's events. The allowlist is a snapshot refreshed every five seconds, as 3.1 planned, but a key the snapshot lacks is asked of the database before it is refused, so a user's first save straight after `/register` isn't turned away.
- **`keflictl`** registers, disables and re-enables keys (section 5), sets one library's quota (`quota <pubkey|npub> <MB>`, flow decision 117) and lists the removed keys whose time has come for the relay's sweep (`gone <days> [<since>]`).
- **`kefli-mailfwd`** forwards mail for `privacy@kefli.app`, which Resend receives, to the company inbox, and opens no database (`server/deploy/README.md`, Mail).

Hardening after the pre-release audit (13 and 14 October 2026, findings F8, F9, F44, F45, F48 and F49; contract 1.11, section 11.2):

- **Addresses by block.** The limiter lives in `internal/limit`, and `limit.Addr` counts an IPv6 client by its /64, so one line can't pass as 2^64 addresses: keflid's offer limits and the write policy's per-address limits count that way, and registrations by the /56 a home line is given.
- **Limits on everyone together.** After 100 phone-offer lookups that find nothing in five minutes, from all callers, every lookup answers 429 until the window ends, so a guesser gets at most two in ten thousand codes against one offer. One block of addresses, an IPv4 /24 or an IPv6 /48 (`limit.Block`), may spend only 10 of them (`MaxBlockMisses`), its own lookups waiting past that, so holding everyone's up takes ten blocks in every five minutes rather than one free tunnel. New accounts are capped at 200 an hour (`Config.MaxRegistrations`), counted from `accounts.created_at` so a restart keeps the count, with one error line in the journal when the cap is reached, and at 20 a day per IPv6 /48 (`MaxBlockRegistrations`); IPv4 has no block limit, since a carrier's shared addresses put many people in one /24. Both shared counts trade availability for a bound, as contract sections 2 and 6 say; the per-offer verifier that would end the lookup's shared count (an offer deleted after a few wrong codes) needs a change to the lookup and waits for a later contract version. Blossom answers 507 to an upload that would leave less than `KEFLID_MIN_FREE_MB` free (4096 by default, `kefli_min_free_mb` in the playbook).
- **Gift wraps** (`kefli-writepolicy`). A wrap from an author who isn't registered counts first against its sender's address (240 an hour), then against that recipient from that address (120 an hour), then against the recipient from everyone (1,200 an hour), so a sender filling one recipient's allowance spends its own. A wrap sent on a connection AUTHed as the recipient, a device of the recipient or the user who owns the recipient device counts only against that key's 60 a minute; the extension AUTHs as its device key to publish, so a flood from elsewhere can't hold up a browser's saves. The policy's old reset of every count past 200,000 keys gives way to the shared limiter, which drops expired windows only when its map has doubled since its last pass, and `offerAllowed` checks the address before the key.
- **What grows.** `DELETE /account` records a removed key only when it had an account, and `Store.Sweep` forgets removed keys after 60 days (`GoneLife`: the relay sweep's 30-day drop plus a month for missed nights). Each sweep looks only at the keys whose time has come since the last one: `relay-sweep` keeps when its last complete run began in `/var/lib/strfry/relay-sweep.last` and asks `keflictl gone <days> <since>` for the keys removed, or gone 30 days, since then, less two days, so each key is swept for on two or three nights; with nothing kept, as on a new box or once the file is removed after the relay is restored from a backup, it sweeps for the whole list. `policy.PruneWraps` forgets, at start and every hour (`PruneEvery`), wraps past 31 days and wraps addressed to keys removed since its last prune began, less that hour (`PruneOverlap`), a time it keeps in `wraps.db`. Each looks back at least as far as the time between two of its runs, so a clock put back, which leaves the time kept ahead of the keys removed after it, puts off a key's sweep or prune by one run at most. The gone list is indexed by `at`, so both reads are a range.
- **`POST /devices` asks for the device's consent** (F44). It takes a device key only with the device's own proof from its pairing offer, used once within six minutes of its making, or in a move a release signed in the last 60 seconds by the user who holds the device; a request with neither is 400 `proof: missing`, which only a build from before contract 1.11 sends, and a caller already holding the device gets 200, for a proof or release of any age whose signature holds, a proof or release within its time being used up all the same so nobody else who saw the code can take the device with it. Proof and release ids are kept with the request ids in `used_auth`. `RemoveDevice` deletes only the inbox blobs counted against the caller. The dev stand-in (`server/dev/api.mjs`) and the staging contract tests follow.
- **Caddy's admin API** listens only on a socket that root and the `caddy` user can open (F49), and **backups** gain the Storage Box's own read-only snapshots, which only the Console or its API can delete, the backup key included, as Richard confirmed in the Console on 15 October 2026 (F48); both are in `server/deploy/README.md`, and the snapshots are on.

Fair use (14 October 2026, flow decision 117; contract 1.12, section 11.1), built the same day:

- **The two limits.** `store.DefaultQuota` is 50 MB (52,428,800 bytes), and `keflictl quota <pubkey|npub> <MB>` sets one library's quota, in whole megabytes of 1,048,576 bytes and 0 included, for a key that has an account; the library keeps that figure from then on. Beside it, a library's uploads may add at most 20 MB (20,971,520 bytes) to the disk in any 24 hours: each upload of a blob the server doesn't already store, for anyone, is logged with its account, size and time, and no hash, and the log is pruned past 24 hours, by the hourly sweep and for each library as its figures are read, so a delete gives none of the day back and a move's re-uploads cost nothing. The day's 20 MB is the same for every library; a paid tier raising it needs a per-library figure like the quota's, which `GET /account`'s `daily` already reports. An account left above its quota by the lowering keeps every blob it holds, and its uploads get 413 `quota` until deletes bring it back within it.
- **The schema's steps.** keflid's database carries a schema version (`PRAGMA user_version`): each step runs once, in the transaction that records it, and keflid or keflictl refuses a database newer than itself (the write policy only reads it). Step 1 lowers once every account still at 200 MB, any other figure (a paid tier's, later) kept as it is; step 2 counts every blob and upload recorded before as at least 4,096 bytes (3.2); step 3 keeps each library's use and day as two running totals on its account row, which triggers keep on every insert and delete, and indexes the blobs by library, so a library's figures take the same few lookups to read whatever it holds, where summing its rows on every upload let one full library's preflights hold keflid's one database connection, other users' uploads taking 4.6 s. The lowering runs at the first open by a 1.12 binary, keflid or keflictl, and a deploy copies keflictl before it restarts keflid, so a library the old keflid registers after keflictl's first open keeps 200 MB; `server/deploy/README.md` says how to find and lower it.
- **What counts.** A blob counts as stored while any owner row holds it, an inbox row past its 14 days that the hourly sweep hasn't removed included, so an upload of it costs no part of a day. A browser's capture stops counting against the quota the moment its 14 days are up; its file stays until the hourly sweep of files.
- **The answers.** Blossom's refusals carry `X-Reason` and `{"v":1,"error":<reason>}`; the two limits' 413s, `quota` and `daily`, add the library's figures (3.2), and a blob over 8 MB is 413 `too_large`, without them. Blossom answers a refusal its client acts on (413 `quota`, `daily` or `too_large`, and 507) only once it has read the rest of the body, up to the 9 MB Caddy lets through, unless the client sent `Expect: 100-continue`: the phone's OkHttp 4.9.2 sends a whole body before it reads, and got a broken pipe or a reset stream in place of a refusal sent while more than 256 KB was unread. The limits are checked again at commit under the upload lock, and a file is unlinked only once a check under the same lock finds no owner. An owner is recorded only while its account, and for an inbox blob its browser, still stands: `DELETE /account` runs in one transaction, and an upload's record checks the account last in its own, so an upload landing as the account goes is deleted with it or refused with 401 `not_registered`, its file taken back. `POST /register` answers the account's own quota and use, and `GET /account` its four figures (3.3).
- **Deleting a browser's capture.** A user's `DELETE` of a blob removes every ownership row counted against them, their devices' inbox uploads included, so the phone can delete a capture once it has taken the save; a device key's removes only its own. `DELETE /account` deletes the library's uploads log with it (3.3).
- **The stand-in and the tests.** `server/dev/api.mjs` answers `POST /register`'s and `GET /account`'s figures and `not_registered` as keflid does; the dev stack's Blossom server is hzrd149's, with no quota or day, so a real 413 `quota` or `daily` comes only from keflid (`server/staging`). `server/staging/contract.ts` has section 7's new rows. A 507 is answered as before; from 1.12 the phone sends the save without its text while it retries the upload as any 5xx, and the extension retries it as any 5xx.

After the hardening (14 and 15 October 2026; flow decision 118). Every part of the server a client reaches was attacked, the API, the blob store, the relay and the mail forwarder among them, and these limits came of it. Each refusal lands in a retry or failure state the clients already have: 429, 503, 507 and `rate-limited` are sent again later by both.

- **The API's requests.** Every signed request, which is all but `GET /defaults.json`, NIP-05's and the health check, counts against its address, an IPv6 client by its /64, at 600 a minute, and against its IPv6 /48 at 3,000 a minute, before anything is read or verified (`MaxAddressCalls`, `MaxBlockCalls`), since any key may call `DELETE /account` or `DELETE /devices`; the phone calls the API a handful of times in its life. Offers are held to 120 an hour per IPv6 /48, both kinds together, beside the 30 per /64 and per key, and to 10,000 held at once from everyone (`DefaultMaxOffers`), each at most 8 KB, with 429 `rate` and `Retry-After` past either. A library holds at most 64 browsers at once (`MaxDevices`), past which `POST /devices` gets 403 `devices: too_many`, and connects at most 128 in a day (`MaxDeviceAdds`), past which it gets 429 `rate`; neither uses up the proof or release. A body over 64 KB is 413 `too_large`, and keflid holds a request's headers to 64 KB, with 10 s to send them, and its body to the guard's pace (below).
- **The blob store's requests.** Uploads, preflights and deletes count against the address that sends them, an IPv6 address by its /64 and its /48, before anything is read: 6,000 a minute from an address and 30,000 from an IPv6 /48. A blob's GETs and HEADs count against no address, since a mirror fetches every user's texts from one address and many people can share one carrier address: each blob is sent at most 16 times an hour, a GET or a HEAD each, a range counted as one, whoever asks (`MaxBlobSends`); a GET for several ranges gets the whole blob, and a request for a blob whose file isn't on the disk is answered 404 from the disk alone. A library's uploads in flight at once number at most 8 and come to at most a day's 20 MB (`MaxInFlight`). Past any of these a request gets 429 `rate` with `Retry-After`. An upload that would leave less than `KEFLID_MIN_FREE_MB` free, the bytes of uploads in flight counted, or less than a tenth of the disk's files free, gets 507. A body for a blob the server already stores is checked against its hash and not written again, unless the file the server holds isn't the body's size, as a power cut can leave it, when the body is written in its place; if the blob's last owner deletes it while the body arrives, the upload gets 500 and is written when it is sent again.
- **Requests held.** One guard stands in front of both of keflid's servers (`internal/guard`). An address, an IPv4 address or an IPv6 /64, has at most 32 requests in flight at once on the two together, reads included, and an IPv6 /48 at most 128 (`guard.MaxInFlight`, `guard.MaxBlockInFlight`); one more gets 429 `rate` with `Retry-After`. A body on anything but a POST or a PUT gets 400 `body`. A body that is read keeps a pace (`guard.Default`): nothing is asked of it in its first 30 seconds, after them it must bring 8 KB for every second, and no read waits a minute for a byte; behind it, the route answers 503 `timeout` with `Retry-After`. The pace takes the place of the server's two-minute `ReadTimeout`, which cut an 8 MB upload on any link slower than about 550 kbps, and an answer has two minutes from its own start. An answer a route writes before its body is in closes the connection: the rest of the body is read for a second at most, or, with more than 256 KB of it to come, the connection is half-closed for half a second before it goes, so the answer reaches Caddy ahead of the reset (the guard puts the server's own body back on the request after the route, which Go 1.26's server looks for). The guard's own refusals, past the count or for a body no route reads, close at once, so as to keep nothing of a refused request, and through Caddy such a refusal to a body of about 100 to 250 KB can come back as a 502, which the phone and the extension send again as they do a 429. Caddy gives every request's body on 443 20 minutes (`read_body`); its own server on port 80, there only to redirect, isn't held to it, and answers its redirect at once but keeps the connection while a body trickles in. `test.sh` sends 30 early refusals of 8 MB uploads through Caddy and expects every one.
- **The relay.** While the disk under strfry's database has less than `kefli_relay_min_free_mb` free (2 GB, below the blob store's 4 GB, so uploads stop first), the write policy answers every new event `rate-limited: the relay is nearly full, try again later` (`policy/floor.go`); reads go on. strfry keeps no compression window for each connection (`relay.compression.slidingWindow = false`), which held about 130 KB a connection, and the firewall holds one client to 512 connections at once.
- **strfry's answers.** `strfry.conf.j2` sets `relay.maxFilterLimit` to 500, strfry's own default, since the phone's inbox reads its wraps 500 at a time and takes an answer the relay ended with EOSE holding fewer than 500 as the whole window, and a later strfry could change the default. strfry passes over a key in the wrong block without a word, so beside the line and the `max_limit` of 500 in the relay's NIP-11, the deploy test runs the deployed file with that figure alone changed, on a port and a database of its own, and reads the new figure back; `apps/mobile/test/strfryLimit.test.ts` holds the template's figure at the inbox's page or more on every push.
- **The mail forwarder** forwards one message at a time, holding it whole in memory, and a webhook that waits 10 s for the one before it is answered 503, for Resend to send again later; it gives a request 30 s and its headers 64 KB, and systemd holds it to 768 MB with no swap.

Monitoring is built smaller than 3.9 (15 October 2026): an on-box health check every five minutes reporting to healthchecks.io, and an outside probe from GitHub's runners in place of Uptime Kuma; `server/deploy/README.md`, "Monitoring", has what each checks and what of 3.9 isn't built.
