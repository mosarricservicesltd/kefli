## 1. Goal and scope

The extension takes the page in front of the user and puts it in their phone's library. One click on the toolbar button, one keyboard shortcut, or one right-click on a link, and a small toast says "Saved to Kefli" with Undo. There is no popup list, no reader, no account. The extension never holds the user's private key; it holds the user's public key, a relay list and a pairing token, all learned from the phone during a QR handshake, and sends every save as a NIP-59 gift wrap that only the phone can open.

In scope for v1: a Manifest V3 WebExtension in TypeScript, one codebase producing a Chrome build (which also installs on Brave, Edge, Vivaldi and Arc) and a Firefox build; Readability capture on the live DOM; the pairing protocol; per-save gift wrap publish to the operator relay and the user's write relays; an offline queue with retry; Undo; context-menu "Save link"; a keyboard shortcut; an options page with pair, unpair and a read-only relay display; submission to the Chrome Web Store and addons.mozilla.org. Out of scope: Safari (Xcode wrapper and Apple review; v2), Firefox for Android, any reading or listing, any analytics, and any Markdown conversion in the extension, which contract 4.2 and 4.4 put on the phone so that one implementation produces the `text_hash` the audio cache depends on.

## 2. Architecture

The manifest is generated at build time from one template with two overlays. Shared keys: `manifest_version: 3`, `action` (toolbar button, "Save to Kefli"), `commands` (one shortcut, default `Alt+Shift+S`, remappable in both browsers), `permissions: ["activeTab", "scripting", "storage", "alarms", "contextMenus"]`, no `host_permissions`, `options_ui` opening in a tab, and the default MV3 content security policy with no remote sources. The Chrome overlay sets `background.service_worker` and `minimum_chrome_version: "116"`, the version from which an open WebSocket keeps the worker alive (section 6). The Firefox overlay sets `background.scripts` (an event page, since Firefox does not support `background.service_worker`: https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/background), `browser_specific_settings.gecko.id`, `strict_min_version: "121"`, and `gecko.data_collection_permissions: { "required": ["none"] }`, which addons.mozilla.org has required of new submissions since 3 November 2025 (https://blog.mozilla.org/addons/2025/10/23/data-collection-consent-changes-for-new-firefox-extensions/).

Four scripts make up the extension. The background (`bg.ts`) owns all state and all network: it handles the action click, the command, the context-menu click and messages from the other scripts, holds the WebSocket pool and runs the offline queue. The capture content script (`capture.ts`) is injected on demand with `chrome.scripting.executeScript` under `activeTab`, runs Readability against a clone of the live document, gathers metadata and returns one message. The toast content script (`toast.ts`) is injected the same way once the background has a result, renders a fixed-position card inside a closed shadow root so that page selectors cannot touch it, and relays Undo clicks back. A closed shadow root still inherits the page's inherited properties (colour, font, line height, letter spacing, text transform, alignment, direction) and its custom properties, so the toast declares all of these, its tokens and its colour scheme on its own root element inside the shadow root, not on `:host` and never from the page (build note in `docs/design/mockups/extension.html`). The options page (`options.ts`) draws the QR, shows connection state and relays, and offers Unpair. The action has no default popup: on pages where no toast can run, the background opens a small confirmation popup with `action.openPopup()` (Chrome 127+, Firefox) alongside the badge tick (flow decision 59). Both browsers expose `chrome.*` with promises, so the code uses that namespace directly and skips `webextension-polyfill`.

Message flow for a save, in text:

```
user clicks action / presses shortcut / picks "Save link"
  bg: read pairing from storage.local; if none -> open options page, stop
  bg -> tab: executeScript(capture.ts)               [activeTab grants access]
  capture: Readability(clone(document)).parse()
           + canonical, title, byline, site, lang, hero
  capture -> bg: { ok, meta, html }                   [html <= 512 KB]
  bg: build rumor kind 979 -> seal kind 13 -> wrap kind 1059 (fresh key)
  bg: enqueue { wrapId, wrap, ephemeralSk, createdAt, status: "pending" }
  bg -> tab: executeScript(toast.ts, { state: "saving" })
  bg: publish wrap to operator relay + user write relays over WebSocket
  relay -> bg: OK true                                 [first OK wins]
  bg -> toast: { state: "saved", wrapId }              -> "Saved to Kefli  Undo"
  toast -> bg: { undo, wrapId }   (within 8 s)         -> bg publishes kind 5 from ephemeralSk
  bg: after 8 s or on toast dismiss, discard ephemeralSk, mark queue entry "sent"
```

The background never parses HTML and never needs a DOM; Readability runs where the page already is. This keeps the service worker small and removes any need for an offscreen document in the save path.

## 3. Pairing protocol

The contract has the extension show a QR that the phone scans, and this document keeps that direction. The phone is the only device with a private key, so the phone must be the one that decides to trust a browser, and scanning is the gesture by which a user points a trusted device at something. If the phone showed the QR the extension would need a camera or a paste box, and the phone would still have to receive a message from the extension before anything could be verified.

The extension's side begins when the options page opens with no pairing stored. The background generates an ephemeral secp256k1 key pair `(esk, epk)` with nostr-tools, keeps `esk` in `chrome.storage.session` (memory only), opens a subscription on the operator relay for `{"kinds":[1059], "#p":[epk]}` after answering the NIP-42 challenge with `esk`, and renders a QR whose text is:

```
kefli://pair?v=1&k=<epk hex, 64 chars>&r=<percent-encoded wss URL>&e=<unix expiry>&n=<percent-encoded browser label>
```

`e` is issue time plus 300 seconds. `n` is a label such as "Chrome on a Linux laptop", built from `navigator.userAgentData` brand and platform, never a hostname or username. The QR is regenerated with a new key every five minutes while the page stays open, with a countdown beneath it and the line "Open Kefli on your phone, go to You, then Connect a browser, and scan this." It is drawn by the Nayuki `qrcodegen` TypeScript port (MIT, no dependencies, https://www.nayuki.io/page/qr-code-generator-library) into an SVG at error-correction level M.

The phone's side, which the Android and iOS engineers implement from this section, begins in the You tab under "Connect a browser". The phone scans, rejects the payload if `v` is unknown, `e` is past, `k` is not a valid x-only pubkey or `r` is not `wss://`, and shows a sheet: "Connect Chrome on a Linux laptop? It will be able to add pages to your library. It can't read anything." with Connect and Cancel. On Connect the phone builds a rumor of kind 978 (pairing acknowledgement, a new kind proposed for the contract) with content:

```
{ "v": 1,
  "pubkey": "<user's hex pubkey>",
  "relays": [ { "url": "wss://relay.<domain>", "read": true, "write": true }, ... ],
  "token": "<32 random bytes, hex>",
  "label": "<the n value echoed back>",
  "ack_for": "<epk>" }
```

`relays` is the operator relay followed by the user's NIP-65 write relays and any NIP-37 private relays. `token` is a per-browser secret the phone stores under "Connected browsers" with the label and date; every save rumor carries it (section 4), the phone drops kind 979 rumors whose token it does not recognise, and Disconnect on the phone forgets it. Without the token anyone who learns the user's npub could push pages into their library, since gift wraps to a pubkey are open to all senders. The phone seals the rumor with its own key to `epk`, wraps it with a fresh random key, tags the wrap `["p", epk]`, publishes it to the relay from `r`, and shows "Connected".

The extension unwraps with `esk`, checks that the seal's signing pubkey equals `pubkey` in the content (so a third party cannot answer on the user's behalf), that `ack_for` equals `epk`, and that the message arrived before `e`. On success it writes `{ v:1, pubkey, relays, token, label, pairedAt }` to `chrome.storage.local`, closes the subscription, discards `esk`, and replaces the QR with "Connected to your phone" and the date. The exchange takes one to three seconds. If the timer runs out the page shows "This code expired" and a "Show a new one" button. If AUTH is refused or the socket fails, the page shows "Can't reach the relay. Check your connection." and retries every ten seconds while visible. Nothing is stored on either side until the acknowledgement lands.

Unpair from the extension side is local: it deletes the pairing record, drains the queue, and shows the QR again; the options page adds "To stop this browser fully, also remove it under Connected browsers on your phone." Unpair from the phone side revokes the token, after which the phone ignores that browser's saves. The extension cannot learn this, because after pairing it holds no key on which a message could be received, so a revoked browser keeps showing "Saved" until the user re-pairs it. This v1 limitation is written into the phone's Disconnect dialog: "Pages saved from that browser will be ignored. Uninstall the extension there or connect it again."

## 4. Save flow

Capture runs under `activeTab`, which grants access to the current tab for the duration of the gesture without any host permission. The capture script deep-clones `document`, because Readability mutates the tree it parses and the user must not see their page change, then calls `new Readability(clone, { charThreshold: 250 }).parse()`. Readability is `@mozilla/readability` 0.6.0, Apache-2.0 (https://github.com/mozilla/readability/blob/main/package.json). Metadata comes from the live document in this order: canonical from `<link rel="canonical">`, then `og:url`, then `location.href` without fragment; title from `og:title`, then Readability's title, then `document.title`; byline from Readability, then `<meta name="author">`; site from `og:site_name`, then Readability's `siteName`, then the hostname; hero from `og:image`. The message to the background is `{ ok, url, canonical, title, site, byline, lang, hero, html }`. If Readability returns null (a login wall, an unrendered JavaScript shell, a PDF viewer) the save proceeds with an empty `html` so that the phone fetches the page itself as it would for a share-sheet save, and the toast reads "Saved — your phone will fetch the text".

The cap is applied in the capture script before the message crosses to the background. The script serialises Readability's `content`, measures it with `TextEncoder`, and if it exceeds 512 × 1024 bytes drops trailing top-level children of the content node until it fits, then appends `<p data-kefli-truncated="1">` so that the phone can show "Text was cut short; open the original". Scripts, styles, forms, iframes and `data:` images are stripped before measurement.

The wrap is built in the background with nostr-tools 2.25.x (Unlicense; https://jsr.io/@nostr/tools/doc), whose `nip59` module provides `createRumor`, `createSeal` and `createWrap`. The rumor is kind 979, `created_at` the capture time, no tags, content the JSON from contract 4.4 plus two proposed fields: `"token"` from the pairing record and `"truncated": true` when the cap fired. The seal is kind 13, signed by a fresh random key `sk1`, its content NIP-44 v2 ciphertext under the conversation key of `sk1` and the user's pubkey, its `created_at` tweaked backwards by up to two days as NIP-59 recommends (https://github.com/nostr-protocol/nips/blob/master/59.md). The wrap is kind 1059 signed by a second fresh key `sk2`, tagged `["p", userPubkey]`, `created_at` tweaked the same way. Nothing in the wrap identifies the extension, the browser or the URL. `sk1` is discarded after sealing; `sk2` is kept for eight seconds in `chrome.storage.session` for Undo.

Publish opens one WebSocket per relay from the pairing record, answers an AUTH challenge with `sk2` (the pubkey the relay sees as the writer), sends `["EVENT", wrap]` and waits for `["OK", id, true]`. Connections are held for 60 seconds after the last message so consecutive saves reuse them. The operator relay's OK flips the toast to "Saved"; the user's own relays are best-effort. If no relay accepts within ten seconds the entry stays pending and the queue takes over.

The toast is the house inverted toast (flow decision 57): a small card 336 pixels wide (never wider than the viewport less 32), radius 14, 16 pixels in from the bottom right of the viewport, set in system-ui at 15/1.45. It takes the opposite token scheme to the page's: its surface is the page scheme's text colour, its text the page scheme's background and its shadow the page scheme's float, and every role inside it (muted, success, error, the fill, the focus ring) comes from the flipped set. The scheme is read from `prefers-color-scheme` on the toast's own root, never from the page. Its leading slot holds the saved page's cover, 40 pixels at radius 8: cover v1's SVG drawn from the save's d-tag hash, which the background sends with the result, inlined in the shadow root with `ShelfCover.css` and hidden from screen readers, so the toast needs no network and no image. The cover draws itself in once while Kefli saves (each shape over 520 ms, 34 ms apart, or already drawn under reduced motion). The same cover element is kept when "Saving…" becomes "Saved", so the drawing isn't restarted, and a small mark lands on its corner with the last shape: a tick once it is saved, the offline mark while it waits to send, the alert mark when it couldn't send. A removed or refused save shows a plain tile the same size instead, since there is no save to show. The 2-pixel countdown along the bottom edge runs in the article's ink, `ShelfCover.lineInk(hash, toast surface, toast text)` for 3:1 on the toast, or in the toast's text colour when there is no cover. The card is a group labelled Kefli, and what it says is announced through one persistent region with `role="status"` and `aria-live="polite"`, created once, whose text alone changes. It shows "Saving…" until the first OK, then "Saved to Kefli" with Undo (Open in app is dropped, flow decision 9), and dismisses after eight seconds, paused on hover or on focus the user gives it, or on Escape or ✕. It never takes focus on its own: pressing the shortcut again while it shows moves focus to Undo, and Escape, ✕ or Tab past its last button returns focus to where it was (flow decision 58). On pages where a content script cannot run (`chrome://`, `about:`, the Chrome Web Store, the built-in PDF viewer, Firefox reader view) the save is URL-only, the action badge shows a tick for four seconds, and on Chrome 127+ and Firefox a small popup under the toolbar button confirms the save with Undo; older Chrome shows the tick only (flow decision 59). Otherwise the badge counts saves queued offline, in a neutral grey (flow decision 30); saves that couldn't send are listed on the options page. Wherever the browser shows Kefli (the toolbar button, the right-click menu, the options page's tab and the options logo), it shows the app icon frozen under flow decision 70: C·L·063 with the paper mark, kept as static artwork in `shared/brand/src`, with its own tuned drawings for 16 and 32 pixels. It replaces the board's provisional icon (the cover of `https://shelf.app/`, decision 67) that the mockup was first drawn with.

Undo publishes a NIP-09 kind 5 signed by `sk2` with `["e", wrapId]` and `["k", "1059"]` to every relay the wrap reached. This is valid because NIP-09 requires the deletion to come from the event's author, and the wrap's author is `sk2`; the operator relay accepts kind 5 from anyone (contract section 3). If the phone was awake and already unwrapped the message, the item exists there and the deletion only removes the wrap, so the options page carries one honest line: "If your phone had already picked the page up, remove it there." A rumor-level unsave is v2.

The toast has no Open in app (flow decision 9): there is nothing useful to open on a laptop until the web reader exists, and the `/open` page leaves the v1 website scope.

The offline queue lives in `chrome.storage.local` under one key, an array of `{ wrapId, wrap, relaysDone, createdAt, attempts }`. Wraps are stored already encrypted, so a queued entry leaks nothing if the profile is copied. `storage.local` allows 10 MB (https://developer.chrome.com/docs/extensions/reference/api/storage) and a wrap is at most about 700 KB after encryption and base64, so the queue is capped at eight entries. A ninth save is refused and nothing is queued: the toast reads "Not saved: 8 are already waiting" and asks the user to save it again once online (flow decision 31, so no queued save is ever lost silently). A `chrome.alarms` alarm fires every minute while the queue is non-empty (the minimum period for a packed extension) and retries each pending entry against the relays it has not reached, with attempts capped at 200, after which the entry appears on the options page under "Couldn't send" with a Retry button. Only a try made while the browser is online counts, so a save made offline waits however long the browser stays offline, though the alarm still tries it each minute. A stopped entry is listed under "Couldn't send" whatever it last waited on, since Retry alone sends it, and the badge and the waiting notice don't count it. For a save made offline the toast reads "Saved — will send when you're online" with Undo, which takes the entry out of the queue and lowers the waiting count; nothing has reached a relay, so nothing needs retracting (flow decision 60).

## 5. NIP-07 decision

The extension does not use `window.nostr` in v1. Signing kind 30979 directly from a NIP-07 signer would require the extension to run the Turndown conversion (duplicating the hash-critical step the contract centralises on the phone), generate an AES key and encrypt the text, upload the blob to Blossom with a kind 24242 auth event, call `POST /register` under NIP-98, and self-encrypt the item JSON with `window.nostr.nip44.encrypt`, which Alby, nos2x and their forks implement unevenly and each behind a separate prompt. That is four or five signer pop-ups for one click, against a contract principle that only the phone holds the key. The gift wrap costs nothing extra and keeps the phone as the single writer of kind 30979, so the audio cache and the fixture hash stay consistent. NIP-07 could offer pairing without a QR via `getPublicKey()`, but that would skip the token exchange and leave the user no way to disconnect a browser from the phone, so it is also rejected. A user with a signer extension installed sees no difference.

## 6. Browser-specific notes

Chrome terminates the service worker after 30 seconds of inactivity and after five minutes of continuous processing of one event; since Chrome 110 extension API calls reset the idle timer, since 114 a long-lived message port does, and since 116 an open WebSocket with traffic does (https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle). The publish path relies on the WebSocket rule and sends a NIP-01 `["REQ", "ping", {"limit":0}]` and `CLOSE` every 20 seconds while a publish is in flight. Nothing in the extension needs the offscreen document API (https://developer.chrome.com/docs/extensions/reference/api/offscreen), since Readability runs in the tab; it is absent from the manifest. All state that must outlive a worker restart is in `storage.local` or `storage.session`, never in module-level variables, and every message handler returns a promise so that the worker stays alive for its duration.

Firefox runs the background as an event page, also suspended after 30 seconds idle and restarted on events, and the same storage discipline covers it. Firefox has no `chrome.offscreen`, which is another reason the design avoids it. The context menu is created unconditionally at the top level of the background script rather than inside `onInstalled`, following the Extension Workshop migration guide (https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/), so that it survives event-page restarts. `commands`, `action`, `alarms` and `storage.session` (Firefox 115+) are supported. Firefox's reader view is a separate `about:reader` document where content scripts do not run; saving from there is URL-only.

Brave and Edge run the Chrome package unmodified. Brave's Shields on the aggressive setting may block the WebSocket to a relay, which appears as a queue that never drains; the "Couldn't send" list names the relay so that the user can allow it. Edge's store takes the same zip and is an optional Stage 5 submission.

## 7. Security and privacy

The extension stores, in `chrome.storage.local`: the pairing record (user pubkey, relay list, token, label, date) and the queue of encrypted wraps. In `chrome.storage.session`: the pairing ephemeral secret while a QR is showing, and each save's `sk2` for eight seconds. Nothing goes to `storage.sync`. No URL, title or article text is persisted in plaintext; the only plaintext exists inside the capture message in memory. The extension makes no HTTP request to any server; its network traffic is WebSocket frames to the paired relays and the user-initiated Open in app tab.

Permissions and why each is needed: `activeTab` grants access to the current tab only on the user's gesture, which is exactly the scope of a save and avoids `<all_urls>`, the largest cause of slow Web Store review (https://developer.chrome.com/docs/webstore/review-process). `scripting` is required to inject the capture and toast scripts under MV3. `storage` holds the pairing and the queue. `alarms` retries the queue after the worker has been terminated. `contextMenus` provides "Save link to Kefli". No `tabs`, `notifications`, `cookies`, `webRequest`, `unlimitedStorage` or host permissions are requested.

If the extension is compromised, by a malicious update, a supply-chain injection or a compromised profile, the attacker learns the user's public key and relay list (public anyway), the pairing token, and the content of any page saved from then on, since capture sees plaintext. The attacker can push arbitrary pages to the library until the user disconnects that browser on the phone, and can delete queued wraps. The attacker cannot read any existing save, decrypt any kind 30979 or earlier wrap, sign as the user, delete the user's items, or reach the audio API, because all of that needs the private key the extension never has. The build is reproducible from a tagged commit with a lockfile, packages are pinned by integrity hash, the content security policy forbids remote code, and each store listing links the source repository and release commit.

From the relay's point of view a wrap reveals the recipient pubkey, a time smeared over two days, and a size, so the operator can count saves per user roughly and guess article length; NIP-44's padding hides size differences below 64 KB.

## 8. Testing at each stage

Unit tests run in Vitest with jsdom. The capture module is tested against the twenty fixture pages in `shared/fixtures/`: each fixture's HTML is loaded into jsdom, the capture function runs, and the test converts the resulting Readability HTML with Turndown 7.2 (MIT, used as a dev dependency only) under `shared/turndown-rules.json` and asserts that the sha256 of the Markdown equals the fixture `text_hash`. This is the proof that the extension's HTML, converted by the phone, yields the same hash the phone would get from its own fetch, and it is the test the project plan says must pass before integration. The cap is tested with a synthetic 2 MB page. The normalise port is tested against `shared/normalise.fixtures.json` even though the extension only uses it for the Undo-time duplicate check on the queue. The wrap module is tested against the fixture kind 1059 save request: given the fixture rumor and known keys the output unwraps to the same rumor, and a round trip with random keys unwraps with the fixture's recipient secret. The pairing parser is tested with expired, malformed, wrong-version and valid payloads. The queue is tested with a fake relay that answers OK, refuses, and times out.

Integration tests run against the staging relay from week 3 with an Android test phone on the staging build. The script is: pair, save five pages of different shapes (news, Substack, Wikipedia, X thread, GitHub README), observe each appear on the phone within ten seconds, Undo one within the window and confirm the wrap is gone from the relay and the phone did not receive it, turn Wi-Fi off, save two pages, turn it back on and confirm both arrive, disconnect the browser on the phone and confirm a further save is ignored, re-pair. A relay-side check with the fixture decryption tool confirms that no wrap carries a URL or title in its tags.

## 10. Integration points and dependencies

On the backend: the strfry write policy must accept kind 1059 from any authenticated pubkey provided the wrap's `p` tag names a registered pubkey, and must accept kind 1059 from a registered, authenticated pubkey addressed to any `p` (the pairing acknowledgement goes to an unregistered ephemeral key). The contract's wording, "accepts writes of those kinds only from authenticated pubkeys", together with the allowlist created by `/register`, would refuse both if the allowlist gates writes, since neither `sk2` nor the pairing key is ever registered. This needs a sentence in contract section 3. The relay must also serve `REQ` for kind 1059 with `#p` equal to the authenticated pubkey for any pubkey that can AUTH, registered or not, so the extension can receive its acknowledgement. On Android: the kind 1059 listener, the kind 978 pairing acknowledgement and the "Connected browsers" screen with Disconnect, the token check on kind 979, fetching the page when `html` is empty, and honouring `truncated`. On iOS: the same, in week 5, with the extension already proven against Android. On the project engineer: adding kind 978, the `token` and `truncated` fields, the empty-`html` rule and the relay policy sentence to contract 1.1; and supplying the fixture kind 1059 with its rumor and the recipient secret so that the wrap test is meaningful.

## 11. Test distribution: developer mode first

Decision (September 2026): the extension is tested in developer mode, not through the stores, until launch. Store listings are prepared in parallel so that review time never sits on the critical path, but nobody installs from a store before Stage 5.

**Two build flavours from one commit.** `npm run build:dev` produces `dist/dev-chrome/` and `dist/dev-firefox/` pointing at the staging relay, Blossom and API; `npm run build:beta` produces `dist/beta-chrome/` and `dist/beta-firefox/` pointing at production. The dev build sets the toolbar badge text (`chrome.action.setBadgeText`) to `DEV` when no save is waiting, so nobody confuses it with a build against production; the beta build shows no badge of its own, and in every build the badge's one other use is the count of saves waiting while the browser is offline (decisions 30 and 64). The options page's Advanced shows the version, environment and commit hash, with a "Copy debug info" button for bug reports whose text includes the outcome of the last twenty saves (flow decision 108). Neither flavour is ever minified or obfuscated, which also keeps the later store submission clean.

**Stable extension ID.** An unpacked Chromium extension gets an ID derived from its folder path, so it changes from machine to machine. The dev and beta manifests carry a fixed `key` field so the ID is identical everywhere; the pairing flow and any logs rely on a stable ID. The Firefox manifests carry a fixed `browser_specific_settings.gecko.id` for the same reason, which Firefox signing requires anyway.

**Chrome, Brave, Edge, Vivaldi, Arc.** `chrome://extensions` (or `brave://`, `edge://`), switch on Developer mode, Load unpacked, choose the `dist/…-chrome` folder, pin the icon. To update: pull or unzip the new build over the same folder and press the reload arrow on the extension's card; the stable ID means pairing survives the reload. For the developer's own loop, `vite-plugin-web-extension` rebuilds on save and reloads the extension automatically. Chrome may show a banner inviting the user to disable developer-mode extensions; testers are told to dismiss it. Developer-mode extensions do not auto-update, so each new beta build is announced with a one-line changelog.

**Firefox.** For the developer: `web-ext run --target=firefox-desktop --source-dir dist/dev-firefox` opens a scratch profile with the extension loaded and reloads it on every change; about:debugging → This Firefox → Load Temporary Add-on is the manual equivalent, cleared on restart. For beta testers, who need it to survive a restart: `web-ext sign --channel=unlisted` has Mozilla's automated signing produce an `.xpi` within minutes, with no listing and no human review; testers install it by opening the file, and an `update_url` in the manifest lets later signed builds update themselves. This is the one place Firefox testing is smoother than Chrome.

**Safari** is out of scope for the extension in v1; iOS and macOS Safari users save through the share sheet.

**Who tests, in what order.** Stage 2 (weeks 3–4): Richard alone on `dev` builds against staging, on Chrome and Firefox. Stage 4 (beta, weeks 6–7): the beta group of ten to twenty on `beta` builds against production, Chromium users via a zipped folder plus a one-page install guide, Firefox users via the signed unlisted `.xpi`. The install guide covers: unzip to a folder you won't delete, Developer mode on, Load unpacked, pin, pair with the phone, and what a number on the button means (saves waiting while offline).

**What the developer-mode phase must prove before any store build.** Pairing works first time on Chrome, Brave, Edge and Firefox on Windows and macOS; a save reaches the phone in under ten seconds with the app open and on next open with it closed; no save is lost across a week of daily use by at least five testers, checked against the options page history; reloading a new build keeps the pairing; and the "Copy debug info" output was enough to diagnose every bug reported. When those hold, the same commit is submitted to the Chrome Web Store and AMO as listed items for launch.

## 13. Risks

Readability drift between the extension and the phone: the phone's share-sheet path fetches and parses on the phone, the extension parses the live DOM, and the same URL can produce different HTML (cookie walls, personalised content, lazy-loaded images). The fixture suite proves equality only for the fixtures; live pages will sometimes hash differently and miss the audio cache. This is accepted for v1 and recorded as a known behaviour, since the extension path with the live DOM is usually the better capture. Relay policy mismatch: if the backend gates 1059 writes by allowlist the whole extension fails on day one; section 10 raises it now so that it is settled in week 1. Service-worker termination on a very slow relay: the ping-keepalive is tested with a throttled relay in the matrix. Store review delays: mitigated by early unlisted submission and minimal permissions. Spam through the gift-wrap channel from parties who know the npub: mitigated by the token; without phone-side enforcement it is a real nuisance vector and the Android engineer must ship the check with the listener. Firefox event-page differences discovered late: the Firefox build is W4 D1, not the last day, and the design avoids every Chrome-only API.

## 14. Definition of done

The extension is done for v1 when: both builds come from one commit through CI that runs the fixture suite and passes all twenty hashes and the 1059 round trip; pairing completes in under five seconds on the staging relay with the Android build and the phone shows the browser under Connected browsers; a save from Chrome and from Firefox appears on the phone within ten seconds on the Stage 2 gate recording; Undo within the window leaves nothing on the relay or the phone; two saves made offline arrive after reconnect without user action; a disconnected browser's saves are ignored; the manual matrix in section 8 has no open failures on Chrome and Firefox and no severity-1 on Brave and Edge; the Chrome Web Store listing is approved (unlisted) and the AMO listing is signed; the privacy policy is live; the source repository is public with the release tag and the store listings link to it; and Richard has used it daily for a week on his own laptop without opening the options page.

Rulings made while building it, under Richard's standing rule that low-level protocol and build calls are decided, recorded and reported:

- **No host permissions; CORS on the operator API.** Pairing posts the offer to `POST /pair-offers` and saves upload to Blossom, which section 2 didn't foresee. Blossom servers already answer with CORS; the operator API does the same (any origin, `Authorization` and `Content-Type` allowed, preflight answered), so the manifest keeps section 2's permissions and no `host_permissions`. The dev API (`server/dev/api.mjs`) does this now; the Go API must too (backend spec).
- **Fragment-only links are made absolute in the capture.** Readability leaves `#note-1` relative when the document's address equals its base, which is true on the live page and false in the phone's WebView and the fixture generator. Untreated, ten of the twenty page fixtures captured from the live page gave a different `text_hash` from the phone's. The capture resolves fragment-only links against the document's base, as Readability does in the other case; all twenty now match (`npm run fixtures -w @kefli/extension`, headless Chrome).
- **The capture runs the phone's parser bundle.** `parser.js` is `shared/vendor`'s bundle unchanged, and the capture calls its `kefliParse` and `kefliArticle` on the serialised live document, so canonical, hero, readerable and the guard come from the same code as on the phone. The guard, the 2 MB cap and the canonical's 2,048 characters (contract 4.3) are applied in the tab, and a page at an address of 4,608 characters or more, which no save request can carry whatever it leaves out, isn't read at all.
- **The offline queue keeps the encrypted blob.** A save made offline keeps its inbox blob, already ciphertext, beside its wrap, so the phone still gets the live page's text once it sends; a blob over 900,000 characters as base64 isn't kept, nor one past the 7,200,000 the queue's blobs may come to in all, and the phone fetches that page itself: the request still names the blob, and the phone, meeting a 404 for it, fetches the page at once. - **The save flow follows section 2's order** (F23). A save is written to the queue, as `why: 'sending'`, before its first send, and such entries don't count towards the eight; `settle` decides afterwards, as before, whether a ninth is refused. The upload has a time limit of 20 seconds plus one for every 32 KB, about 109 seconds for the largest blob, rather than a flat 20 that would fail a 2 MB blob on every retry over a slow line. The browser's start and install flush the queue too, since Firefox doesn't keep alarms across a restart, and every change to the queue turns the minute alarm on while an entry that isn't stopped remains, so a start-up flush that fails leaves the alarm to try again. The save goes into the queue inside its own per-save run, so a flush already going never finds it there unclaimed and sends it a second time.
- **Undo** (F24, F40). The background no longer times Undo: it can be pressed for as long as the toast or popup showing it is up, and that countdown pauses under the pointer or focus. Undo waits for a send of that save already under way, then retracts it if it went or takes it off the queue if it didn't; the flush reads each entry again at its turn, so a save undone meanwhile isn't sent. A waiting save whose send may have reached the relay all the same (any but an offline save never tried, such as one whose answer timed out) is retracted as well as taken off the queue; the relay refuses a retraction of a wrap it doesn't hold, which then changes nothing, and a save the phone already has shows "Already on your phone". A retraction is taken; refused as `blocked:`, the relay's answer to a kind 5 naming a wrap it doesn't hold from that key; or not made (out of reach, unanswered, or `rate-limited:`). A save that went, whose retraction wasn't taken or whose second look got no answer, shows the drafted `undofailed` toast, records `undo: failed` and keeps the key. A waiting save whose wrap the relay doesn't hold is removed with its entry; one whose retraction couldn't be made shows `undofailed` and keeps the key. A press whose key the session no longer holds, for a save that went or a waiting one a try may have sent, retracts nothing, still checks the phone, then shows "Already on your phone" or `undofailed`. Undo follows each wrap the save went by under that wrap's own lock, and reads its key and the queue, and takes the save off the queue, under the move's lock. A second Undo of a save already undone, such as a double click, changes and says nothing more.
- **Too large to wrap** (F39). `prepare()` sets the request's `hero`, `byline`, `site`, `lang`, `title`, `canonical` and last `html` to null, one at a time, until the wrap fits under 8 KB; NIP-44's padding makes the steps coarse, so up to about 2,350 characters of address keeps the text and about 2,370 to 2,570 sends without it. - **A refused upload sends the request without its HTML.** An inbox blob counts against the library's day of uploads, and against its storage until the phone deletes it once the save is made, or it expires after 14 days (contract 4.4 and 5). - **A wrap that waited is made again.** The phone reads its inbox from 172,800 + 300 seconds before its last look, so a wrap made more than a minute before it goes (`WRAP_FRESH_FOR`) is made again just before it is sent: the same request with the same uuid, under a new wrap and key dated from now. It takes the old one's place in the queue, Undo's key and the per-save lock, as a refused save's does; offline it waits as it is. The queue counts tries by save, not by wrap, so a wrap whose try failed before its publish is kept too; its retraction is refused as `blocked:` and changes nothing.
- **A move carries Undo with it** (F40). Each waiting save a move wraps again for the new key has its Undo key moved, as a save sent again without its HTML has: the new wrap's own key under the new id, and the old id pointing to it, so Undo on a toast from before the move, such as the offline one, takes the save off the queue. When the old wrap may already be on the relay, because a send of it was tried (an answer that timed out) or was under way as the move was taken, it keeps its own key, and the library it went to, beside the new one: Undo retracts it too, and looks for the phone's kind 5 for it under that library's key, since the phone's last look at the old inbox (contract 4.8, step 5) would otherwise bring the save into the new library; a save the phone took there shows "Already on your phone". These kept wraps stay with the save when its wrap is made again later.
- **A move found mid-send.** A save whose send is under way when the move is found is wrapped again too, and its new wrap waits for that send. The background remembers the rename as the move makes it, before Undo's key follows, so a send that then fails waits under the new wrap and its toast says it couldn't send, and one whose upload the operator refuses meanwhile goes as it was, its Undo still reaching the move's wrap. One that went to the old library is Saved, and its new wrap still goes to the new library at the next flush; Undo on its toast retracts the one that went and takes the other off the queue. A move is taken under a lock of its own and only once, so two looks for a move at once wrap the queue again only once. A move is taken only while the pairing is still the one the look began from, so a Disconnect, or a pairing with another library, made while the look waited is left as it is; the options page writes and removes the pairing under the move's lock.
- **A move taken as a save is made.** A save reads the pairing before it is prepared, so one made while the half-hourly look takes a move could be wrapped for the old library and join the queue just after the move had wrapped the queue again, and every try after made its wrap again for that library. Before each try the background reads the pairing under the move's lock, and a save wrapped for another user, or with another token, is wrapped again for the pairing, its Undo key following and an old wrap that may be on the relay kept for Undo to retract. The move writes the pairing before it wraps the queue again, so a worker stopped between the two leaves the waiting saves to be caught up the same way, and a save already wrapped for the new pairing is left as it is.
- **A page whose HTML was left out to fit the wrap** (F39) shows the `notext` toast and is recorded as "sent, no text", as a link save and a save whose upload the operator refused are.
- **A queue storage.local can't read** no longer holds a save at "Saving…": it ends on Saved once sent, or on the queue-full toast when it can be neither sent nor kept, and Undo, finding no waiting save there, retracts it and says if it couldn't.

After the hardening (14 and 15 October 2026; flow decision 118). Every way a save enters was attacked, a page and its tab, the network's answers and the browser's storage among them, and these limits came of it. Nothing new is drawn: each lands in a state the extension already has.

- **What the capture reads.** A page past 200,000 elements, 4 million characters of body text less its scripts and styles, 32 million characters serialised, or whose widest element's children × text length / 2 passes 4,000 million is saved as its address and title, `html` null, without being read, since reading runs on the page's own thread and freezes its tab while it runs: the HTML Standard's single page froze one for two minutes. The largest real pages tried read inside the limits: World War II on Wikipedia (17,011 elements, read in 2.8 s), War and Peace on Project Gutenberg (3.6 million characters of text, 7.9 s), and Moby-Dick, its 2,846 paragraphs all in the body, at 1,964 million by the widest measure. The guard counts spoken words only in the first 4,096 characters of the Markdown, since the count runs on the page's thread and the parse costs more than its length; a page that isn't readerable and has fewer than 120 words there goes without its HTML, and the phone applies the guard to the whole page. The address loses its fragment and any user name and password, the canonical is left out past 2,048 characters before it is read and kept only from the page's own site without user info (contract 4.3), and a page's `<base>` counts only at an http(s) address.
- **Waiting on the page.** The capture has 30 s, after which the save goes as the page's address through the popup, and another press on a tab still being read counts as that save. The shortcut waits 2 s to learn whether a toast took the press for its Undo. A save waits at most 2 s for its toast before it is queued and sent, the toast showing later if the page lets it, and where no toast can run (an SVG, a page that took the toast's element name for its own), the popup shows it instead.
- **Answers and deadlines.** `defaults.json` has 10 s, then the kept copy, and is kept only with a ws(s) relay, http(s) Blossom and API addresses, and relays and mirrors of at most 32 addresses each, every address at most 2,048 characters; the phone's lists in a pairing are kept to 100 entries of the same length. Answers from Kefli's servers (a Blossom descriptor or refusal, `defaults.json`, the pair-offers reply) are read to 64 KB. `POST /pair-offers` has 15 s and the pairing relay's connection 10 s; a relay connection has 10 s to open and a publish 10 s for its OK; Undo's DELETE of the inbox blob has 10 s. A read of the relay is whole only once the relay ends its answer with EOSE; nostr-tools' own 4.4 s wait is set past the extension's 10 s. A look for a move asks the relay for 100 wraps at most and keeps each once, one sent again passed over before its signature is checked; one stopped at 100, at its 10 s, or closed by the relay keeps what came and takes a move found there. The last look's time moves on only once the window has been read to its end: to when the look began, when its newest answer comes back whole with fewer than 100; otherwise the looks at start and every half hour read on down the window by `until`, at most five answers of 100 each time, from where the last of them stopped (`movesScan`), as the phone's inbox does, and the time moves to when that scan began once an answer comes back whole. A full answer that brings nothing new is stepped past, and an answer cut short leaves the scan where it was. A save's look reads the newest answer alone. Undo's look for the phone's kind 5 is found once it comes, not found only when the relay finishes without it, and no answer otherwise. A connection that sent nothing for a whole read is closed. Still to do: the redirect rules contract 1.12 set (sections 3.1, 5 and 6) aren't applied here yet, since the pair-offers post, the Blossom upload and delete and the `defaults.json` fetch follow the browser's redirects.
- **The queue's storage.** Saves on their first send count here too: at most 64 entries in all, and the blobs kept come to at most 7,200,000 characters as base64 (eight at the 900,000 cap), within the 10 MB Chrome gives `storage.local`. A save storage won't take is sent anyway; one that also can't be sent is kept without its blob, or else refused as the ninth is. A queue value that isn't a list reads as empty.
