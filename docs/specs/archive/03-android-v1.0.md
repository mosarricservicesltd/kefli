# Android app specification

Owner: Android engineer. Version 1.0, September 2026. Codes against `00-contract.md` v1.0 and follows the sequence in `01-project-plan.md`. Where this document proposes a change to the contract it says so, and section 9 collects those proposals for the project engineer.

> **Revision note (contract v1.1).** This specification was written against contract v1.0. Contract v1.1 (document 00) takes precedence wherever they differ; apply its section 11 changelog, in particular the move to NIP-78 kind 30078, default public mirrors, AUTH only for reading gift wraps, the 16 KB event ceiling, and the extension device key with inbox blobs. References here to kinds 30979, 979, 978 or 10013 should be read in that light.

## 1. Goal and scope

The Android app is the first client and the reference implementation for everything the contract leaves to a client: parsing, Markdown conversion, self-encryption, Blossom upload, the offline queue, the gift-wrap listener and both voice providers. It must pass the stage 1 gate at the end of week 2 (Richard saves from X and Chrome, reads offline, listens with the system voice, archives, events verify on the relay) and the stage 2 gate at the end of week 4 (laptop saves appear within ten seconds, server audio plays with highlighting, a second device pairs, Play internal test track live). After week 4 it is what the iOS engineer copies, so the code has to be legible as well as working.

In scope: the share target, first launch and key generation, the Library, the Reader, both Listen providers with a mini player and lock-screen controls, the Listen tab, the You tab with backup, pairing, appearance, voice, delete and advanced relays, the three signer providers, existing-user import, and the Play listing requirements. Out of scope per the flow map: tags, folders, search beyond a title filter, highlights, the Recommend gesture (kind 39701 is reserved and never emitted), widgets, Wear, tablets beyond "the phone layout does not break", and any discovery surface.

Minimum SDK is 26. Three things fix it there: `UtteranceProgressListener.onRangeStart`, which drives system-voice word highlighting, was added at API 26 ([reference](https://learn.microsoft.com/en-us/dotnet/api/android.speech.tts.utteranceprogresslistener.onrangestart?view=net-android-34.0)); Media3 needs 23 ([release notes](https://developer.android.com/jetpack/androidx/releases/media3)); and the Keystore AES-GCM path used for key wrapping is clean from 23 with StrongBox from 28. Going lower would buy a sliver of very old devices at the cost of a second highlighting path and a doubled device checklist. Target SDK is 36, which Play requires for new apps and updates from 31 August 2026 ([Play Console help](https://support.google.com/googleplay/android-developer/answer/11926878?hl=en)).

## 2. Architecture and stack

Kotlin 2.x, Jetpack Compose with Material 3 under our own tokens, a single activity with Navigation Compose, Hilt, coroutines and Flow, Room, WorkManager for anything that must survive process death, Media3 for playback. The Gradle build has these modules, each with its own tests. `:core:model` holds the item JSON classes (kotlinx.serialization, `ignoreUnknownKeys`, a hard refusal to write `v != 1`), the URL normaliser and other pure functions that run in JVM tests against the shared fixtures. `:core:nostr` wraps the nostr library behind our `Signer` and `RelayPool` interfaces and owns NIP-42 auth, NIP-98 headers, NIP-44 self-encryption, NIP-59 unwrap and NIP-49. `:core:parse` owns the fetch, the hidden-WebView parser host, the vendored Readability and Turndown bundle, and the Markdown offset map both voice providers use. `:core:crypto` owns the key file, mnemonic derivation, AES-GCM blob encryption and the Blossom auth event. `:core:data` owns Room, sync, the queue workers and the cache. `:feature:library`, `:feature:reader`, `:feature:listen`, `:feature:you`, `:feature:signin` and `:feature:share` are Compose screens with view models that depend on `:core:*` and never on each other. `:app` wires the manifest, Hilt graph, share-target activity, `MediaSessionService` and backup rules. `:shared` copies `shared/fixtures/`, `shared/normalise.fixtures.json` and `shared/turndown-rules.json` from the monorepo into test resources at build time so the fixture suite cannot drift.

Two nostr libraries were evaluated. rust-nostr publishes Kotlin bindings to Maven Central as `org.rust-nostr:nostr-sdk` (0.45.0-alpha.7 at the time of writing, MIT, UniFFI) and its NIP table lists NIP-06, 42, 44, 46, 49, 59, 65 and 98 as implemented with NIP-55 explicitly absent; the project calls itself alpha with an API that changes in breaking ways ([rust-nostr/nostr](https://github.com/rust-nostr/nostr), [nostr-sdk-ffi](https://github.com/rust-nostr/nostr-sdk-ffi), [Maven Central](https://central.sonatype.com/artifact/org.rust-nostr/nostr-sdk)). Quartz, extracted from Amethyst, is `com.vitorpamplona.quartz:quartz` 1.14.0, MIT, Kotlin Multiplatform for JVM, Android, iOS and Linux, carrying Amethyst's production NIP-55 and NIP-46 code, but documented as a client guide rather than a NIP table and shaped by Amethyst's release needs ([Maven Central](https://central.sonatype.com/artifact/com.vitorpamplona.quartz/quartz), [GitHub](https://github.com/vitorpamplona/quartz)).

The decision is rust-nostr, pinned to an exact version, because the iOS engineer gets the same code through the Swift bindings: NIP-44 padding, NIP-59 timestamp randomisation, NIP-49 parameters and NIP-98 tag order then behave identically on both phones and against the fixtures without two implementations being reconciled. Everything goes through the `:core:nostr` facade, so a breaking release costs a day in one module, and Quartz behind the same facade is the fallback if the bindings fail a week-1 integration test. NIP-55 is our own `AmberSigner`: the `nostrsigner:` scheme, `queryIntentActivities` to detect a signer, `get_public_key` with a permission list requesting `sign_event` for kinds 30979, 5, 24242, 27235 and 22242 plus `nip44_encrypt` and `nip44_decrypt`, and the `content://<package>.<TYPE>` resolver for background signing once the user has ticked "remember" ([NIP-55](https://github.com/nostr-protocol/nips/blob/master/55.md)). Amber (`com.greenart7c3.nostrsigner`) supports that resolver path ([Amber](https://github.com/greenart7c3/Amber)) and is one implementation of the interface, never a hard-coded dependency.

For parsing, the options were Readability4J, Mozilla's Readability.js in a hidden WebView, and a Rust port. Readability4J 1.0.8 dates from 27 October 2021 ([Maven](https://mvnrepository.com/artifact/net.dankito.readability4j/readability4j/1.0.8)), ports a February 2018 Readability commit ([README](https://github.com/dankito/Readability4J)), serialises through Jsoup with formatting that differs from a browser's, and a September 2025 issue on the Feeder project describes it as dead ([Feeder #930](https://github.com/spacecowboy/Feeder/issues/930)). The extension will run current Readability in the browser's DOM, and any byte-level difference in the HTML reaching Turndown changes `text_hash` and silently loses audio cache hits, the failure the plan warns about in section 4. A Rust port would be fast and shareable with iOS, but I found none claiming output identical to Mozilla's at a pinned commit, and we would own its divergence for ever. The hidden WebView wins: it runs the exact `@mozilla/readability` 0.6.0 (Apache-2.0) and `turndown` 7.2.4 (MIT) files vendored under `shared/` against a real Blink DOM, using `DOMParser.parseFromString` so page scripts never execute, with `blockNetworkLoads` set so nothing is fetched. The same bundle runs in the extension and in WKWebView on iOS, the only arrangement in which three platforms can plausibly agree on twenty fixture hashes. The cost is that a WebView is created on the main thread and holds roughly 60–100 MB while alive; section 4.1 shows how the worker borrows the main looper and tears the WebView down afterwards.

## 3. Data layer

Room is the source of truth for the screen; relays are the source of truth for the account. Every write goes to Room first and to the network through a queue; every relay read is merged into Room by `d` and `created_at`. There are seven tables. `items` is keyed by `d` and stores every field of the decrypted item JSON as columns plus `event_id`, `event_created_at`, `dirty`, `text_state` (`none`, `pending`, `cached`, `failed_honest`), `text_path` (decrypted Markdown in private storage), `hero_path` and `parse_error`. `blobs` holds the ciphertext sha256, local path, size and per-server confirmation. `outbox` is the offline queue: one row per pending operation with `kind` (`publish_item`, `publish_deletion`, `upload_blob`, `register`, `delete_wrap`), a JSON payload, `attempts` and `next_attempt_at`; workers drain it in order and the Library reads it to draw ⏳. `audio` records `text_hash`, `voice`, `model`, `status` (`unknown`, `miss`, `queued`, `ready`, `downloaded`, `unavailable`), server URL, local file, `duration` and the downloaded `words.json` path. `relays` holds URL, read and write flags, `source` (`operator`, `nip65`, `nip37`, `manual`) and last AUTH time. `wraps_seen` stores unwrapped kind 1059 ids so a reconnect replay is idempotent. `settings` is a single row for reader size and theme, voice, backup-card state, save count and pubkey; the private key never touches Room.

`SyncWorker` has three phases. Outbound drains `outbox` in order, publishing to the operator relay and every write relay, plus NIP-37 relays for kind 30979; a row is removed only on the operator relay's OK, other relays' failures being logged and retried without blocking. Inbound opens a REQ for kind 30979 by the user since the last seen `created_at` minus five minutes, answers AUTH, decrypts and upserts by `d` keeping the newer `created_at`, with a local `dirty` row winning a tie and being republished. The third phase fetches text for items with `text_state = none`, decrypts with the item's key and nonce, verifies the ciphertext sha256 and writes the Markdown file. Sync runs on foreground, after a save, from the gift-wrap listener, and every six hours under the `CONNECTED` constraint.

The cache is plain. Text files live with the item and go on NIP-09 deletion. Hero and inline images load through Coil with a 256 MB disk cache and are pre-warmed for the newest fifty unread items after each sync, on unmetered network unless "Download on mobile data" is on under You. Audio is kept until an item has been archived for thirty days, under a 1 GB ceiling with oldest-archived evicted first. You shows one "Storage" line with a clear action.

No gesture ever fails because of the network. Save, archive, un-archive, progress, delete and voice choice write Room and append to `outbox` synchronously; the worker is enqueued expedited with `RUN_AS_NON_EXPEDITED_WORK_REQUEST`, the `CONNECTED` constraint, exponential backoff from thirty seconds and unlimited attempts ([WorkManager](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work)).

## 4. Feature specifications

### 4.1 Save

The share target is a translucent `Activity` registered for `ACTION_SEND` with `text/plain`. It takes the first `http(s)://` URL from `EXTRA_TEXT` (the last one when the first is a known shortener, since X puts the `t.co` link last), uses `EXTRA_SUBJECT` or the host as a provisional title, normalises, computes `d`, and inserts an `items` row with `state = unread`, `saved_at = now`, `text_state = pending`. It shows the Saved sheet with "Undo" and "Read now" for two seconds and finishes; the whole path runs synchronously in under 100 ms so the sheet appears before the thumb lifts. Undo deletes the row; "Read now" opens the Reader on a pending item. If `d` exists and is archived, the target un-archives and bumps `saved_at`; if it exists unread, the sheet says "Already saved".

`ParseWorker`, enqueued expedited, fetches with OkHttp using a desktop Chrome user agent and a mobile fallback on 403, follows redirects, caps the body at 5 MB, and records the final URL and any `<link rel="canonical">` for the normaliser's `amp.`/`m.` rule. It posts to the main looper to create a `WebView` with JavaScript on, network loads blocked, file and content access off, loads `about:blank` and injects the bundle through `evaluateJavascript`. The bundle exposes `shelfParse(html, url, rules)`, which builds a document with `DOMParser`, runs `Readability` with the extension's options and returns title, byline, site, lang and content HTML, and `shelfMarkdown(contentHtml, rules)`, which runs Turndown with `shared/turndown-rules.json`. The worker awaits the result in a `suspendCancellableCoroutine`, destroys the WebView, then on a background thread computes `text_hash`, the word count, AES-256-GCM ciphertext under a fresh key and nonce, and the ciphertext sha256, writes the Markdown file, updates the row to `cached`, and appends `upload_blob` and `publish_item` to the outbox. Upload precedes publish so another device never sees an item whose blob is missing. If no WebView provider exists the row becomes `failed_honest` and the Reader offers the original.

The item JSON is NIP-44 encrypted with the conversation key from the user's own key pair, signed through `Signer`, and sent as kind 30979 with exactly the two permitted tags. The Blossom upload targets the user's kind 10063 servers or else the operator's, with a kind 24242 auth event carrying the `x` tag and a one-hour `expiration`.

Extension saves arrive through `WrapListener`, a WorkManager job that holds a REQ for kind 1059 with `#p` equal to the user's pubkey on the operator relay. Each event is unwrapped with NIP-59, checked for rumor kind 979 and `v = 1`, and its `html` (capped at 512 KB) handed straight to `shelfMarkdown`; the pipeline from there is identical, which is the point. After publishing, a `delete_wrap` row sends the kind 5 and the id goes into `wraps_seen`. Section 4.5 explains why the ten-second gate holds only while the phone is awake.

### 4.2 First launch

No signup, no tour. On first start the app draws 128 bits from `SecureRandom`, encodes a twelve-word BIP-39 English mnemonic, derives the key at `m/44'/1237'/0'/0/0` through rust-nostr, and stores mnemonic and key as in section 6. `POST /register` goes through the queue with a NIP-98 header, so a first launch on the train still lands in an empty Library with "Share any link here" and "Link your browser". After the third successful save the backup card appears at the top of the Library; dismissing hides it until the tenth save, after which it lives only under You. The recovery sheet shows the twelve words behind a device-credential prompt in a numbered grid with `FLAG_SECURE`.

### 4.3 Read

The Library is a `LazyColumn` of rows showing source, title, read time (words over 230 per minute, "1 min" floor) and an audio dot when audio is downloaded, in `saved_at` order, with Unread and Archive tabs. Swipe left archives with a five-second Snackbar undo; the row leaves immediately, the Room write happens on timeout, and process death inside the window commits the archive. Pending items show ⏳ instead of read time. The offline banner appears when `ConnectivityManager` reports no validated network, with the flow map's wording, and nothing polls.

The Reader parses the Markdown once with commonmark-java, source spans retained, into paragraph blocks each carrying its character range; each block is a Compose `Text` over an `AnnotatedString`, images are Coil `AsyncImage` at their original URLs, links open in a Custom Tab. The progress line is a 2 dp bar whose fraction is the first visible block's start offset over total length, saved to `items.progress` on scroll idle and republished at most once a minute and on exit; reopening scrolls to the block containing `progress × length`. The top bar has back, Aa, play and archive; Aa is a sheet with sizes 16 to 24 sp and three theme chips persisted in `settings`. The end card offers Archive and Next unread. When `text_state` is `pending` the Reader shows title, host, one sentence saying the text is still being fetched, and a button to open the original; when `failed_honest` the sentence names the reason ("This page needs a login" for 401/403, "This page is mostly video" when Readability returns under 200 words beside a `<video>`, "This is a PDF", which v1 does not parse) with the same button.

### 4.4 Listen

`Voice` exposes `prepare(item)`, `play()`, `pause()`, `seekTo(offset)`, `rate`, a `Flow<Highlight>` of Markdown offset pairs and a `Flow<Position>`. `SystemVoice` wraps `android.speech.tts.TextToSpeech`. Before speaking, `:core:parse` builds a spoken-text projection: syntax characters dropped, headings and list items given a terminal full stop, images and link URLs removed, and an `IntArray` mapping every spoken index back to its Markdown offset. The projection is split at paragraph boundaries under `getMaxSpeechInputLength` and queued with `QUEUE_ADD`, each utterance id carrying its paragraph's base offset. `onRangeStart(utteranceId, start, end, frame)` maps to `(base + map[start], base + map[end])`; the reference notes the callback arrives only when the engine supplies timing, which Google's engine does, so for silent engines the app highlights the whole paragraph from `onStart`, which is honest and still useful. Rate maps the 0.8×–2× control to `setSpeechRate`; audio attributes are `USAGE_MEDIA` with `AUDIOFOCUS_GAIN`, so Bluetooth routing and ducking behave like music.

`CachedVoice` posts `text_hash`, `voice` and `model` with a NIP-98 header, re-posts with the text on `miss`, and then polls `GET /audio/status/…` every five seconds from a WorkManager job under `CONNECTED`, so the app can be closed while Kokoro works; the mini player shows "Preparing audio" and a notification is posted only if the user has left the screen. On `ready` it downloads the audio and `words.json` and marks `downloaded`. Playback is Media3 ExoPlayer 1.11.0 inside a `MediaSessionService` declared with `foregroundServiceType="mediaPlayback"` and `FOREGROUND_SERVICE_MEDIA_PLAYBACK` ([service types](https://developer.android.com/develop/background-work/services/fgs/service-types)), which supplies lock-screen, Bluetooth and car controls and the notification ([Media3 session](https://developer.android.com/media/media3/session/control-playback)). Highlighting samples `currentPosition` at 100 ms and binary-searches `words.json` by `s`, emitting `o` and `o + w.length`; the plan's drift mitigation is implemented by snapping to the paragraph containing `o` whenever the match sits more than 400 ms from the sampled position. `SystemVoice` is also routed through the same `MediaSession` via a custom `Player` implementation so both providers share the lock-screen controls; that is the largest piece of Listen work and is scheduled for week 3.

Whichever provider started an article finishes it. The mini player sits above the bottom navigation on every screen with title, play/pause, back 15 s, forward 30 s, speed and next. The in-article player stops at the end and offers Next; the Listen tab lists items with audio in Library order with a downloaded tick, and "Play all" builds a session queue of unread items and continues through them, requesting audio for the next three unread items in advance on Wi-Fi.

### 4.5 Offline

Offline is a mode. The banner shows, cached items open identically, play works when audio is downloaded and otherwise the button reads "Available when online" with no spinner. Offline saves complete in Room and queue; the parser waits on `CONNECTED` and the Library shows ⏳. When connectivity returns `SyncWorker` drains the queue silently.

Battery behaviour follows the platform. Nothing runs as a foreground service except playback. The gift-wrap subscription lives in a WorkManager job while the app is in the foreground and for ten minutes after, then drops; a periodic fifteen-minute job under `CONNECTED` reconnects, fetches 1059 events since the last seen timestamp, processes them and exits. In Doze that job is deferred to maintenance windows, so a laptop save made while the phone has been face-down for two hours appears at the next window, which is acceptable because the extension toast never promises immediacy. The app never requests the battery-optimisation exemption in v1; expedited work is reserved for user-initiated saves, which fit the quota.

### 4.6 Another device

"Add another device" on the source phone encodes the mnemonic as a NIP-49 `ncryptsec` using a six-digit `SecureRandom` code as the password with log_n 16, shows the QR with ZXing and the digits beneath, keeps the screen on and sets `FLAG_SECURE`; the QR payload also carries the pubkey in clear. The target phone chooses "I already use this app" at first launch, scans with CameraX and ZXing, takes the six digits, decodes, checks the derived pubkey against the payload and stores the key as in section 6. The Library then fills from the relay through normal inbound sync, text blobs downloading on Wi-Fi first and on any network when an item is opened. A fresh code is generated each time the sheet opens.

### 4.7 Sign in as an existing nostr user

The first-launch button "Sign in with your nostr app" opens a sheet with three rows. If a NIP-55 signer is installed the first row names it; tapping sends `get_public_key` with the permission list, then the app calls `nip44_encrypt` and `nip44_decrypt` on a test string and refuses the sign-in with the contract's wording if either returns null or `rejected`. "Connect a remote signer" shows a `nostrconnect://` QR and deep link with an ephemeral client key, the operator relay and a secret, waits two minutes for the NIP-46 `connect` response, runs the same probe and persists the session. Behind an "Advanced" disclosure, a pasted nsec or twelve words is stored exactly as a generated key would be. Signer-backed accounts use `Signer.nip44Encrypt` for every self-encryption, never receive the private key, and cannot use "Add another device", which the You tab hides with a one-line explanation.

On sign-in the app reads kind 10002 and 10013 into `relays`, kind 10063 into the Blossom list, then kind 10003 and every kind 30003. Each `r` tag becomes a pending item with a parse job at two concurrent fetches; each `a` tag to a kind 30023 becomes a `nostr-article` item whose Markdown is the article content, hashed the same way. `e` tags are ignored. The contract's one-time note is a dismissable Library card. Import is capped at 500 entries with an "Import more" action so the first Library paint stays under two seconds.

## 5. UI implementation notes

The stage 0 token file becomes `Tokens.kt` in the shared theme module, exposing exactly the nine colours, the six type sizes, the seven spacing steps, the two radii, and a `ReaderTypography` object with body 18 sp at 1.55 line height in Noto Serif. ## 6. Security

The contract specifies `EncryptedSharedPreferences` backed by the Keystore with the key blob included in Auto Backup. That combination cannot work, and it is the most important finding here. AndroidX `security-crypto` deprecated every API, including `EncryptedSharedPreferences`, at 1.1.0-beta01 in June 2025 and shipped that deprecation as stable 1.1.0 on 30 July 2025, recommending platform APIs and direct Keystore use ([release notes](https://developer.android.com/jetpack/androidx/releases/security)). More seriously, the Keystore master key never leaves the device and is removed with the app, so a restored preferences file on a new phone, or after a same-device reinstall, is ciphertext without a key; the failure is well documented ([The Code Side](https://www.thecodeside.com/2020/09/14/android-auto-backup-keystore-encryption-broken-heart-love-story/)). The plan's check "reinstall and confirm the key returns via credential sync" would fail as written.

The replacement, which I ask the project engineer to adopt into contract section 2, has three layers. Locally, the mnemonic and derived key are written to a file under `noBackupFiles`, encrypted with AES-256-GCM under a Keystore key with `setIsStrongBoxBacked(true)` where available and no user-authentication requirement so background signing works; the file is excluded by `data_extraction_rules`. For recovery without typing twelve words, the app uses Google's Block Store, which keeps up to 16 entries of 4 KB, survives device-to-device restore, and backs up to the cloud with end-to-end encryption on Android 9 and later when a screen lock is set; the app writes the mnemonic there only when `isEndToEndEncryptionAvailable()` is true, and cloud restore needs Android 9 on Pixel and Android 12 elsewhere ([Block Store](https://developer.android.com/identity/block-store)). Block Store is Play services code, so the `foss` flavour omits it and shows the backup card after the first save. The third layer is the recovery code, the only path that works everywhere.

`Signer` has the contract's four methods plus `capabilities()`, reporting NIP-44 availability so the sign-in probe has one place to look. `LocalSigner` decrypts the key into memory on demand, clears it on process trim and signs on a single-thread dispatcher. The NIP-46 client key lives in the same file. NIP-42 AUTH is signed through `Signer`, so a signer-backed account sees one Amber prompt for kind 22242 before the remembered permission takes over.

Blobs use the platform `Cipher` with a per-item key and nonce, hashed before upload and verified after download. NIP-98 headers come from rust-nostr with `u`, `method` and, for POST, `payload` computed by the OkHttp interceptor from the exact request bytes. Cleartext is disabled in the network security config and the advanced relay screen accepts only `wss://`. The share target validates that `EXTRA_TEXT` is a string under 64 KB. The hidden WebView has `blockNetworkLoads`, file, content and cookie access off, never navigates, and receives the HTML as a JSON-encoded argument so nothing from the page is interpreted as script. The recovery sheet, pairing QR and nsec field set `FLAG_SECURE`. Logs never contain content, keys, URLs or titles. Crash reporting is ACRA to an email address, opt-in per crash, off by default in `foss`.

"Delete my data" publishes kind 5 deletions for every known kind 30979 (fifty `a` tags per event) and every id in `wraps_seen`, calls `DELETE /account` with NIP-98, and only then wipes the key file, Block Store entry, Room and caches; the dialog states that copies on relays the user added may persist. If the server is unreachable the deletions still publish and the wipe still runs, with a note that the server audio cache expires after ninety days without access, which the contract already guarantees.

## 7. Testing at each stage

JVM unit tests in `:core:model`, `:core:crypto` and `:core:nostr` cover the normalise fixtures, the three kind 30979 samples decrypting to their JSON, the kind 1059 unwrap, the NIP-98 example reproducing its header, and JSON round trips with unknown fields. The twenty `text_hash` fixtures need Blink, so they run as an instrumented test in `:core:parse` on the CI emulator. Room migrations are tested from schema version 1; the queue is tested against a fake relay that acknowledges, refuses and times out. Instrumented tests also cover the share target end to end with a fake relay and Blossom stub, swipe-archive-undo timing, progress restore, a property test that every spoken-text offset maps to a non-syntax character, and `MediaController` commands. Manual checks run on a current Pixel, a Samsung with its own TTS engine and battery manager, and a de-Googled device on the `foss` flavour.

## 10. Risks

The hidden-WebView parser is the widest risk: it costs memory, needs the main thread, and a few devices lack a WebView provider. Mitigations are the honest-failure state, the week 0 spike, and the fact that the bundle can move to a QuickJS host later without changing output. rust-nostr's alpha status may bring a breaking release mid-build; the version is pinned, the facade isolates it and Quartz is the fallback. Block Store needs Play services, a screen lock and Android 9 or later for end-to-end encryption, so some users will have only the recovery code, which the earlier backup card on `foss` and on Block Store-unavailable devices addresses. Third-party TTS engines that never call `onRangeStart` degrade to paragraph highlighting, tested on Samsung. Doze delays gift-wrap arrival, so the ten-second gate is honest only with the app recently active and the extension toast should avoid promising a time. The `MediaSession` wrapper around `TextToSpeech` is bespoke and the likeliest week 3 overrun. NIP-46 depends on third-party bunkers and stays an existing-user path with generous timeouts and plain copy. Target SDK 36 becomes mandatory on 31 August 2026, before submission, so the build targets 36 from week 0 and its foreground-service and broadcast restrictions are handled early.
