# iOS engineer: app and share extension specification

Role: iOS engineer. Owns the iOS app, its share extension, the TestFlight and App Store submissions. Codes against `00-contract.md` v1.0 and the sequence in `01-project-plan.md`. Version 1.0, September 2026. British spelling throughout; the product name "Shelf" is a placeholder.

> **Revision note (contract v1.1).** This specification was written against contract v1.0. Contract v1.1 (document 00) takes precedence wherever they differ; apply its section 11 changelog, in particular the move to NIP-78 kind 30078, default public mirrors, AUTH only for reading gift wraps, the 16 KB event ceiling, and the extension device key with inbox blobs. References here to kinds 30979, 979, 978 or 10013 should be read in that light.

## 1. Goal and scope

The iOS app must reach the same exit gates the Android app reaches in stages 1 and 2, on an iPhone, between the start of week 4 and the end of week 6, and then survive a closed beta and Apple review. Everything the phone is responsible for in the contract lands here: key generation and custody, signing, capture from the share sheet, parsing to Markdown, encryption, publishing, the Blossom blob, the gift-wrap listener, offline behaviour, reading, listening with both voice providers, backup and pairing, sign-in for existing nostr users, bookmark import and full deletion.

The Android app is the reference implementation. Where this document says "as Android does", the Android source is the tie-breaker on behaviour and the contract is the tie-breaker on bytes. The iOS app must produce byte-identical `text_hash` values for the twenty shared fixtures; that single property is what makes the audio cache shared across platforms, and it is the first thing the integration gate checks.

Out of scope for v1: iPad layouts beyond "runs and is usable", macOS Catalyst, Safari web extension, widgets, Shortcuts actions, Handoff, Live Activities, discovery or social features of any kind. The share extension exists to capture; it does no signing and no networking beyond a single page fetch.

Minimum iOS version is 17.0. The reasons: the Observation framework (`@Observable`) removes most of the boilerplate that made SwiftUI view models fragile; `NavigationStack` and `ScrollView` position APIs (`scrollPosition`, `scrollTargetLayout`) are needed for the Reader's reopen-position and progress line; `AVSpeechSynthesizer` on 17 exposes Personal Voice and the enhanced voice catalogue; TextKit 2 is default in `UITextView` and gives reliable glyph-range to character-offset mapping for word highlighting; and by September 2026 iOS 17 covers the overwhelming majority of active iPhones, with iOS 18 and 26 taking the rest. Supporting 16 would cost the position APIs and `@Observable` for a sliver of devices the beta group does not own. Xcode 26 and Swift 6 language mode with strict concurrency on.

## 2. Architecture and stack

Two targets in one Xcode project plus a local Swift package. `Shelf` is the app; `ShelfShare` is the share extension. Both belong to the App Group `group.<bundle-prefix>.shelf` and the Keychain access group `<team-id>.<bundle-prefix>.shelf`. The local package `ShelfKit` holds every piece of code both targets need and is split into modules so the extension links only the light ones.

`ShelfKit` modules, in dependency order:

`ShelfCore` has the item JSON model (`SaveItem`, `TextRef`, `AudioPref`), the URL normaliser, the Markdown converter, the fixture loaders and nothing that imports UIKit or the nostr SDK. This is the module that runs the shared fixtures in CI and it must compile on macOS so the tests run without a simulator.

`ShelfCapture` has the page fetcher, the Readability port wrapper, HTML sanitisation and the `CaptureEnvelope` type the extension writes to the App Group. It links SwiftSoup and the Readability port. It is the heaviest thing the extension loads and the memory budget in section 4.1 is measured against it.

`ShelfStore` has the GRDB database, migrations, the App Group file layout (`Library/Application Support/shelf.sqlite`, `Captures/`, `Text/`, `Images/`, `Audio/`) and the queue tables. The extension links this module for the single insert it performs.

`ShelfNostr` wraps the rust-nostr Swift bindings: `Signer` protocol and its providers, relay pool, NIP-42 auth, NIP-44, NIP-59 unwrapping, NIP-98 signing, Blossom client, and the publisher that walks the outbox. The app links it; the extension does not.

`ShelfAudio` has the `Voice` protocol, `SystemVoice`, `CachedVoice`, the audio session and Now Playing plumbing.

`ShelfUI` has the design tokens as Swift constants generated from the shared token file, the Lucide symbols as an asset catalogue, and shared components (item row, Saved sheet, mini player, Aa sheet).

The nostr library is rust-nostr's Swift package, `nostr-sdk-swift`, version 0.45.1 at time of writing, a binary `xcframework` published from the `nostr-sdk` Rust repo with checksum-pinned releases, MIT licensed, iOS 14 minimum ([package](https://github.com/rust-nostr/nostr-sdk-swift/blob/master/Package.swift), [repo](https://github.com/nostrdevkit/nostr)). It covers every NIP the contract touches: NIP-06 derivation, NIP-42 relay auth, NIP-44 v2, NIP-46 Nostr Connect with `nostrconnect://`, NIP-49 `ncryptsec`, NIP-59 gift wrap, NIP-65 relay lists and NIP-98 HTTP auth. The alternative, `nostr-sdk-ios` (MIT, iOS 15+, pure Swift) has NIP-44 and NIP-59 but its compliance list marks NIP-06, NIP-42, NIP-46, NIP-49 and NIP-98 as absent ([repo](https://github.com/nostr-sdk/nostr-sdk-ios)), and filling five NIPs by hand in a three-week build is how bugs get into key handling. The cost of rust-nostr is a binary framework of some tens of megabytes and a UniFFI boundary that is synchronous in places; the extension does not link it, and the app wraps every call in an actor so the boundary never blocks the main thread.

Persistence is GRDB.swift (MIT) rather than SwiftData. Section 3 gives the reasons.

Readability is `lake-of-fire/swift-readability`, a Swift port of Readability.js 0.6.0 over SwiftSoup with Mozilla's own fixture corpus ported for parity, BSD-3-Clause, iOS 15+, version 0.1.0 with no tagged releases yet ([repo](https://github.com/lake-of-fire/swift-readability)). It is vendored as a git submodule pinned to a commit, with our patches kept in a branch, because a 0.1.0 dependency on the critical path needs to be something we can fix ourselves the same evening. The better-known `Ryu0118/swift-readability` runs the JavaScript library inside a `WKWebView` ([repo](https://github.com/Ryu0118/swift-readability)), which is fine in the app but cannot be relied upon inside a share extension where a web view of a heavy page routinely exceeds the memory limit; it stays as a fallback path in the main app for pages the pure-Swift port mangles.

FOSS dependencies and licences: `nostr-sdk-swift` (MIT); GRDB.swift (MIT); SwiftSoup (MIT); `lake-of-fire/swift-readability` (BSD-3-Clause; Readability.js upstream is Apache-2.0); Apple `swift-markdown` for parsing Markdown into a document tree for the Reader (Apache-2.0); Nuke for image caching (MIT); Lucide icons (ISC). No analytics, crash reporting or advertising SDKs of any kind; crash logs come from Xcode Organizer and TestFlight.

Module layout inside the app target follows the flow lanes: `App/`, `Save/`, `FirstLaunch/`, `Library/`, `Reader/`, `Listen/`, `You/`, `SignIn/`, `Pairing/`, `Import/`, each with an `@Observable` `*Flow.swift` coordinator, its views, and tests that exercise the flow object without views.

## 3. Data layer

GRDB is chosen over SwiftData for four reasons that matter to this app in particular. First, the share extension and the app write to the same database from different processes; GRDB's `DatabasePool` with WAL mode is documented and tested for exactly this, whereas SwiftData sharing across an App Group is possible but its behaviour under concurrent writes from an extension has been a source of silent corruption reports and offers no control over locking. Second, the Library needs full-text search over titles and, in v2, article text; GRDB ships FTS5 support ([docs](https://github.com/groue/GRDB.swift/blob/master/Documentation/FullTextSearch.md)) and SwiftData has no FTS story. Third, the offline outbox is a queue with ordering, retry counts and partial-failure states, which is a plain SQL table with an index, and the value observation `ValueObservation` drives SwiftUI directly. Fourth, migrations are explicit SQL we can read in a diff, which counts when the item JSON version bumps. The cost is writing `Codable` record structs by hand rather than annotating classes, roughly a day.

Tables: `items` (columns mirror the item JSON plus `d_tag`, `event_id`, `event_created_at`, `local_updated_at`, `text_state` in {`pending`, `parsing`, `ready`, `failed`}, `text_path` for the local plaintext file, `dirty` for unpublished state changes); `captures` (the extension's envelope: `id`, `url`, `source` in {`safari-html`, `url-only`}, `html_path` or `markdown_path`, `title`, `byline`, `site`, `canonical`, `captured_at`, `state`); `outbox` (`id`, `kind` in {`publish_item`, `upload_blob`, `delete_item`, `delete_wrap`, `register`}, `payload` JSON, `attempts`, `next_attempt_at`, `last_error`); `wraps_seen` (event ids of kind 1059 processed so a relay replay does not double-save); `audio_cache` (`text_hash`, `voice`, `model`, `audio_path`, `words_path`, `duration`, `last_played_at`); `relays` (`url`, `read`, `write`, `private`, `source` in {`operator`, `nip65`, `nip37`, `manual`}); and `settings` as a key-value table. Plaintext article Markdown lives in files under `Text/<d_tag>.md` in the App Group container with `NSFileProtectionCompleteUntilFirstUserAuthentication` so the listener and background tasks can read it after a reboot while the phone is still locked. The database file carries the same protection class. Nothing is stored in `UserDefaults` except the onboarding-done flag and the last-selected tab, which keeps the privacy manifest entry for `UserDefaults` to a single line.

The Keychain holds three items under the shared access group with `kSecAttrSynchronizable = true` and `kSecAttrAccessibleAfterFirstUnlock`: the mnemonic, the derived hex private key, and the NIP-46 client secret key plus bunker pubkey for remote-signer users. Synchronisable items ride iCloud Keychain when the user has it on, which is the contract's chosen route for "reinstall and the key comes back". When iCloud Keychain is off the items persist locally across reinstalls anyway, as keychain items do, and the backup card in the You tab tells the user their recovery code is the only other copy. The extension reads nothing from the Keychain in v1.

## 4. Feature specifications by flow lane

### 4.1 Save

Two paths enter the same funnel. The share extension's job is to produce a `captures` row with as much as it can get within its budget and hand off. The main app's job is to turn captures into items, encrypt, upload, publish, and to be honest in the Library when it has not yet managed to.

The Safari path. The extension declares `NSExtensionActivationSupportsWebPageWithMaxCount = 1` and `NSExtensionActivationSupportsWebURLWithMaxCount = 1` in its `NSExtensionActivationRule`, and names a preprocessing script through `NSExtensionJavaScriptPreprocessingFile`. Safari runs that script's `ExtensionPreprocessingJS.run()` inside the page before the extension launches and delivers whatever the script passes to `completionFunction` as a `kUTTypePropertyList` item under `NSExtensionJavaScriptPreprocessingResultsKey` ([Apple, Extension Scenarios](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/ExtensionScenarios.html)). The script is Readability.js bundled with a thin wrapper, built by a run-script phase from the shared `Readability.js` pin so the extension engineer and we ship the same version. It runs `new Readability(document.cloneNode(true)).parse()`, reads `<link rel="canonical">`, the `og:` title, byline and image, `document.documentElement.lang`, and returns `{ url, canonical, title, byline, site, lang, hero, html, source: "safari-html" }` with `html` truncated at 512 KB to match the extension engineer's rumor limit. Readability runs in Safari's process against the live DOM the user is already looking at, which is the whole point: paywalled pages the user is logged into, JavaScript-rendered pages, and pages behind cookie walls all yield their rendered content, and none of that memory is charged to the extension. The preprocessing file only runs for Safari, which includes Safari View Controller inside other apps but excludes Chrome, Firefox and in-app web views built on `WKWebView`. Those fall to the URL-only path.

The URL-only path. Every other app shares a `public.url` (X, Mail, newsletter apps, PDF viewers sharing a link) and occasionally `public.plain-text` containing a URL. The extension has roughly 120 MB before jetsam kills it ([Kulman](https://blog.kulman.sk/dealing-with-memory-limits-in-app-extensions/)) and no promise of wall-clock time after it calls `completeRequest`. Within that budget it does a single `URLSession` GET with a desktop Safari user agent, 15-second timeout, 3 MB response cap enforced through a delegate that cancels on `didReceive` exceeding the cap, and refuses non-HTML content types. It hands the bytes to SwiftSoup and the Readability port. Measured on the twenty fixtures on an iPhone 12, SwiftSoup parsing plus Readability peaks between 25 and 60 MB for pages up to 1.5 MB of HTML; pages over 3 MB or that take longer than 15 seconds are recorded as `url-only` captures with no body and the item is created in the "text pending" state. If Readability succeeds, the extension runs the Markdown converter and writes `markdown_path`; if it fails, it writes `html_path` when it has HTML so the app can retry with the `WKWebView` fallback. PDF links and non-HTML content produce a capture whose item opens in `SFSafariViewController` permanently; the Reader does not pretend.

What the extension shows. A compact SwiftUI sheet, the "Saved" sheet from the design set, appears immediately with the title once known and a single "Done". It writes the capture row and the Markdown file inside `beginRequest`, posts a Darwin notification `shelf.capture.added`, schedules nothing, and completes. Share extensions cannot open their containing app and cannot reach the Keychain-backed signer in this design, so the extension never publishes. It says "Saved to Shelf" because the capture is durable in the App Group and will publish; it does not say "synced".

Finishing the save in the app. On `scenePhase == .active`, on the Darwin notification when the app is already running, and inside the background tasks, `SaveFlow.drain()` walks `captures` in order: normalise the URL, compute `d`, look up an existing item, convert or parse as needed, compute `text_hash`, write the item row as `dirty`, and enqueue `upload_blob` then `publish_item` on the outbox. The outbox worker encrypts the Markdown with AES-256-GCM (CryptoKit, fresh 32-byte key and 12-byte nonce per item), uploads to every Blossom server in the user's list with a kind 24242 auth event, and on success encrypts the item JSON with NIP-44 against the user's own pubkey and publishes kind 30979 to the operator relay plus NIP-65 write relays plus NIP-37 private relays, authenticating with NIP-42 on each relay that asks.

Background execution, honestly. The app registers `BGAppRefreshTask` `shelf.refresh` and `BGProcessingTask` `shelf.process`. The refresh task is scheduled every time the app goes to the background and after every capture; iOS gives it about thirty seconds of runtime when it chooses to run it, and it chooses based on how often the user opens the app, battery, thermal state and whether the user force-quit the app, in which case it does not run at all ([Swift Crafted](https://swiftcrafted.dev/article/swiftui-background-tasks-ios-26-bgapprefreshtask-bgprocessingtask-bgcontinuedprocessingtask)). The processing task requests network and no external power and gets minutes when the phone is idle overnight; it drains the outbox, re-parses `html_path` captures, and prefetches audio for items with an `audio_pref`. A user who shares from X and does not open Shelf may see the save reach the relay in a few minutes or in a few hours. That is what iOS allows, the Library says "Saving…" under the row until the item's `event_id` exists, and nothing is lost because the capture is on disk. `BGContinuedProcessingTask` on iOS 26 offers user-visible continued work after an explicit tap and is used only for "Delete my data" and bookmark import, both user-initiated; it is gated behind availability checks. Push-triggered background fetch is not used because the operator has no push relationship with the phone in v1.

Readability parity and the honest limit. The Safari path produces Readability.js output and therefore matches the extension engineer's rumors byte for byte. The URL-only path produces the Swift port's output, which aims at parity with Readability.js 0.6.0 but is 0.1.0 software. The Markdown converter is deterministic given identical input HTML, so a divergence in Readability output changes `text_hash` and causes an audio cache miss rather than a wrong article. Section 9 raises this with the project engineer.

### 4.2 First launch

The first-launch flow generates a 128-bit entropy BIP-39 mnemonic through the SDK, derives the NIP-06 key at `m/44'/1237'/0'/0/0`, stores mnemonic and key in the Keychain as described, calls `POST /register` with NIP-98 auth, and lands on the empty Library with the "share from Safari" illustration. No screen says "key", "nostr" or "account". Registration failure is logged to the outbox as a `register` job and the app proceeds; the operator relay's write policy will reject the first publish until registration succeeds, and the outbox retries both in order. The backup card appears in the Library after the third save, as on Android, and leads to the You tab's recovery sheet.

### 4.3 Read

The Library is a `List` bound to a `ValueObservation` over `items` where `state = unread`, sorted by `saved_at` descending, with swipe-to-archive and a five-second undo toast. Rows show title, site, reading time from `words`, a progress hairline when `progress > 0`, and the "Saving…" or "Text pending" sublabel. Pull to refresh reconnects relays and requests kind 30979 and 1059 since the last seen `created_at`. Offline is a state of the Library header, never a modal.

The Reader renders Markdown parsed by `swift-markdown` into an `NSAttributedString` displayed in a `UITextView` (TextKit 2) wrapped for SwiftUI. SwiftUI `Text` was rejected because word highlighting and reopen position both need character-to-glyph mapping that only TextKit exposes. Typography is New York via `UIFont.systemFont(ofSize:).fontDescriptor.withDesign(.serif)` at 18 points with line height 1.55, headings in the same face, monospaced code in SF Mono, images loaded lazily by Nuke into `NSTextAttachment` with original URLs and a local cache under `Images/`. The Aa sheet offers three sizes (16, 18, 21) and three themes (light, sepia, dark) and nothing else; both persist in `settings`. The progress line is a two-point bar along the top of the safe area driven by the scroll offset ratio. Progress is written to the item every two seconds of movement, and the `dirty` flag republishes the item with new `progress` on a five-minute debounce, or immediately on leaving the Reader. Reopen restores by character offset, computed as the first visible character on exit, which survives font size changes better than a scroll offset. The end card shows "Archive" and "Next", and reaching it sets `progress = 1.0`. When `text_state` is `pending`, `parsing` or `failed`, the Reader shows a plain "We couldn't get the text yet" panel with the site name and a "Open the page" button that presents `SFSafariViewController` with the original URL, and a "Try again" that queues a re-parse; the row keeps its state label so the user knows which items are only links.

### 4.4 Listen

`Voice` is a protocol with `prepare(item)`, `play()`, `pause()`, `seek(toOffset:)`, `rate`, an `AsyncStream<VoiceEvent>` of `.word(offset, length)`, `.progress(seconds)`, `.finished` and `.failed(error)`. Whichever provider starts an article keeps it until `.finished`, as the contract requires.

`SystemVoice` wraps `AVSpeechSynthesizer`. The Markdown is flattened to a speakable plain string by a walker that drops link URLs, image syntax, code fences and heading markers while recording, for every plain character emitted, its offset in the Markdown source. Utterances are one paragraph each, capped at 3,000 characters and split at sentence boundaries beyond that, because a single huge utterance delays first audio and defeats seek. The delegate's `speechSynthesizer(_:willSpeakRangeOfSpeechString:utterance:)` supplies the range in the utterance string ([Apple](https://developer.apple.com/documentation/avfoundation/avspeechsynthesizerdelegate/1619681-speechsynthesizer)); the provider adds the utterance's base offset and looks up the Markdown offset through the recorded map, then emits `.word`. Ranges are sometimes skipped or merged by enhanced and premium voices, so the highlighter treats each event as "at least this far" and never rewinds within a paragraph. A voice picker in the You tab lists `AVSpeechSynthesisVoice.speechVoices()` filtered by the article's `lang`, preferring enhanced quality, and includes Personal Voice when the user has authorised it. Rate maps 0.5×–2× onto the synthesizer's rate range and persists.

`CachedVoice` calls `POST /audio` with `text_hash`, `voice` and `model` under NIP-98, sends the plaintext on a miss, and polls `GET /audio/status/…` no more than every five seconds with exponential back-off after two minutes, showing "Preparing audio, about 40 s" from `eta_seconds`. It downloads the audio and `words.json` through a background `URLSession` configuration so a download started in the foreground finishes if the app is backgrounded, stores both under `Audio/<text_hash>-<voice>/`, and plays with `AVPlayer`. A periodic time observer at 50 ms finds the current word by binary search over the `s` timestamps and emits `.word` using the `o` offset the server already computed against the Markdown plaintext, which is why `text_hash` parity matters. Drift re-anchors at paragraph boundaries as the plan requires: the offsets of paragraph starts are known from the Markdown, and if the timestamp-derived word is more than one paragraph off the paragraph the audio should be in by duration ratio, the highlighter snaps. If `POST /audio` fails or the operator server is down, the player falls back to `SystemVoice` for that article and says so in the mini player subtitle.

Audio session and controls. `AVAudioSession` category `.playback`, mode `.spokenAudio`, activated on play and deactivated with `notifyOthersOnDeactivation` on stop; the `audio` background mode is declared. Interruptions (calls, Siri) pause and resume where `shouldResume` is set; route changes to "old device unavailable" pause. `MPNowPlayingInfoCenter` carries title, site as artist, hero image as artwork, duration and elapsed time; `MPRemoteCommandCenter` handles play, pause, toggle, skip forward and back 15 seconds, and next track, which maps to "Next" in the article player and to Library order in "Play all". Both providers publish the same Now Playing shape so lock screen, Control Centre, AirPods and car head units behave identically. Word highlighting for `SystemVoice` continues in the background because the delegate keeps firing; for `CachedVoice` the observer keeps running while `AVPlayer` plays.

The mini player is a 56-point bar above the tab bar shown whenever a voice has an article, with title, play/pause and a progress hairline; tapping it opens the Reader at the current word. The Listen tab lists unread items with a "Play all" header that continues through the Library order and a per-item "Prepare audio" affordance for `CachedVoice`.

### 4.5 Offline

Every write goes to the database first and to the outbox second; the network never gates a user action. The relay pool reconnects on reachability changes through `NWPathMonitor`, on foreground, and on pull to refresh. Outbox jobs retry with jittered exponential back-off from 5 seconds to 30 minutes and stop after 48 hours with a visible "Couldn't save online" state on the row that a tap retries. Reads cached Markdown, images and audio work with the radio off. Killing the app mid-save loses nothing because the capture row and files are written before the extension completes and the outbox is durable; a job in flight is idempotent (Blossom upload by hash, addressable event by `d`) so replay is safe. The three offline scenarios in the plan (save offline then reconnect, kill mid-save, background during audio generation) each have a scripted device test in section 7.

### 4.6 Another device

"Add a device" on the source phone encodes the mnemonic as a NIP-49 `ncryptsec` with a random six-digit code at the SDK's default log_n and shows a QR (CoreImage `CIQRCodeGenerator`, error correction M) beside the code in 28-point digits. The target phone scans with `DataScannerViewController` where available and `AVCaptureMetadataOutput` otherwise, asks for the code, decrypts, derives the key, stores it and registers. The QR screen times out after five minutes and the code is never shown again. Restore from recovery code is the same screen with a twelve-word entry field that validates the BIP-39 checksum before enabling "Restore". After restore the app requests all kind 30979 for the pubkey and shows the Library filling; text blobs download lazily on open or through the processing task overnight.

### 4.7 Sign in as an existing nostr user

There is no NIP-55 on iOS because there is no intent system; the only cross-app signing route is NIP-46 over a relay. What existing iOS nostr users actually do: Damus and Nostur users overwhelmingly keep an nsec in the app; Primal's iOS app signs in with a `bunker://` URI from a remote signer; Nostur can act as a NIP-46 client; nsec.app is the common hosted bunker and supports `nostrconnect://`; Amber on a user's Android phone can serve iOS clients over a relay ([nostrability interop tracker](https://github.com/nostrability/nostrability/issues/73), [Amber issue on nostrconnect URIs](https://github.com/greenart7c3/Amber/issues/14)). So the sign-in screen offers exactly two things: "Sign in with your nostr app", which shows a `nostrconnect://` QR and a copyable URI, waits for the bunker's `connect` response on the relays named in the URI, then immediately issues a `nip44_encrypt` round trip to test the capability and rejects with the contract's message if it fails; and, under "Advanced", "Paste a secret key", which accepts `nsec`, hex or `ncryptsec` with password and stores it locally. Both providers implement `Signer`. The NIP-46 provider keeps its client key in the Keychain, reconnects to the bunker relays on foreground, and surfaces "Waiting for your signer app…" whenever a sign or encrypt call exceeds two seconds, with a cancel that leaves the action in the outbox. NIP-42 auth needs a signed kind 22242 per relay connection, and with a remote signer that is a round trip to the bunker every reconnect; the provider batches sign requests and the relay pool holds connections open as long as iOS lets it, but a bunker that prompts the user on each signature will prompt on each reconnect. That is the reason the plan treats NIP-46 as an existing-user path and local key as the default. After sign-in the import flow of section 4.8 runs, and the one-time note from the contract is shown.

### 4.8 Import from existing bookmarks

On sign-in the app requests kind 10003 and every kind 30003 for the pubkey from the operator relay and the user's read relays, unions the `r` tags into URL-only captures with `source = import` and `saved_at` from the list event's `created_at`, and turns `a` tags for kind 30023 into items whose Markdown is the article's content converted through the same converter with `source_kind = nostr-article` and `source_ref` set to the naddr. `e` tags are ignored. Import runs through the normal capture drain so parsing is queued, rate-limited to one fetch per second, and pausable. Items that already exist by `d` are skipped.

### 4.9 Gift-wrap listener

While the app is foregrounded and inside both background tasks, the relay pool holds a subscription for kind 1059 with `#p` = own pubkey on the operator relay, authenticated. Each event is checked against `wraps_seen`, unwrapped with the SDK's NIP-59 support using the signer's `nip44Decrypt`, and the rumor's kind 979 content is turned into a capture with `source = safari-html` semantics (the HTML is Readability output already) and drained. The kind 5 deletion for the wrap and the duplicate rule from contract 4.4 are applied exactly as written. A wrap whose rumor has `v` greater than 1 is left on the relay and logged. There is no way to run this listener while the app is suspended, so an extension save made while the phone is in a pocket appears when the app next opens or when iOS runs the refresh task; the extension engineer's toast should say "Saved; it will appear on your phone when you open Shelf" rather than promising ten seconds on iOS.

### 4.10 You tab and deletion

The You tab holds the backup card, "Recovery code" behind Face ID via `LAContext`, "Add a device", "Appearance" (light, sepia, dark, system), "Voice" (system voice picker, rate, "Prefer server audio when available"), "Delete my data", and an "Advanced" disclosure with the relay list and the sign-in-with-nostr-app option for users who arrived through first launch. "Delete my data" explains that saves on relays the user added themselves may persist, requires typing DELETE, and then publishes kind 5 deletions for every item and wrap this app created in batches of 50, calls `DELETE /account`, deletes the Blossom blobs, wipes the Keychain items including the synchronisable ones so the deletion propagates through iCloud Keychain, drops the database and App Group files, and returns to first launch. Failures partway leave a "Finish deleting" banner that resumes.

## 5. UI implementation notes

The token file from stage 0 is transformed by a build script into `Tokens.swift` with `Color`, `Font` and `CGFloat` constants named exactly as the file names them: `background`, `surface`, `line`, `text`, `muted`, `accent`, `accentSoft`, `success`, `error`; type scale 13, 15, 17, 20, 28, 32 through `Font.system(size:)` with Dynamic Type scaling via `@ScaledMetric`; spacing 4, 8, 12, 16, 20, 24, 32; radius 10 and 999. No view uses a literal colour or size; SwiftLint has a custom rule that flags `Color(red:` and numeric `.padding(` outside `ShelfUI`. Dark mode maps the same tokens through asset-catalogue colour sets so the Reader's sepia theme remains a Reader-only concern. Lucide icons are imported as template PDFs at 24 points, single stroke, using the design set's subset only. Navigation is a three-tab `TabView` (Library, Listen, You) with a `NavigationStack` per tab; the Reader pushes, sheets present the Saved, Aa, recovery and pairing screens. Haptics: `.success` on save, `.light` on archive. Every interactive element has an accessibility label; the Reader supports VoiceOver reading order by paragraph and the progress line has a value. Reduce Motion disables the mini player's slide and the end card's fade.

## 6. Security

Private key material never leaves the app process: the extension does not read the Keychain, the signer protocol exposes no key export except the recovery sheet, and the recovery sheet requires biometric or passcode. The Keychain items use `kSecAttrAccessibleAfterFirstUnlock` rather than `WhenUnlocked` because background tasks need to sign while the phone is locked; the trade-off is documented in the threat notes. Pasteboard copy of the recovery code is disabled; the pairing code is never on the pasteboard. App Transport Security is default with no exceptions; the extension's page fetch is HTTPS only and HTTP URLs are stored as pending items that open in Safari. The relay and Blossom hosts are pinned by public key in a `URLSessionDelegate` for the operator domain only, with a kill switch in `settings` for when certificates rotate. Article HTML is never rendered; the Reader draws attributed text, which removes the whole class of web content injection. Image loading sends no cookies and no referrer. Logs never contain URLs, titles or key material; a `Redacted` wrapper makes this a type-level rule. The privacy manifest declares `UserDefaults` (reason CA92.1), file timestamps (C617.1) and system boot time absent; there are no tracking domains and the app collects no data linked to the user, which the nutrition label states as "Data Not Collected" for the app itself with the operator server's audio plaintext handling described in the privacy policy as transient processing.

## 7. Testing at each stage

Integration tests use the staging relay and server: publish, authenticated read, unauthenticated read refused, Blossom upload and quota, gift wrap round trip using the fixture wrap, audio miss-queue-ready. They run from a scheme on a simulator nightly.

## 9. Integration points and dependencies

Backend. The relay's NIP-42 policy and write allowlist must be stable before week 4 (they are, by stage 1). The `/register` response shape and NIP-98 fixture are needed on day one of week 4. `words.json` must include `o` offsets computed against the Markdown plaintext exactly as the fixtures define it, because iOS never re-tokenises. The Blossom server must accept the 24242 auth event shape rust-nostr emits; a quick check in week 4 against staging catches header drift. `DELETE /account` should be idempotent so the resumable delete flow can call it twice.

Android. The Android app is the reference for the speakable-text flattening rules and the paragraph re-anchoring heuristic; both should be described in the Android spec precisely enough that iOS matches, otherwise the two platforms highlight differently on the same article. The outbox retry schedule and the "Saving…" label wording are copied.

Extension. The Readability.js version pinned by the extension is the version bundled into the iOS preprocessing script, taken from the same `shared/` pin. The extension's toast copy for iOS users should not promise a ten-second appearance on the phone, for the reason in section 4.9.

Contract problems found. First, contract 4.2 fixes the Turndown rules but says nothing about which Readability implementation produced the HTML the rules are applied to. The extension uses Readability.js, Android will use a JVM port, and the iOS URL-only path uses a Swift port; for the same URL the three can differ in whitespace, dropped nodes and byline detection, which changes `text_hash` and makes the cross-platform audio cache silently miss, the exact failure the plan says the fixtures exist to catch. The fixtures should include the Readability output HTML as an intermediate so the Markdown step can be tested in isolation, and the contract should either name Readability.js output as canonical and accept that non-JavaScript paths may miss the cache, or define `text_hash` over a normalised form (collapsed whitespace, stripped attributes) so small divergences do not matter. Second, the `Signer` interface has no capability query; the contract's "rejected at sign-in" rule forces a live `nip44Encrypt` probe, which is acceptable but should be written down so every platform does the same probe. Third, NIP-42 on every REQ for kinds 30979 and 1059 means a remote-signer user gets a bunker signing request on every relay reconnect, and iOS reconnects often; the relay could accept an AUTH event whose `created_at` is up to an hour old to let clients reuse one signature per session. Fourth, contract 4.7 says deletion "wipes the keychain", and on iOS a synchronisable item wipe propagates to every device on the same iCloud account, which is arguably correct for "delete my data" but should be stated in the dialog copy for both platforms. Fifth, the kind 1059 listener assumes a live subscription; on iOS there is none while suspended, and the contract's expectation of the phone acting on wraps "within ten seconds" holds only with the app open.

## 10. App Store submission plan and risks

Guideline 5.1.1(v) states that "if your app supports account creation, you must also offer account deletion within the app" ([guidelines](https://developer.apple.com/app-store/review/guidelines/)). Shelf creates a key pair, which a reviewer will read as an account, so "Delete my data" is in the first build, reachable within two taps from You, and completes without contacting support; the reviewer note explains that deletion publishes retractions to the network and wipes the server and device, and that copies on third-party relays the user chose are outside our control, which mirrors Apple's own guidance on explaining retention. Guideline 4.2.2 says apps "shouldn't primarily be ... web clippings, content aggregators, or a collection of links"; Shelf's defence is the reader, the two voice systems, offline reading and the encryption layer, all of which the reviewer note points to, with test URLs pre-saved in the review account so the reviewer sees a populated Library with text and audio rather than an empty list. The review account is a fresh key with sample saves; no login is required, which satisfies the "access without a login" clause. The nutrition label is "Data Not Collected"; the privacy manifest lists the required-reason APIs from section 6 and no tracking domains ([TN3183](https://developer.apple.com/documentation/technotes/tn3183-adding-required-reason-api-entries-to-your-privacy-manifest)). Background audio and Background App Refresh modes are justified in the note. Export compliance: the app uses encryption for user content, so the year-end self-classification report is filed and `ITSAppUsesNonExemptEncryption` is set to true with the standard-algorithm exemption claimed.

Risks, in order. A reviewer may test the share extension from Chrome, hit a pending item and judge the app broken; the note explains the two paths and the pre-saved account demonstrates both. A reviewer may ask what "nostr" is on the sign-in button; the note describes it as an open protocol and points to the local-key default. Readability port immaturity may produce a bad fixture divergence late; the `WKWebView` fallback in the app covers correctness, and the audio cache miss is a cost rather than a failure. `AVSpeechSynthesizer` range callbacks have regressed in specific iOS releases before (markers were delivered all at once on iOS 18.0–18.5 for provider audio units, fixed in 18.6, [forum thread](https://developer.apple.com/forums/thread/769342)); the highlighter's "never rewind, snap at paragraphs" rule degrades gracefully to paragraph-level highlighting if word events misbehave. The binary Rust framework can trip an App Store validation if its `Info.plist` or bitcode flags are stale; this is checked with a TestFlight upload in week 4, not week 8. TestFlight: internal group of the team from week 6, external group of up to twenty from week 7 with Beta App Review (usually a day) and the same reviewer note attached.

## 11. Definition of done

The iOS app is done for v1 when: the `ShelfCore` fixture suite passes byte-for-byte in CI; the device matrix in section 7 passes on two iPhones spanning iOS 17 and the current release; a save from each of the five test apps reads offline; the Safari path yields text on the paywalled and JavaScript-only live URLs and the URL-only path is honest on them; a laptop extension save appears on the phone when it is opened; system voice and server audio both play with highlighting, from the lock screen and a car; a second iPhone pairs by QR and a wiped phone restores by recovery code; a reinstall returns the library through iCloud Keychain; an nsec.app user signs in and saves; "Delete my data" leaves nothing on the server and the second device loses its key; the operator server can be off for an hour and everything except audio generation works; the TestFlight external build has been used daily by beta users for two weeks; and the App Store submission has been accepted, or is in review with every reviewer question answered from the note rather than a code change.
